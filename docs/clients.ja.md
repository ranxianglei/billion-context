## dsh (deepseek-harness)

2 つのレーン、同じプラグイン (#941)：

- **ランチャー：** `bili dsh` は `--patch` オーバーレイ（`~/.dsh-bili/.bili-acp.patch.yml`）を通じて完全なネイティブプラグインを注入します — すべてのプロファイルが bili ツールをネイティブ登録した状態で起動し、モデル要求は `x-bili-plugin` + dsh セッション id を帯びる（プラグインモード）、`/acp` はセッションにバインドされます。dsh のネイティブ自動圧縮は同じパッチ内で無効化されます（ホスト平面的な `compaction-basic` → `auto: false`；web プロファイルのプリセットインスタンスは #3354 のオーバーレイによりロード時に無効化される）；手動 `/compact` は非 web プロファイルでは利用可能のままです。同じパッチは組み込み DeepSeek ルートのリトライホワイトリストに `MALFORMED_RESPONSE` も追加するため、ツール呼び出し引数の JSON を壊す 1 回のサンプリング乱れはターンを殺すのではなくリトライされます (#2605)。
- **プロファイルインストール（ランチャーなし）— 1 レーン (#966)：** `bili plugin install dsh` は既存のプロファイルすべてに対して `dsh plugin --profile <name> add billion-context` を実行します — pnpm がパッケージを各プロファイル自身の `node_modules` にインストールし、dsh がバンドルされたパッチレイヤー（`dsh.bundle.patch.yml`）を自動的にマウントします — `bili-native` をマウントして dsh の自動圧縮を無効化するほかに、組み込み DeepSeek ルートのリトライホワイトリストに `MALFORMED_RESPONSE` を追加します (#2605)；プロファイル自身の `cordis.patch.yml` はその後で適用されるため、そこに書かれた完全な `retryPolicy` はこれを上書きします。spec は bili 自体のインストール方法を踏襲します (#925)：npm 形式のインストールはレジストリ名を渡す、チェックアウト/開発ビルドは絶対パスを渡す（`link:` 依存なので、ローカル作業がライブのまま）。レガシーの管理ブロック（`# bili begin` / `# bili end`、#966 以前のインストールが書いたもの）はインストールと削除の際に取り除かれ — ユーザーのエントリとコメントは残され、空になったファイルにはプレースホルダの `[]` が戻る — まず各プロファイルで一度だけ dsh を実行してプロファイルディレクトリが存在させます。プラグインはロード時に独自のプロキシを spawn します（健康なものがあればそれに取り付き二重化しない；親 pid ウォッチドッグ）、グローバル fetch と Codex Responses WebSocket パッチ（#5838）を通じてモデル API トラフィックを `<proxy>/bili/<upstream-url>` に書き換え、マニフェストのツールをそのまま登録し、ツール準備完了を条件にプラグインモードヘッダをゲートします。WS アップグレードは登録完了を待ち、DSH のセッション/モデルヘッダを帯びる；すべての `response.create` は帰属判定とフォーク準備を待って実行されます。キャッシュされたソケットは identity/model、プラグイン有効化、またはプロキシオリジンの変更後の送信を拒否し、再接続が必要になります（あるいはプロバイダーの SSE フォールバック）。他の WebSocket は触れません。オプトアウト：`BILI_NATIVE_DSH=0`。削除は `bili plugin remove dsh` または `dsh plugin --profile <name> remove billion-context` — どちらも同じチャネルを経ます。レジストリからのインストールは `dsh.bundle.patch.yml` を含む公開リリースが必要です；npm 形式を使ってください — GitHub ソースアドレスだと `dist/` なしのソースがインストールされるため（エントリポイントが宙吊りになり dsh はバンドルを黙ってスキップする；代わりにインストール時のガードが明白に失敗する、#2471）。add の直後に `billion-context/dsh` で `ERR_MODULE_NOT_FOUND` が起きて dsh がブートできない場合、プロファイルが古いパッケージメタデータキャッシュからバンドル前のコピーを解決しています (#953) — pin 指定で再追加してください：`dsh plugin --profile <name> add billion-context@latest`。
- **Codex WebSocket レグ (#5838)：** 埋め込まれた pi-ai の `openai-codex` プロバイダーはデフォルトが `transport: auto` で、直接の WebSocket 交換を優先します — 成功した WS ラウンドトリップは決して fetch を呼びません。したがって WS レーンの修正より前に出荷されたビルドでは、そうしたモデル要求が見えることが決してありません：ACP ツールは 404 で応答し、コンテキスト上限まで何も圧縮されません。そのようなビルドでは、DSH の既存の設定 `providers.openai-codex.transport` を `sse` に設定してください（ホット設定；新しい bili 設定キーは不要）するとトラフィックが fetch レグに乗ります；修正リリース以降は WebSocket レグが自動的にインターセプトされてヘッダが押印されます。
- **境界 — サードパーティの Codex トランスポート：** 自分自身の Codex WebSocket クライアントを組み込むプラグインは、構造上 bili のインターセプトを回避します。2026-11-08 に実在で発見された例：`connectionMode: websocket` の `dsh-codex-subscription` は `ws` パッケージを直接 import し、ホストごとに `globalThis.WebSocket` を Proxy に差し替えるため、モデルフレームはグローバル fetch/WS パッチを通ることが決してなく — プロキシ可視性がなく、ACP ツールは 404 に応答し、ネイティブ圧縮が抑制されているため圧縮パスがまったく存在しません（#5838 の第 2 の原因）。プラグインが CONNECT プロキシエージェントが不要なときに環境の `globalThis.WebSocket` をそのまま通すようになるまで、`connectionMode: sse`（プラグインのデフォルト）を使ってください；host 所有のプロファイルバンドル内部のモジュールスコープの `ws` import を bili がインターセプトすることはできません。
- **デスクトップアプリ（Electron ホスト）：** 同じプラグインは deepseek-harness の**デスクトップ**アプリ内でも動作し、そのアプリ内プラグインマネージャを通じてインストールされます。そこでブートストラップはアプリプロセスの内側からプロキシを spawn しますが、その `process.execPath` は Node ではなく Electron バイナリであり、GUI の PATH には通常のインストール場所が含まれていません — `resolveNodeRuntime` (#819/#1429) はまずよく知られた場所を探索します（`/opt/homebrew/bin`、`/usr/local/bin`、Volta など）し、アプリ自身のバイナリをプレーンな Node として実行すること（`ELECTRON_RUN_AS_NODE=1`、子プロセス環境に強制）にフォールバックするため、PATH に独立した Node がなくてもゼロ設定で圧縮が動作します；特定の Node を強制するには `BILLION_CONTEXT_NODE` を設定してください（両方に優先）。#1429 以前はこのパスは spawn 前に例外を投げ、すべてのセッションが直接送信（非圧縮）に黙って退化しており、bili.log でしか見えませんでした。
- **自動更新がプロファイルをロックステップに保つ：** リフレッシュには 2 つのトリガーがあります — グローバル自己更新のあと、および**プロファイルコピー自身のプロキシ**から（その定期チェックが新しいレジストリバージョンを見つけたとき；つまりグローバルの bili を走らせない dsh プラグインマーケットユーザーでもリフレッシュされる、#1196）。どちらも `~/.dsh/profiles/*/package.json` をスキャンし、レジストリに pin された `billion-context` 依存を目標バージョンまで引き上げます（グローバルトリガーなら新しいグローバルバージョン、セルフトリガーならレジストリ最新）— いずれも必ず dsh 自身の `plugin add` チャネルを通じて — いつものインプレースコピーではなく — そのためロードされたプラグインとプロキシが再び乖離することがありません (#953)；ローカルソースに pin されたプロファイルは触られません。リフレッシュはベストエフォートで、失敗すれば次のサイクルで再試行し、更新やプロキシを失敗させることはありません。
  - **報告済み：profile インストール下で一部のトランスポートにプロキシトラフィックがゼロ (#1158、調査中)：** dsh の `llm-pi-ai` レイヤートランスポートの一部によって提供されるセッションでは、モデル要求がプロキシに到達したことが**ない**（`processTurn` のログなし；bili ツールは「no model request has arrived」で 404）一方、同じホスト内の他のプロバイダーは正常に動作します。根本原因はまだランタイム証拠で絞り込まれており — 候補：トランスポートレベルの fetch の形（SDK 注入 fetch / グローバルでないディスパッチャ）か、引き継ぎゲートがトラフィックを未主張のままにするホスト側の帰属ギャップ — 検出方法：プロキシが一時的な `[plugin] NO MODEL REQUESTS seen for conversation …` 警告をログに出し、dsh プラグインが帰属ゲートがプロキシせず通過させた各異なるエンドポイントをログに出します（プロセスごとに 1 回）。当面の確実な回避策：代わりに `bili dsh` 経由で起動する — ランチャーの設定オーバーレイがそうしたプロバイダーの `baseURL` を `/bili/` URL に書き換えるため、トランスポートがどの fetch を使おうと、帰属状態がどうあれ、トラフィックはプロキシに到達します。
   - **web プロファイルの圧縮 (#1772、#3354 で解決)：** プロファイルのバンドルに `@deepseek-ai/dsh-web-app` が含まれる場合、稼働中の `compaction-basic` インスタンスはエージェントのプリセット（`preset-standard.config.plugins`）の中にあります。いかなるパッチレイヤーもそのネストされた行を id で指定できません — dsh のパッチエンジンはトップレベルの行と真のグループ子しか索引しない — ため、バンドルの `auto: false` は web-app のすでに無効化されているホスト平面の行に着地して何も変わりません。#3354 以降、bili はこのギャップを**ロード時**に埋めます：常時有効なバンドルエントリ `bili-compaction-gate` — `bili-native` と並ぶ別の cordis エントリで、同じパッチレイヤー群にマウントされるため、`bili-native` が無効化またはキルスイッチされたときも生き残る (#3662) — これは cordis の `internal/config` オーバーレイ（deshark42/dsh-compaction-basic-disable から vendored、MIT）を登録し、bili がレーンを所有している間プリセットの `compaction-basic` と `command-compact` 行を `disabled: true` にマークします。またバンドルパッチのプリセットゲート行により、各 web プリセットはそのオーバーレイのサービスが登録されるまで待つようになります。これらのプロファイルでもネイティブ自動圧縮は OFF です（`/compact` もそこで利用できない — これは**期待どおり**でありバグではありません (#4002)：bili がレーン上で圧縮を所有するため、プリセットの compact コマンドとその自動圧縮は両方とも意図的に退いている；設計上再有効化スイッチはありません (#3651/#3666)、configuration.md を参照）；ACP 圧縮には影響しません。#4147 以降、オーバーレイは**構造的に**マッチします — 解決後の `config.plugins` が `compaction-basic`/`command-compact` 行をネストしているあらゆるエントリがそれらを無効化され、カスタムやプロファイルローカルのプリセットもファクトリのものと全く同じように扱われます（`dsh.bundle.patch.yml` の 4 つのゲート行 id はファクトリ名簿のための順序保険であり、カバレッジの境界ではありません — 他のプリセット id を出荷するプロファイルは構造的な走査でカバーされます）。一時的な `[dsh-client]` ブート注記はオーバーレイが書き換えた実際のエントリ名を明示します (#3962) ため、名前が変わった名簿でのパッチ行の取りこぼしもホストローダのログを読まなくても見えます。オーバーレイは dsh の**内部**フックに乗っておりバージョンに敏感です — 新しい/古い dsh ビルドで dsh の圧縮チェックポイントが届くのがまだ見える場合は、#2474 の手順にフォールバックしてください：プロファイルレベルのパッチ（あなたのプロファイルの `cordis.patch.yml`、全バンドル後に適用）が id で preset-standard を上書きし、**フルスナップショット**の `config` を与えます — `dsh --profile <name> --dump-config` から完全なプリセット設定をコピーし、その `compaction-basic` 行の下に `config.auto: false` を加え、結果を `cordis.patch.yml` に追記します。設定の置換は**丸ごと**です：部分スニペットだと再言及されていないものはすべて黙って落ちます — プリセット自身の `id`/`order` identity（名簿に認識されなくなる可能性がある）も含み — また同じ id の `- insert:` はマージするのではなく第 2 の死んだ行を追加します。スナップショットは dsh のプリセット更新後に再コピーされるまで名簿を凍結します。そのようなプロファイルではプラグインは一時的な `[dsh-client]` 注記をブート時にログ出し、両方のパスを明示します。
    - **プラグインの無効化 vs 削除 (#3662)：** #3662 以前、`bili-native` を無効化すると（dsh プラグインマネージャ、または任意のパッチレイヤーでの `disabled: true`）、ゲートサービスの唯一の提供元が消えながらプリセット行はそれを待ち続けていました — 4 つの web プリセットすべてが永遠に pending のままとなり、すべての新規/再開セッションが `Unknown agent preset: standard` で失敗しました。サービスは現在、別の常時有効な `bili-compaction-gate` エントリに移っています：`bili-native` を無効化またはキルスイッチ（`BILLION_CONTEXT_PLUGIN=0`）しても、レーンは**純正 dsh の挙動**に戻ります — プリセットは正常にブートしネイティブ自動圧縮が復帰し、単に圧縮がオフになるだけです。**`bili-compaction-gate` 自身は無効化しないでください** — それ brick が再現されます。完全にアンインストールするには、プロファイルの `dsh.profile.bundles` から `billion-context`（とその依存）を削除して再起動してください：パッチレイヤー全体が消え、`compaction-basic` は純正の `auto: true` に戻ります。すでにプラグインが無効化済みの #3662 以前バージョンで固まっている場合、アップグレードで自己修復します（パッチレイヤーは bundles に載っているパッケージからマウントされるため、`bili-native` の状態に関係なく）；手動の brick 解除は HOME レイヤのパッチ `$DSH_HOME/cordis.patch.yml`（`DSH_HOME` が未設定なら `~/.dsh/cordis.patch.yml`）に 4 行を追記することです — `- id: preset-standard` / `preset-ptc` / `preset-minimal` / `preset-cordis`、それぞれ `inject: null` を付けて。トップレベルのキーは丸ごと置換され、pending ラッチがクリアされます。
    - **グローバルコピーがロード時にプロファイルコピーを影にする (#2891)：** dsh は `dsh.profile.bundles` 中の裸の `billion-context` 名をインストールアンカー優先で解決します — プロファイルの `node_modules` よりも自分のインストールツリー（グローバル npm ルート）から先に。つまりマシン全体の `billion-context` がプロファイルローカル版と併存する場合、dsh は**グローバル**コピーを読み、プロファイル側のは黙って無視されます — クラッシュもログエントリもない。両者が異なると、プロファイルが宣言したものとは異なるビルドが動いている可能性があります（例：#1590 以前グローバルには `dsh.client` web フェースがないため、設定ページのメニューが消えただけ）。これはデフォルトですべての場所で目に見えません：`bili doctor` はプロファイルごとに乖離したグローバル-vs-プロファイルペアをフラグ付けします (#2891)；dsh が実際に何を読み込んだかは `dsh --profile <name> --dump-config` で確認できます（バンドルの `name:` 行を読む）。

`bili dsh` 起動下では、プラグインはランチャーのプロキシに**取り付きます**（第 2 の spawn はなし）。生のアップストリーム URL は spawn モードと同様に `<proxy>/bili/<url>` に書き換えられます（ループバックのプロキシ目标是決してプロキシされないため、MITM 環境変数は単純にバイパスされる）；すでにルーティング済みの `/bili/` プレフィックス付き要求はヘッダ押印を除いてそのまま通過します。既知の制約：手動 `/compact` には dsh 側のイベントフックがないため、その境界はカーネルの自然な ingest diff に委ねられます（自動圧縮はどこでもオフになっています — ホスト平面はバンドルパッチ経由、web プロファイルのプリセットは #3354 のロード時オーバーレイ経由；上記の web プロファイル注記を参照）。

**ホスト側のコンテキストメーターは設計上、モデルの視点と乖離します (#2837)：** プラグインモードでは、ホストの永続セッションログは意図的にロスレスのままです — 完全な展開済み履歴はプレフィックスキャッシュと厳密エコーのために再送されます（technical-notes.md、「Two compression modes」）。そのためホストやそのプラグインがそのローカルログから計算するめったなメーターは、次の要求が実際に運ぶものではなく**展開済みのローカル表面**を測ります — 圧縮が有効な間にローカル値が実入力よりはるかに高いのは**期待どおり**であり、詰まった圧縮器ではありません。実効サイズはプロキシのものです：ローカルで再導出するのではなく `/acp`（または `GET /__bili/plugin/status` → `contextTokens`、出所は `contextTokensSource`）を読んでください。

**dsh クライアントはこのために Context タブを同梱します (#3862)：** ネイティブプラグインは dsh の会話ビューにセッションスコープの `Context` タブを登録します（Chat/Trajectory の右）。dsh web アプリからクロスオリジンで `GET /__bili/plugin/status` を読み、`/acp` パネルがライブで計算するのと同じ内訳を描画します：ウィンドウ上限に対する圧縮後送信総量、カテゴリ別セグメント（system+tools / tools / text / code / summaries）、独自のラベル付きスケールでの請求グレードの billing アンカー、そして回収トークンを伴う最近の fold/switch イベント。10 秒ごとに更新されます；稼働中のプロキシがこのビルドより古い場合、タブは推測する代わりに再起動通知 + Web UI 開くボタンの表示に退化します。dsh 自身のランタイムからのプレーン React — iframe なし、追加依存なし。

## Kimi Code（Moonshot）

整列した 3 つのモード：`bili kimi`（ランチャー、cert-MITM — README クイックスタート Option 2）、`/bili/` URL プレフィックス、ネイティブプラグインモード（`bili plugin install kimi`、#963）。Kimi Code v2 のプラグインシステムは宣言型のみです（`kimi.plugin.json`：MCP サーバー、フック、スキル — プロセス内 JS 実行なし）ので、bili は pi/opencode/dsh でやっているようにクライアントの fetch スタックをパッチできません。代わりにプラグインはクライアントの周りで仕事をこなす小さな node スクリプトを 2 つ同梱します：

- **インストール：** `bili plugin install kimi` は `$KIMI_CODE_HOME/plugins/managed/billion-context/kimi.plugin.json` を書き、stdio MCP サーバー（`node <root>/dist/kimi/native-mcp.js`）と `SessionStart` フック（`node <root>/dist/kimi/bootstrap-hook.js`、タイムアウト 30 秒）を宣言し、プラグインを `$KIMI_CODE_HOME/plugins/installed.json` に登録します。インストーラは `kimi --version` ≥ 2.0.0 を要求し、それ未満では拒否します（ランチャーはどちらでも動作します）。削除は `bili plugin remove kimi`（管理ディレクトリ + レジストリ記録 + 設定の復元）。
- **セッションごとのブートストラップ：** kimi は各セッションについて MCP サーバーを直接の子プロセスとして spawn します；起動時に健康なプロキシ（`BILLION_CONTEXT_PROXY`）に取り付いたり、エフェメラルポートで独自のものを spawn したりしてから、`~/.kimi-code/config.toml` 内の冪等な行サージカルな管理ブロックでクライアントのルーティングを書き換えます：自身のプロバイダー `[providers.bili]`（`base_url = http://127.0.0.1:<port>/bili/<upstream>`、アクティブなプロバイダーの `oauth` / `api_key` 参照をそのまま複製）、`[models.bili-kimi]` エイリアス、そして前の値をブロック内に記録したトップレベルの `default_model` リダイレクト。元のファイルは一度だけ `config.toml.bili-bak` にスナップショットされます；すべての書き込みは mkdir ロックファイル下で行われ、ブロック外のユーザー内容は決して触られません。Kimi の設定ホットリロードが変更をライブセッションに適用します。`SessionStart` フックは同じブートストラップを機会的に実行します（attach のみ — spawn は絶対にしない）；その非ブロッキングな競合は設計上許容されます：ラウンド 1 が direct/wire モードに乗ってもよく、不変条件は `base_url` を死んだポートに向けないことです。
- **プラグインモード押印：** ブロックに `custom_headers = { x-bili-plugin = "kimi" }` が加わるのは、ACP ツールリストが生きたプロキシのマニフェストと照合されて検証された**あと**だけです — それまではトラフィックは wire モードに乗ります。`custom_headers` はプロバイダーごとに静的なので、モデル切り替えで古くなることなく要求ごとのウィンドウ/モデルヘッダを運ぶことはできず；そのためランタイム情報の報告はブートストラップ時のみ行われます（存在する限りクライアント自身設定から model + context window + max output）。
- **ウォッチドッグとライフサイクル：** MCP 子プロセスは 30 秒ごとにプロキシをプローブします。attach モードでは永遠に待ちます（ユーザー所有のプロキシには決して触れない）；spawn モードでは死んだプロキシは再起動され、ルーティングは新しいオリジンに書き換えられます。復旧に失敗すると、管理ブロックは削除され、トラフィックは死んだポートに当たるのではなく直接アップストリームへ退化します。セッションが終わると、kimi は MCP 子プロセスを kill し、親 pid ウォッチドッグが spawn したプロキシを解体します。並行する複数の TUI は最初に spawn されたプロキシを共有します；それが消えると残りのセッションは自動的に再起動して再ルーティングします。
- **既知の制約：** サブエージェントの会話は自分自身の派生プロキシセッションを得ます（kimi は安定したセッション id を公開しない；ツール呼び出しは呼び出しごとの `conversation_id` 引数でバインドされる）、そして kimi のネイティブ自動圧縮は押し出されません — ACP 圧縮はランチャーモードと同様に単に先に発火します。オプトアウト：`BILI_NATIVE_KIMI=0`。
- **モデル/プロバイダー切り替えでプロキシを外れる (#2954)：** ルーティングがカバーするのはブートストラップ時にエイリアス化されたデフォルトモデル（`bili-kimi`）**のみ**です。他のモデルやサードパーティプロバイダーへの `/model` 切り替えは、後のセッションが再びエイリアスでブートストラップするまで bili を完全にバイパスします — 圧縮も統計もなし。単一エイリアス設計の意図的な爆発半径トレードオフ (#963)：プロキシが死んでも影響を受けるのはエイリアス化されたモデルだけで、他のすべてのモデルはそのまま直接動作し続ける；完全なマルチプロバイダー引き継ぎならすべてのユーザー所有 `[providers.*]` base_url をその場で書き換え、「マーカー外ユーザー内容に触れない」管理ブロックの不変条件を破る。エイリアス自体はソースモデルの `capabilities` / `support_efforts` / `default_effort` をそのまま継承します (#2954)、そして config.toml のすべての `[models.*]` ウィンドウは spawn 時にプロキシに届く（`BILI_LAUNCHER_MODEL_WINDOWS`）ため、通過するものの要求ごとのウィンドウ解決は正確さを保ちます。

## Hermes（Nous Research）

整列した 3 つのモード：`bili hermes`（ランチャー、cert-MITM — README クイックスタート Option 2）、`/bili/` URL プレフィックス、ネイティブプラグインモード（`bili plugin install hermes`、#958）。hermes CLI エージェントのプラグイン API は Python のみです（`desktop/plugin.js` SDK は別物の Desktop アプリのもの）ので、ネイティブプラグインは npm パッケージの中に同梱される小さな純標準ライブラリの Python モジュールです：

- **インストール：** `bili plugin install hermes` は `plugin.yaml` + `__init__.py` を `~/.hermes/plugins/billion-context/` にコピーし、グローバルの bili インストール（`dist/index.js` + node パス）を指すマシン所有の `bili.json` サイドカーを書いて、hermes 自身のチャネルを通じてプラグインを有効にします（`hermes plugins enable billion-context` — CLI が PATH にない場合は同じコマンドが表示される代わりに）。新しい hermes セッションを開始すると有効になります。削除は `bili plugin remove hermes`；グローバル更新後は `bili plugin update hermes` でリフレッシュします。インストールまたはリフレッシュされたプラグインは**新しい** hermes セッションでのみ有効になります — 注入コードはホストプロセスに住むため、稼働中のセッションは再起動まで古いコピーを保ったままです（まだ稼働している古いプロキシは通常の stale バナーとして表示されます、README の Self-update を参照）。
- **ライフサイクル：** ロード時にプラグインは健康な稼働中プロキシに取り付きます — #2905 以降レーン認識：まず自分の hermes レーンインスタンス、他の宣言レーンのインスタンスは**決して**ない（オプトインするには `native.attachLanePriority` に列挙）、8787 ユーザーゾーンデーモンを最後のフォールバックとして — またはエフェメラルポートで独自のものを spawn します（`lane: hermes` を宣言するため他のレーンはそれに乗れない；hermes が終了すると親 pid ウォッチドッグが解体；並行起動はランチャーが使っているのと同じ starting-marker プロトコルで仲裁）。プロキシが健康だと確認できて初めて、`HTTPS_PROXY` / `https_proxy` + `SSL_CERT_FILE`（bili の結合 CA バンドル — 現在の hermes はそこで環境の信頼を解決する；古いビルド向けに `HERMES_CA_BUNDLE` も設定されたまま）を通じて hermes の httpx スタックをそこに向けます — `~/.hermes/config.yaml` は決して触れません。プロバイダーの https ホストは hermes の設定から読み MITM にホワイトリスト化されます；それ以外はすべてランチャーモードと同様にブラインドトンネル化されます。健康なプロキシを作れなければ、プラグインは黙って退き、トラフィックは直接いきます（圧縮も死んだポートもない）。
- **プラグインモード押印：** `llm_request` ミドルウェアは `x-bili-plugin: hermes` + 会話 id（= hermes セッション id なのでゲートウェイのマルチセッションが安全）+ model を押印し、判明したら `x-bili-plugin-max-output` を押印し、ホスト自身のモデルごとのウィンドウが判明していれば `x-bili-plugin-context-window` も押印します（`HERMES_HOME/context_length_cache.yaml` から読み、キーは `<model>@<base_url>`；曖昧なエントリは推測しない、#3261）— ただしすべては ACP ツールが生きたプロキシのマニフェストに対して登録された**あと**のみ；ラウンド 1 は wire モードに乗ります。`pre_api_request` フックは実効的な `max_tokens` を捕獲し、ランタイム情報（model + max output + context window）をプロキシにプッシュします。`compress` / `decompress` / `acp_status` は既存のプロキシのプラグインエンドポイントによって提供される真の hermes ツールとして登録されます。
- **セッション内コマンド (#3697)：** プラグインは `/acp` と `/acp-cache` を hermes の `PluginContext.register_command` 経由で登録するため、組み込みのものと同様にスラッシュコマンドのヘルプ/補完に表示されます。`/acp` はこのセッションの ACP ステータスパネルをプロキシからそのまま描画します（ヘッダにバージョン + ビルド）；ホストが現在のセッション名を指定できない場合、最近アクティブだったものにフォールバックし、それを最初の行で明示します。`/acp-cache` は `acp_cache` ツールと同じキャッシュレポートを表示します。これは hermes 自身の `hermes acp` CLI サブコマンド（ACP クライアントのエントリポイント）とは**別物**です — 別物で無関係な機能。コマンド登録にはホストに `register_command` が必要（2026.9.x ビルドに存在）；古いビルドでは 2 つのコマンドだけがスキップされつつツールは動き続けます。
- **既知の制約：** hermes の Codex ワイヤートランスポートから出る要求は要求ごとのヘッダ表面を落とす可能性があるため、そうしたセットアップはそのトランスポートがヘッダを公開するまで wire モードのままです。`BILLION_CONTEXT_PROXY` が設定されているとき（ランチャーがプロキシ所有）または `BILI_PROVIDER_REWRITES` が定義されているときは無効。オプトアウト：`BILI_NATIVE_HERMES=0`。

## ZCode（Z.ai / bigmodel コーディングプラン）

整列した 3 つのモード：`/bili/` URL プレフィックス、GUI の Settings → Network（HTTP プロキシ + ルート CA パス）を通じた cert-MITM、ネイティブプラグインモード（`bili plugin install zcode`、#1145）。ZCode のエクステンション表面は Claude-Code 形状ですが宣言型です：`~/.zcode/cli/config.json` のユーザーレベルフックと stdio MCP サーバー、プロセス内 JS シームなし。そのためネイティブレーンはクライアントの周りで仕事をこなす小さな node スクリプトを 2 つ同梱します：

- **インストール：** `bili plugin install zcode` は `~/.zcode/cli/config.json` を書き、`hooks.enabled = true` を設定し、`SessionStart` プロセスフック（`node <root>/dist/zcode/bootstrap-hook.js`）を追加し、stdio MCP サーバー `mcp.servers.bili`（`node <root>/dist/zcode/mcp-entry.js`）を登録します。既存のユーザー所有 `mcp.servers.bili` エントリは決して上書きされません — インストーラは代わりに明白に拒否します。インストール時に URL は凍結されません；ルーティングはセッションごとに行われます。削除は `bili plugin remove zcode`（bili のエントリのみを取り除き、自分が有効にしたものなら `hooks.enabled` を戻し、スナップショットからプロバイダーストアを復元）。
- **削除後のオープンセッション (#2155)：** `bili plugin remove zcode` はすでに開かれたクライアントウィンドウの中までは到達できません — その MCP 子プロセスは消えたが、プロキシ側のバインド（セッションメタデータ）は生き残っています。そのようなゾンビセッションは、プラグインヘッダなし・ワイヤ上に bili ツールなし・圧縮なしの nudge 付きラウンドが 5 回連続したあとに検出されます：セッションは**proxy モードへの退化**によって自己修復します — ACP ツールは wire 側に再注入され、プロキシが再び圧縮を所有する（nudge は残る）。wire 注入が利用不可（`compress.injectTool=false`）の場合、nudge は圧縮削減が再開するまで代わりに抑制されます。戻ってきたプラグインヘッダ（クライアント再起動 / 再インストール）は最初の要求でプラグインモードを回復します。削除コマンドは直近 10 分間にライブセッションが見られたら注記を表示します；web UI はそうしたセッションにバッジ（「heal」）を付けます。
- **セッションごとのブートストラップ：** 各 ZCode セッションは MCP 子プロセスを直接のプロセスとして spawn します；起動時に健康なプロキシ（`BILLION_CONTEXT_PROXY`）に取り付いたり、エフェメラルポートで独自のものを spawn したりしてから、mkdir ロックファイル下で冪等な JSON サージェリーによりアクティブなプロバイダーストアを書き換えます：ルーティング可能な各プロバイダーストアエントリの `baseURL` が `http://127.0.0.1:<port>/bili/<upstream>` になる（自分で設定した任意の baseURL はラッパーの後ろにそのまま保持）。両方のストア世代に対応します：レガシー `~/.zcode/v2/config.json`（`provider.<id>.options.baseURL`）と v3.14+ のパーソナルストア `~/.zcode/v2/provider_config.json`（`config.providerConfigRules.providerRules[].config.api.baseUrl`）— 両方が存在するなら新しいストアが優先（どのエントリがルーティングされ、どれがスキップされるかは Routing scope を参照）。元のファイルはユーザー編集ごとに一度だけ `<file>.bili-bak` にスナップショットされます（スナップショットは常にあなたの最後の実際の状態を反映し、決して bili 自身の書き込みを反映しない）；他のすべてのキーはバイト単位で同一。レガシー世代のクライアントは起動時にプロバイダ設定を読み込むため、インストール後に ZCode を一度再起動してください；新しいビルドはセッション中にルーティング変更を取得します（約 1 秒ポーリング）。`SessionStart` フックは同じブートストラップを機会的に実行します（attach のみ — spawn は絶対にしない）；その非ブロッキングな競合は設計上許容されます：ラウンド 1 が wire モードに乗ってもよく、不変条件は `baseURL` を死んだポートに向けないことです。
- **プラグインモード押印：** MCP 子プロセスが ACP ツールリストを生きたプロキシのマニフェストと照合して検証したら、ルーティングされたエントリに `headers["x-bili-plugin"] = "zcode"` が加わります — それまではトラフィックは wire モードに乗ります。ツール呼び出しは呼び出しごとの `conversation_id` 引数でバインドされます (#760)。
- **何がきれいになり、何が決して触られない（統合 ACP 不変条件）：** モデル散文では bili のレンダリングタグエコー / マーカー行 / 退化残渣が通過時に除去され得ます；**thinking チャネル**（anthropic `thinking`、google `thought`、openai `reasoning_content`/`reasoning`、responses reasoning summaries）、**ツール呼び出し引数**（モデルが書いたファイル内容）、**ユーザーメッセージ**はバイト単位で触れられません。
- **ルーティング範囲 (#1622)：** ネイティブモードは利用可能な http(s) `baseURL` を持つ**すべての**プロバイダーストアエントリをラップします — プロセス内ネイティブ（pi/dsh）と同じ「全プロバイダーが圧縮に乗る」セマンティクス — bigmodel コーディングプランアカウントだけに限りません。ラップできないエントリは黙って落とされるのではなく、ログ付き理由でスキップされます：
   - **クライアント署名アカウント (#1621)：** v3.14+ のパーソナルストアではコーディングプランアカウントはそのまま direct（既知の制約を参照）；他のすべてのプロバイダーは引き続きルーティングされる。
   - **ループバック対象 (#809)：** http ループバック `baseURL`（localhost / 127.x.x.x / ::1）は決して再プロキシされない — ラップすると bili が自分自身や自分のローカル中継の上に積み重なる。
   - **`direct` 免除：** `providers` テーブル（アップストリーム URL をキー — configuration.md を参照）で `"direct": true` を宣言するプロバイダールートは direct に留まる；どのレーンでも尊重できる同じ免除。
   レーンはセルフマネージドポートゾーンでプロキシを起動します (#1660)：ゾーンベース `18787`、過去に +1 ラダーでドリフトしても自動的に追従するレーンごとのスティッキー記録、衝突は子プロセスの +1 ラダーで解決、ドリフト時は共有ストアが生きたオリジンに書き換えられる — ハンドオフがなくてもラッパーはセッション再起動を生き残る。`BILI_ZCODE_PORT` は代わりに正確なポートを pin する（strict-port：居座りは明白に拒否、hop なし）。`BILI_ZCODE_ROUTE`（`plans`/`none`）は互換エスケープハッチ、`BILI_ZCODE_SIGNING_FIXED=1` は ZCode ビルドが署名修正を出した時点で #1621 のスキップをオフにする。
- **ウォッチドッグとライフサイクル：** MCP 子プロセスは 30 秒ごとにプロキシをプローブします。attach モードでは永遠に待ちます（ユーザー所有のプロキシには決して触れない）；spawn モードでは死んだプロキシは再起動され、ルーティングは新しいオリジンに書き換えられます。復旧に失敗すると、管理書き換えは削除され、トラフィックは死んだポートに当たるのではなく直接アップストリームへ退化します。セッションが終わると、ZCode は MCP 子プロセスを kill し、親 pid ウォッチドッグが spawn したプロキシを解体します；MCP 子プロセスが終了する前（SIGTERM/SIGINT/正常終了）にロックの下で引き継ぎを行います — 共有プロバイダーストアがまだ自分のプロキシを指している場合、別のライブな互換インスタンスに向け直すか、存在しなければ direct に戻して管理書き換えを削除する (#1623) そのため、死んだインスタンスが共有設定に死んだポートを残しません。ウォッチドッグは毎ティック共有ストアもチェックします：別のインスタンスによる死んだポートが残っている場合（ハンドオフが実行されないハードキルのケース — 例：Windows の TerminateProcess は JS ハンドラーをスキップ）は修復を引き受けます（ライブインスタンス優先、なければ direct に復帰）；ストアが死んだポートを指している間のみ行動し、ライブインスタンスからルーティングを奪わない。並行セッションは最初に spawn されたプロキシを共有します；それが消えると残りのセッションは自動的に再起動して再ルーティングします。境界：ZCode はセッションごとにプロバイダの baseURL をキャッシュするため、上記の修復は**新規読み取り**（新しいセッション/クエリ）でのみ効力を発揮します — 進行中のセッションは再読み取りまでキャッシュされた古いポートのリトライを続けます。これを構造的に避けるには、`BILLION_CONTEXT_PROXY` を常駐プロキシ（`bili start`）に pin し、すべてのセッションがそこに attach させます（attach モードはユーザー所有プロキシには触れない）。
- **既知の制約：** ZCode の不正防止フィンガープリンティング (#661) は `zcode.z.ai` ログイントラフィックの MITM 再構築ボディに適用されます — ネイティブモードはその表面には触れません（モデルトラフィックは GUI プロキシではなくプロバイダーストアを通る）；GUI-proxy/MITM セットアップも走らせるなら、`"mitm://zcode.z.ai": { "passthrough": true }` ルートを保ってください。v3.14+ ビルドでは、コーディングプランアカウントの ClientRequestSigningV4 はモデル作成時に非 HTTPS オリジンを拒否し、ハンドシェークパスをオリジンのみから導出する（`/bili/` プレフィックスを落とす）ため、`/bili/` ラップの baseURL は「Client signing handshake requires HTTPS.」で失敗します (#1621)。競合は ZCode 側でハードコードされているため、ネイティブモードは v3.14+ のストア世代を検出し、書き換えをまったくスキップします — 理由をログに出してトラフィックを direct にしておく；これらのアカウントで圧縮するには ZCode が署名修正を出すまで GUI cert-MITM セットアップを使う；出たら `BILI_ZCODE_SIGNING_FIXED=1` を設定すればまたルーティングされる。デフォルトの `route:"all"` ではそうしたアカウントのみがスキップされ — ストアの他のすべてのプロバイダーは引き続きルーティングされる；ストア全体の退化（ルーティングを完全にオフ）は現在 `route:"plans"` の下でのみ適用され、そこでは plan アカウントこそが署名アカウントです。Pre-3.14 レガシーストアのクライアントには影響なし。`BILLION_CONTEXT_PROXY` が設定されているとき（attach モードがプロキシ所有）または `BILI_PROVIDER_REWRITES` が定義されているときは無効。オプトアウト：`BILI_NATIVE_ZCODE=0`。

## Codex（OpenAI Codex CLI）

**一時的なカタログ障害 (#3993)。** Bili を経由してルーティングされる認証付き `GET https://chatgpt.com/backend-api/codex/models` 要求に対して、最後に有効だった完全なカタログがトランスポート失敗と HTTP 500/502/503/504 をカバーできます。これにより、一時的なディスカバリー失敗が Codex の既知のコンテキスト/ツール機能を捨て去ることを防ぎます。プライベートキャッシュは既存の XDG キャッシュディレクトリ配下（`codex-model-catalog-v1`）にあります；完全な URL/クライアントバージョンと credential/account/org/project のフィンガープリントで分離され、生 credential を含まず、カタログごとに 1 MiB・16 エントリ・6 時間に制限されます。オンラインディスカバリーは常に優先されます；オフラインヒットは経過時間を延長しません。利用可能なキャッシュがある場合、ネットワーク/ボディの期限は 4 秒です。呼び出し側のキャンセル、401/403、他の明示的なエラー、無効/空のカタログはキャッシュされた成功になりません。コールド、期限切れ、credential が変わった要求は依然として成功したディスカバリーが必要です。オフライン再生はアップストリームサーキットをクリアせず、推論の到達可能性を証明しません。推論ペイロード、圧縮モード、設定されたコンテキスト上限はいずれも変更されません。

**ウィンドウ整合。** クライアントが報告するプラグイン/ランタイムウィンドウとランチャーウィンドウは、バンドルされた Codex モデルテーブルより優先されます。報告がない場合、ローカルプロキシは `CODEX_HOME`（デフォルト `~/.codex`）配下の `models_cache.json` とベースの `config.toml` を読み、`model_context_window` は該当モデルの `max_context_window` で上限が決まり、その後 `effective_context_window_percent`（Codex のデフォルトは 95）で減算されます。キャッシュの変更は後の要求で取得されます。欠落、読み取り不能、無効なメタデータはバンドルテーブルとその既存の 272K 不明モデル上限にフォールバックします。リモートプロキシや別クライアントプロファイルの場合は、クライアントのウィンドウを既存のランチャー/ランタイム報告メカニズムで渡すか、既存の `compress.modelContextLimit` を設定してください；プロキシのローカルキャッシュは別マシンの設定の証拠にはなりません。出力ヘッドルームは依然適用されます。

Codex は、プラグインインストールだけでは自己完結できない唯一のクライアントです。シーム行列がその理由を説明します：claude には `SessionStart` フック + 管理設定ブロックがあり、zcode には書き換え可能な `baseURL` を持つプロバイダーストアがある — codex はどちらもありません。そのモデルトラフィックは環境変数のみでルーティングされます（`HTTPS_PROXY` / `SSL_CERT_FILE` — これが `bili codex` の仕組み）；デフォルトの ChatGPT ログインプロバイダーには設定ファイルのルーティングシームがなく、管理 `model_providers` ブロックは `env_key` API キー認証を強制し **サブスクリプションログインを落としてしまう**。MCP サーバーは親プロセスに環境を注入できないため、プラグインは codex 自身のトラフィックをルーティングできません。3 つの態勢：

| 態勢 | 得られるもの |
|---|---|
| `bili codex`（ランチャー） | フル・ゼロ設定：セルフマネージドのレーンプロキシ（#1660 ゾーン、スティッキーポート）+ codex に注入される cert-MITM 環境変数 — ツール*と*圧縮の両方 |
| `bili plugin install codex` + 稼働中の bili + 自分でエクスポートした `HTTPS_PROXY` | 自分自身で環境を管理するパワーユーザー向けにツール+圧縮 |
| `bili plugin install codex` のみ | 4 つのツールは codex に現れるが、プロキシされる会話がないので作用対象がない；何も到達できない場合 `tools/list` は -32003 で失敗する（`bili proxy unreachable … — start bili or set BILI_MCP_PROXY`） |

**並行セッション (#3203)。** 複数の `bili codex` 起動が同じプロジェクトディレクトリで同じ `CODEX_HOME` を使って同時に動いてもよい：各起動は自分自身のセッションごとのオーバーリースロット（`<CODEX_HOME>-bili-s<N>`、プール 16）と自分自身のレーンプロキシを取るため、ルーティング、MCP 会話バインド、圧縮状態はセッション間で決して交わりません。共有状態デフォルト（codex ≥ 0.147.0）では、両セッションの履歴は実 home の**1 つの**ライブ状態 DB に着地し、いかなる終了順序でも生き残ります — configuration.md の `BILI_CODEX_STATE_MODE` を参照。古いバイナリ、または `BILI_CODEX_STATE_MODE=legacy` は home ごとに排他的なオーバーレイを 1 つ保ちます：第 2 の並行起動は `BILI_OVERLAY_BUSY` で拒否されます。

インストールは単一の `[mcp_servers.bili]` ブロックを `~/.codex/config.toml` に書き込みます（command = node、args = dist/mcp.js）。#1660 はインストール時のオリジンの焼き込みを削除しました（#403：焼き込まれた URL はドリフト/再起動後に古くなり、ツールを死んだポートに向けたままにした）；シェルはセッション開始時にプロキシを解決します — 環境 `BILI_MCP_PROXY` > ライブインスタンス記録（どのレーンのプロキシでもよい、または `bili start` デーモン）> 8787 ユーザーゾーンデフォルト — ためドリフトした再起動したプロキシは死んだ URL を取り残すことがなく、シェルは単に生きているものに attach します。セッションバインドはヘッドレスです：ランチャーは spawn 時に `BILI_CONVERSATION_ID` を渡し、それ以外ではプラグインシェルが次の NEW セッションをバインドします；呼び出しごとの `conversation_id` 上書きはどこでも機能します (#760)。Codex ≥0.160 はさらに `_meta.threadId` を通じてすべての `tools/call` に実際のスレッド id を押印します；シェルは呼び出しごとにそれを消費します（厳密に検証され、spawn 時バインドへ書き戻されることはない）、そしてそれは古い `BILI_CONVERSATION_ID` 残骸とモデル転記の `conversation_id` の両方に優先します (#2024)。

**Responses ネイティブチェイニング（注意点）。** bili は完全な `input` を再生して圧縮するため、OpenAI のネイティブ `previous_response_id` チェイニングに従えません：delta のみの継続は、200 を返しながらも以前のターンをアップストリームで失います。今日は codex では非問題です — 観察されたビルドは `store:false` を送り、`previous_response_id` を決して設定しません（観察であり証明ではない；E2E はその形状をカバーしない）。ネイティブチェイニング Responses クライアントを bili に向ける場合は、完全な input/output 履歴を再送するか `ACP_KEEP_RESPONSE_ID=1` を設定してください；bili が空でない `previous_response_id` を除去すると、今は `warn` をログに出します (#1954)。完全なチェイニング対応は #1973 で追跡されています。[公式マイグレーションガイド](https://developers.openai.com/api/docs/guides/migrate-to-responses) を参照。

### 実行モード：`bili codex` は embedded を固定する (#1867)

約 0.156 以降、Codex はマシン全体の共有バックグラウンドサーバーに attach（または自動起動）でき、そのモデルトラフィックはセッション開始時ではなく**デーモン起動時に**存在した環境を使います。ランチャーのプロキシはセッションスコープ（そのポートはプロセスと共に死ぬ）なので、長寿命デーモンが安全にそれを経由してルーティングできません：codex が先に bili の環境なしで起動すると、後の `bili codex` セッションは黙ってそこに attach して圧縮を完全にバイパスする；bili が先に起動すると、生き残ったデーモンは死んだポートを指し続ける。そのためランチャーは明示的に `--no-daemon` を渡します — フラグのために `codex --help` をプローブしてから（古いバイナリは無変更で起動）、ユーザーがすでにモードを pin していないときのみ（`--no-daemon` または `--remote`）。結果：決定的な embedded 実行、起動ごとのフォールバック警告なし、黙ったバイパスなし。#321 の予算 `-c` 引数はそのまま保持されます（embedded モードは同様に尊重する）。共有バックグラウンドサーバーが欲しいならネイティブ `codex` を直接実行してください — 圧縮はないが、ツールは `bili plugin install codex` 経由で引き続き動作する。

### Windows 起動パス：ユーザー argv は二度と cmd.exe に戻らない (#2196)

Windows ではデフォルトの npm インストールが PATH に `codex.cmd` シムを置き、その `%*` 転送はすべてのユーザー引数を cmd.exe の LINE パーサを通じて再パースします — そこにはエスケープ機構がありません：埋め込まれた二重引用符がトークンを分割する（`Please say "hello world" exactly` は 4 つの引数として届く）、`%VAR%` は展開され、`&|<>^()` はコマンド演算子として働き、空引数は消える。空白区切りのプレーンプランプトは生存していたため、#679 のスペース截断修正がそれを露呈させませんでした。#2196 はランチャーがユーザー argv をそのパーサに与えることを拒否するようにします：

- **解決順序（win32 のみ）：** 各 PATH ディレクトリ内ではネイティブ `codex.exe` が `codex.cmd`/`codex.bat` に優先する（最も早いディレクトリが全体で依然優先）；`.cmd`/`.bat` ヒットは信頼できる npm レイアウトの隣にある場合に `node <official bin/codex.js>` に格上げされる — package.json が `@openai/codex` と名付けられ解決可能な `"codex"` bin エントリを持つ `<dir>/node_modules/@openai/codex`、かつそのパッケージを参照するシムテキスト（無関係なツリーの隣に置かれた手書き `codex.cmd` は起動をハイジャックしてはならない）。Node 上で公式ラッパーを実行するとシムが行うこと（ベンダーバイナリ探索、環境初期化、シグナル転送）を正確に再現しつつ、Node 自身の CreateProcess argv エンコーディングが各引数をそのまま運ぶ。認識できないレイアウト（yarn-classic の `.bin` ツリー、ローカルリンクなし pnpm ストアシムなど）は以下の契約の下でレガシー cmd パスを保つ。
- **パススルー契約：** 残りの cmd ラップ起動 — いかなるクライアントの `.cmd`/`.bat`/拡張子なしバイナリ、および dsh チャネル spawn — は行パーサがそのまま運べる argv のみを受理する。それ以外（埋め込み引用符、`%VAR%`、メタ文字、空引数、改行、奇妙な末尾バックスラッシュ連続）は、破損して届いたり意図しないコマンドを実行したりするのではなく、プロセス開始*前*に実行可能なエラーで明白に失敗する。直接 spawn の `.exe` 起動には影響ない：Node はそれらの argv を自らロスレスにエンコードする。
- **回避策 / パワーユーザー用ノブ：** `BILI_CLIENT_BIN=<path>` は依然すべてに優先する — 実際の `codex.exe`（または node 下で実行されるスクリプトエントリ）に向ければシムを完全にバイパスできる。

windows-latest CI で実際のグローバル `@openai/codex` インストールに対して検証済み（`tests/win-cmd-argv.test.ts`、`ci-windows-codex.yml` のハードゲート）：完全なコーパス — 空引数、プレーンなスペース、埋め込み引用符、TOML `-c` 値、JSON、Unicode、末尾バックスラッシュ、`%COMSPEC%`、`!VAR!`、`&|<>^()` — が呼び出し側配列と項目ごとに同一のまま子プロセスに届く。

### Composer 予測（Codex Desktop）：カスタムプロバイダーのスレッドは対象外 (#3408)

Codex Desktop の Composer 予測機能には、予測要求が billion-context に到達し得る**前**に走る**クライアント側の資格ゲート**があります：再開されたソーススレッドの*実際の*プロバイダーをチェックし、組み込み `openai` プロバイダーを要求します — 他のプロバイダーは `unsupported_provider` を選び、クライアントは予測を生成せずに帰る（Desktop 26.1013.3656.0 の静的検査、#3408）。ゲートは*グローバルデフォルト*ではなく*スレッドの*プロバイダーを読む：予測パスはソーススレッドを特別な予測モードでフォークし、その呼び出しは独立した予測プロバイダーを供給しないため、グローバルデフォルトを変更しても既存スレッドの資格は再付与されない。結果：

- **カスタムプロバイダーのスレッドは予測を表示しない** — クライアントの設計によるもので、bili の欠陥ではない。予測要求は決してプロキシに届かないので、bili 側に修正や設定すべきものはなく；予測に対するゲートウェイトラフィックの不在は期待どおりであり、要求が落ちた証拠ではない。
- **プロバイダーを保つトランスポートは機械的に資格を保持する。** cert-MITM ルーティング（`bili codex` ランチャーが注入する `HTTPS_PROXY` + `SSL_CERT_FILE`）はプロバイダー層の下でインターセプトする：codex 自身の設定とプロバイダー選択は触れられないため、スレッドは組み込み `openai` プロバイダー identity と公式 ChatGPT 認証を保つ — ゲートが読むのはまさにそれ。Desktop ビルドでのランタイム確認は未だ pending（マッチした A/B なし）；このトランスポート下で Desktop の予測を確認または否定できるなら #3408 に報告してください。
- **カスタムプロバイダーのスレッドで予測を回復するサポートされた設定はない。** カスタム `model_providers` エントリを通るあらゆるルート — API キー認証、サードパーティのワンクリックインストールを含む — は構造上ゲートの対象外側に位置する（そうしたエントリは上記のようにサブスクリプションログインも落とす）。カスタムプロバイダーを `openai` に偽装するリネーム、やクライアントの資格チェックのパッチはサポートされず、回避策として文書化されない。

経験則：予測が必要なら組み込み OpenAI プロバイダー経路にとどまる；カスタムプロバイダーが必要なら、そうしたスレッドに予測が表示されないことを受け入れる。

## Gemini ファミリー（Gemini CLI / iFlow CLI / Qwen Code / Antigravity）

gemini-cli アーキテクチャファミリーのための 4 つのランチャー (#1043 tier 1)。4 つのうち 3 つに base-URL 環境フックがある；1 つにはない：

- **`bili gemini`** — Gemini CLI (`@google/gemini-cli`)。`GOOGLE_GEMINI_BASE_URL=<proxy>/bili/<upstream>` を設定する（デフォルトアップストリーム `https://generativelanguage.googleapis.com`；自分で `GOOGLE_GEMINI_BASE_URL` をエクスポートするなら、その値が代わりにプロキシ経由で中継される）。クライアントは `gateway` 認証モードに切り替わり、Google ネイティブワイヤ要求をループバックプロキシに直接送る — MITM なし、CA インストールなし、`~/.gemini` は決して触れない。プロキシはこのワイヤをネイティブで話す（モデル名は URL パスに乗る）。制約：ヘッドレス `-p` 実行は保存済みの認証選択が必要（例：settings の `security.auth.selectedType = "gemini-api-key"` + `GEMINI_API_KEY`）— gemini-cli は非対話モードで純粋に環境由来の gateway 認証を拒否するため；OAuth 個人ログイン（CodeAssist）ユーザーはこのルートでまったくカバーされない — そのパスは base-URL フックを無視する。
- **`bili iflow`** — iFlow CLI (`@iflow-ai/iflow-cli`)。`IFLOW_BASE_URL` 経由で同じパターン（デフォルト `https://apis.iflow.cn/v1`、設定したら中継）；OpenAI chat-completions ワイヤ。
- **`bili qwen`** — Qwen Code (`QwenLM/qwen-code`)。このフォークは base-URL フックを落とした（`DASHSCOPE_PROXY_BASE_URL` はヘッダ調整ノブであってルーティングではない）が、標準プロキシ環境変数は尊重するので、ランチャーは cert-MITM を使う：`HTTPS_PROXY=<proxy>` + `NODE_EXTRA_CA_CERTS=<bili CA>`、デフォルトモデルホスト（DashScope / Qwen ゲートウェイ / よくあるサードパーティエンドポイント）の静的ホワイトリスト付き。カスタム中継ホスト：`--mitm-domain <host>` で追加。ベストエフォートルート — ログの `BLIND TUNNEL WARNING` はホストがホワイトリストから漏れていることを意味する。
- **`bili antigravity`** — Google Antigravity (#2115)。ランチャーは公式 CLI バイナリ **`agy`** を駆動する（Gemini CLI の後継で、2026-06 に廃止；`PATH` または `~/.local/bin/agy`、Windows `%LOCALAPPDATA%\agy\bin` にある）。そのモデルチャネルはクローズドソースの Go `language_server` の中にあり、**文書化されていない** `CLOUD_CODE_URL` 環境上書きを尊重する（v2.19.1 バイナリで確認：*"Overriding CloudCodeServerURL via CLOUD_CODE_URL environment variable"*）— gemini-cli の base-URL フックと同じ形状。ランチャーは `CLOUD_CODE_URL=<proxy>/bili/<upstream>` を設定する（デフォルトアップストリーム `https://daily-cloudcode-pa.googleapis.com` — Antigravity の実際のデフォルト；裸の `cloudcode-pa` ホストは `/v1internal:*` で 400 になる、#3129；自分で `CLOUD_CODE_URL` をエクスポートするなら、その値が代わりにプロキシ経由で中継される）。MITM なし、CA インストールなし。プロキシは**パスで**ワイヤを認識する：`:streamGenerateContent` / `:generateContent` / `:countTokens` 要求は Google ネイティブアダプタにルーティングされ `bili gemini` と同様に圧縮される。サーバーが代わりに gRPC メソッドパス（`/google.internal.cloud.code.v1internal.CloudCode/*`）を使う場合、そうした要求は認識されずそのまま圧縮なしで中継される — グレースフルな退化で、確認次第レーンごとの `protocol` 宣言 (#1909) で修正可能。Google がいつか環境フックを削除した場合のフォールバック：cert-MITM — language_server は `HTTPS_PROXY` を尊重し証明書ピン留めをしないので、`daily-cloudcode-pa.googleapis.com`（Antigravity の実際のデフォルトエンドポイント；裸の `cloudcode-pa` 名は `/v1internal:*` で 400 になる、#3129）を `"mitm".domains` に追加し、bili のルート CA を信頼する。デスクトップアプリと IDE エクステンションはこの同じ language_server チャネルを共有する；ランチャーは具体的には CLI を駆動する — デスクトップユーザーは `CLOUD_CODE_URL` を手動でエクスポートするか、MITM レシピを使える。

4 つのいずれにもネイティブモードはない：どれもループ内ツール注入シームを公開しない（gemini-cli のエクステンションはカスタムコマンドにしか到達できない；フォークはその表面を継承；Antigravity はユーザープラグインシステムを同梱する — `plugins/<name>/` に `plugin.json`、`hooks.json`、`mcp_config.json`、`skills/`、JS サイドカー — がすべての表面は追加型のみ：ツール、プロンプト、UI、イベントコールバック。その中の何ものもモデル要求/応答ストリームをインターセプトしたり書き換えたりできず、それはクローズドな language_server の内部に完全に留まるため、ワイヤのみ統合が v1 の天井）。設計上ランチャーのみ。

## Pi（pi.dev コーディングエージェント）

Pi は完全なネイティブモード（`bili plugin install pi`、README クイックスタートのオプション 1）を持つ；このセクションは一行テーブルでは伝えきれないことを扱う — **ネイティブインターセプトが実際にカバーするモデルトランスポート**。DSH も Codex Responses WebSocket をインターセプトする (#5838)；そのホスト固有のライフサイクルは上記に説明がある。

**サブエージェント設定 (#2230)。** 組み込み `acp_delegate` 表面（3 つのデリゲートツール、ロール、フリートインスペクタ — `bili pi` が埋め込みエクステンションを通じて配線する）は bili 自身の設定ファイル、`~/.config/billion-context/billion-context.json` の `pi.subagents` セクションで設定される（ブール短縮形 `"pi": {"subagents": false}` で無効化）。4 つの `~/.pi/acp.json` キー（`delegate` / `delegatePrompt` / `displayUsage` / `debug`）は非推奨フォールバック — セクションが存在しない間のみ読み、存在すれば無視。完全なフィールドテーブルと `PI_ACP_DELEGATE_*` 環境上書き：configuration.md → [`pi`](configuration.md#pi)。

**ルーティングの仕組み。** pi エクステンションは自分自身のプロキシをブートストラップ（または attach し）、プロセス内で `globalThis.fetch` をパッチする：すべてのモデル API HTTP 要求は `<proxy>/bili/<upstream-url>` に書き換えられ、エクステンションは pi の `before_provider_headers` イベントを通じて `x-bili-plugin*` ヘッダを押印する。すべての HTTP ベースプロバイダー（Anthropic、OpenAI chat/completions/responses、Gemini、Mistral、OpenRouter、Azure、カスタム中継…）は名前付きプラグインモードセッションとしてこのパスに乗る。

**pi-claude-bridge と一緒に：圧縮状態は reopen/resume を生き残らない (#3429)。** pi-claude-bridge は **pi セッション開始ごとに新しい Claude Code サブプロセスを spawn し**、そのサブプロセスはすべてのモデル要求に自分自身の `x-claude-code-session-id` を押印する — pi の安定した会話 id はこの HTTP に決して乗らない。bili は見た id（ここでは `x-claude-code-session-id`）をそのままキーにするので、reopen/resume/fork の後、ブリッジの新しい CC id は空の会話にマッピングされる：折りたたまれた履歴と圧縮の集計は引き継がれず、pi id 宛のランチャー/ネイティブ `compress` は 404（未知のプラグイン会話）を返す — 一つの根本機構であり、二つの bug ではない。これはブリッジ側の identity ギャップであり、bili の欠陥ではない：内容は決して失われ壊れることはなく、圧縮の*状態*だけがリセットされる。適切な修正は pi-claude-bridge に属する（pi 会話 id から CC セッション id を安定して導出する）；それまで、コンテキスト管理のために pi+claude-bridge をプレーンプロキシモードとして扱え。

**WebSocket カバレッジ (#2073、#2111 で実装)。** WebSocket 接続は決して `globalThis.fetch` を通らないため、ネイティブエクステンションはロード時に `globalThis.WebSocket` もラップする — pi の最初のモデル接続より前に（pi の Node ブランチは呼び出しごとにグローバルを読む；Bun ブランチは初回呼び出しでサブクラスをキャッシュする、これが両ランタイムでインストール時の順序が安全な理由）。サポートされた Codex Responses モデル接続のみが書き換えられる — 他のすべての WebSocket（devtools、サードパーティライブラリ、すでにルーティングされた URL）は無変更で通過する：

| プロバイダー / トランスポート | 状態 |
|---|---|
| すべての HTTP プロバイダー | ✅ カバー — 名前付きプラグインモードセッション |
| `openai-codex-responses`（ChatGPT backend-api）、`transport: "sse"` | ✅ カバー — いかなる HTTP プロバイダーとも同一 |
| `openai-codex-responses`、`transport: "auto"`（デフォルト）または `"websocket"` / `"websocket-cached"` | ✅ カバー (#2111) — コンストラクタ URL が `<proxy-ws>/bili/<https-upstream>` に書き換えられる（例：`wss://chatgpt.com/backend-api/codex/responses` → `ws://127.0.0.1:<port>/bili/https://chatgpt.com/backend-api/codex/responses`）。コンストラクタ引数、サブプロトコル、要求ヘッダは保持されるため、pi が SSE で送る同じ `session-id` がアップグレードに乗ってトランスポート間でセッション identity はバイト同一；サブエージェントは自分自身の id を保つ。`previous_response_id` 増分継続はレーン上で機能する（プロキシはパイプライン前に delta を展開し、それを上流へ再最適化して戻す） |
| AWS Bedrock（`bedrock-converse-stream`） | ❌ Bedrock トラフィックはすべて WebSocket で、トランスポートオプションもなくアップグレードにカスタムヘッダもない — URL インターセプトだけではカバー不能；専用のプロキシ側 WS コーデックが必要（#2111 のスコープ外、#2073 の下で別途追跡） |

インターセプトの一つのトポロジー結果：pi のクライアント側ハンドシェイクは今やローカルプロキシをターゲットとする（常に成功するため）、*アップストリーム* WS 拒否は pi の同じターン SSE フォールバックをトリガーするのではなく、ストリーム中のトランスポート失敗として表面化する — そのフォールバックはクライアント側ハンドシェイク失敗でのみ発火する。下の明示的 `sse` レーンが依然として決定的なエスケープハッチである。

**codex プロバイダーのための回避策。** pi の設定で SSE レーンを強制する（`~/.pi/agent/settings.json`；プロジェクト `.pi/settings.json` が上書き）：

```json
{ "transport": "sse" }
```

デフォルトの `"auto"` は WebSocket を先に試し、ハンドシェイク失敗時のみ SSE にフォールバックする；レガシーのブールキー `"websockets": false` は自動的に移行する。キーはグローバルだが、マルチトランスポートプロバイダー（今日は codex プロバイダー）のみが消費し — HTTP のみプロバイダーは無視する。Windows + Pi 1.0.2 (#2063 owner 再現) で検証済み：明示的 `sse` は正しいセッション id で bili に入る。

レーンはエンドツーエンドで検証済み（`tests/e2e/e2e-pi-codex-ws.test.ts`、決定的モックアップストリームを本物のプロキシ経由で本物の pi に対して）：明示的 websocket と auto ルーティング、`session-id` == 会話 id によるアップグレードヘッダ押印、compress/decompress ラウンドトリップが後続要求に反映されること、`previous_response_id` 展開、アップストリーム拒否の挙動、明示的 sse の回帰ガード、そしてクロス-talk なしで一つのプロキシを共有する二つの並行サブエージェント風セッション。

### サブエージェント（pi-subagents）— ネイティブインストールのカバレッジ (#2185)

pi-subagents（pi.dev パッケージ）は前景と背景サブエージェント実行のために**子セッション**を spawn する。#2185 より前、ネイティブインストール（`bili plugin install pi` / `pi install npm:billion-context`）はこれらの子に bili エクステンションを確実にロードできなかった：

- **前景の子**は環境エクステンション探索をオフでプロセス内で実行される（`noExtensions: true`）→ bili エクステンションは決してロードされなかった；そのトラフィックは親プロセスのグローバル fetch パッチを通じてのみプロキシに到達したため、各子は**匿名プロキシモード `pfa-*` 会話**として記録された：圧縮は動作したが、名前付き `x-bili-plugin-conversation` identity も親系譜もなく、ACP ツールはプロキシ側ワイヤ注入としてしか存在しなかった；
- **背景の非同期実行**はデタッチされたランナーを起動し、その子*はもしかして*環境探索を通じてエクステンションをロードできる — デフォルト設定では偶然動作し、エージェント定義が `extensions`（`[]` でも）や `denyExtensions` を設定した場合、または pi-subagents バージョンドリフト / npm ストア同期問題では、直接アップストリーム接続（ゼロのプロキシ可視性）に黙って退化した。

**修正。** セッション開始時、pi エクステンションは pi-subagents のグローバル必須子エクステンションレジストリ（`globalThis[Symbol.for("pi-subagents.required-child-extensions.v1")]` で機能検出）に自身を自己登録する。レジストリエントリにより bili は**その親セッションから起動されるすべての子の必須エクステンション**になる；必須エクステンションは `additionalExtensionPaths` を通じて移動し、pi は `noExtensions: true` でも**`cliEnabledExtensions` バケットにロードする** — ため以下のすべてのセルでロードが決定的になる。登録は親セッションごとで、セッション終了時に破棄され、同じセッションの競合では既存のエントリに従う（先着ライター勝ち）。`requireForAllRunners` は意図的に**設定しない**：非 pi ランナー配置は拒否されるのではなく今日の挙動を保つ。レジストリが不在か外部形状（古い/新しい pi-subagents）の場合、エクステンションは修正前の挙動に退化し一度ログを出す。キルスイッチ `BILLION_CONTEXT_PLUGIN=0` / `BILI_NATIVE_PI=0` も登録を抑制する。新しい設定表面なし。

修正後マトリクス（実機検証済み：pi 0.83.6 + pi-subagents 0.76.0、HTTP トランスポート；WS 行は #2073 から文書化、ライブセルなし）：

| セル | 修正前 | 修正後 |
|---|---|---|
| ネイティブ × 前景 × デフォルト設定 | 匿名 `pfa-*` プロキシモード；ACP ツールはプロキシワイヤ注入経由のみ | **名前付き child-sid プラグインモードセッション**；ACP ツールは初回要求からローカル登録；圧縮は子の自分の id で記録 |
| ネイティブ × 背景 × デフォルト設定 | 環境の偶然 — 設定パッケージが偶然ロードされたときの名前付きプラグインモード | 同上、今や決定的（子の起動解決エクステンションに `required: ["bili"]`） |
| ネイティブ × 背景 × エージェント定義 `extensions: []` / `denyExtensions` | **黙った直接接続** — ゼロのプロキシ可視性、圧縮なし | 決定的な必須パスロード；名前付きプラグインセッション。（ランタイム能力上限がエクステンションを硬く拒否する場合、pi-subagents 0.76.0 は子起動を明白に失敗させる — fail-fast、黙ったものではなく） |
| ランチャーモード（`bili pi`）× 背景 | 子はプロバイダー書き換えを継承したが (#535)、bili は環境の偶然のみでロード | 登録が有効（意図的に `BILI_PROVIDER_REWRITES` でゲートしない）；親と子は継承した書き換えを経てルーティングされる名前付きセッション |
| いずれも × WebSocket のみトランスポート | スコープ外 — 上記 WS ギャップ参照 | 不変：クライアント側 WS インターセプトは依然 owner ゲート (#2073) |

知っておく価値のある注意点：

- **制限的な `tools:` ホワイトリストを持つロールは ACP チャネルを自動的に取り戻す (#2268)。** frontmatter の `tools:` リストが ACP ツール名を省略するエージェント定義 — 全 7 つの組み込みロールはこのように出荷される（例：`delegate` は `read,grep,find,ls,bash,edit,write,contact_supervisor` を列挙）— は #2185 の名前付きプラグイン修正の後、インタラクティブ圧縮を失わなくなった。bili はそうした子を要求ごとに検出する（pi-subagents はすべての子セッションのシステムプロンプトに完全な `<active_agent name="…">` マーカーを押印する；検出はシステムプロンプトキャリアにスコープされるため、歴史が単にマーカーを引用しているメインセッションは自分自身のチャネルを保つ (#2694)；ゲートはさらに要求の tools 配列 — namespace ラップ宣言を含む — が bili が注入する名前のどれも公開していないことも要求する）し、**プロキシ風圧縮チャネル**を通じて提供：ワイヤ注入 ACP ツール + nudge、サーバー側実行、`acp_summary` キャリア — 一方 #2185 の名前付きプラグインセッション identity を保つ。設定変更不要；ロールの元のホワイトリストはワイヤ上でそのまま残り、セッション中のホワイトリスト変更は次の要求で自己修復する。nicobailon/pi-subagents の子にのみスコープされる（マーカーはそのもの）；他のすべてのプラグインホストには影響ない。upstream がいつかマーカーを落とすと、これらのロールは #2268 前挙動（名前付きセッション、ローカル ACP ツールなし）に退化する。
  - ロールが ACP/bili 注入可能名の**どれか**を公開すると純粋プラグインモードにとどまる（重複ツール宣言はプロバイダーに拒否される）ため、**部分付与はサポートされない** — 何も付与するか、すべて付与する（`compress,decompress,search_context,acp_status[,acp_cache]`）。
  - 特定のロールにローカル登録（プラグインキャリア）ツールが欲しい？ 手動付与を保て：`tools:` フィールドを省略するか、そこに ACP 名を追加する。
- **背景の子の one-request 登録レース**（ACP ツールは 2 番目の要求から存在）はすべてのモードで既存。
- **挙動変更の開示：** 前景の子は匿名プロキシモード（`pfa-*`）から名前付きプラグインモード（child session id + 親系譜）に移る。厳密に多くの情報だが、`pfa-*` identity をキーにしているものは異なる id を観察することになる。

## Kiro CLI（AWS）

`bili kiro [opts --] [args]` はプロキシを起動し `kiro-cli` を起動する（`PATH` から解決、なければ `~/.local/bin/kiro-cli`；`BILI_CLIENT_BIN` が上書き）。`--` の後はすべて `kiro-cli` に渡る、例：`bili kiro -- chat --resume`。

**Kiro がモデルと話す方法（kiro-cli 2.37 で観察）。** エージェントのモデル呼び出しは **OpenAI Responses ワイヤ**：`POST https://runtime.<region>.kiro.dev/v1/responses`、ペイロード `{ model, input, tools, stream, origin, profileArn, metadata }`、`text/event-stream` としてストリーム返却される。Kiro は**ターンごとに完全な履歴を再生する**（そのシステムプロンプトは `input[0]` に `user` アイテムとして乗る）、bearer トークンで認証する（ボディ署名がないため書き換えられたボディも依然有効）、そして `HTTPS_PROXY` を尊重する。他のランタイム呼び出し（`KiroRuntimeService.*`、`/` の AWS-JSON）はモデルワイヤではなくバイト単位で中継される；ログに一度「unrecognized path」として現れるが、これは期待どおり。

**レーンが行うこと。**

- **cert-MITM、モデルゲートウェイのみ：** `runtime.us-east-1`、`runtime.eu-central-1`、`runtime.us-gov-east-1`、`runtime.us-gov-west-1`（`.kiro.dev`）。管理、認証、テレメトリホストはブラインドトンネルのまま。`--mitm-domain` で他を追加。
- **CA：** 両方の `SSL_CERT_FILE`（Rust シェルの rustls はルート*を置き換える*ためシステムルートも一緒に載せる必要）と `NODE_EXTRA_CA_CERTS`（バンドルされた Node エージェントサーバー、付加型）への結合バンドル。`NO_PROXY` はループバック（ローカルエージェントサーバー、MCP サーバー）を直接に保つ。
- **ロール（組み込み互換）：** ゲートウェイは `user` / `assistant` メッセージアイテムのみを受け入れる。bili が注入する compress プロンプトは `developer` アイテムで、ゲートウェイは `400 This request contains parameters or input that are not supported`（`param: input[0]`）で拒否する；`system` も同じく失敗。Kiro トラフィック（User-Agent `KiroCLI/…` または `x-amzn-kiro-origin`、`runtime.*.kiro.dev` ホスト上）では bili が自動的に `developer`/`system` → `user` に声を替える。最優先度：設定の `compat.roles` と学習済みロールは依然キーごとに優先。不変量判定者は注入プロンプトを元のロールのまま見るため、誤った I1 警告はない。
- **セッション identity：** Kiro の最初のアイテム（そのシステムプロンプト）はプロセス間でバイト安定ではないため、内容プレフィックスアフィニティでは `kiro-cli chat --resume` のたびに新しいセッションを鋳造してしまう。bili は `metadata["kiro:conversation_id"]` をセッション id（`kiro-<id>`、内容フィンガープリントの上でのみ、実際の会話ヘッダ / `session_id` / `prompt_cache_key` の上では決して）に昇格するため、圧縮状態が resume を生き残る。

**注記。**

- Kiro 自身のオートコンパクトはバックストップとしてオンに残る；bili はより早く折りたたむため、めったにトリガーしない。bili のみに依存するなら：`kiro-cli settings chat.disableAutoCompaction true`（グローバル Kiro 設定；`false` で元に戻す）。
- Kiro のストリームには usage 報告がないため、nudge 判定は bili のローカルトークン推定を使う（ログの `upstream success without usage report` は期待どおり）。
- Kiro の `reasoning` アイテムは署名付き（`encrypted_content`）でそのまま保持される；ターンと共に折りたたまれて消える。
- ランチャーなしの手動セットアップ：`BILI_MITM_DOMAINS=runtime.us-east-1.kiro.dev` で `bili` を実行し、その後 `HTTPS_PROXY=http://127.0.0.1:8787`、`SSL_CERT_FILE`、`NODE_EXTRA_CA_CERTS` を `~/.local/share/billion-context/ca/combined-ca.pem` に向かせて `kiro-cli` を起動する。

## 未リストクライアントの採用（モデル base URL が設定できる任意のクライアント）(#2340)

**モデルエンドポイントを編集でき API キーを持つ**（ログインではなく）すべてのクライアントは、一行の変更で今日すでに圧縮に乗れる — ランチャー不要、コード不要：base URL の先頭にプロキシオリジン + `/bili/` を前置する（`http://127.0.0.1:8787/bili/https://api.example.com/v1`）、API キーはそのままで、デーモンを実行する（`bili start`）。得られるのは完全な純粋プロキシ処理：圧縮 + ワイヤレベルツール注入。詳細と例：[configuration.md → `/bili/` プレフィックス](configuration.md#bili-prefix-api-key-clients)。

検証済みのエントリポイント（コミュニティ維持リスト — メカニズムは汎用的）：

| クライアント | base URL の場所 |
|---|---|
| **Cline / Roo Code / Kilo Code**（VS Code） | プロバイダー設定 —「OpenAI Compatible」Base URL、または Anthropic プロバイダーの base URL |
| **Continue** | `~/.continue/config.yaml` — モデルごとの `apiBase` |
| **OpenHands** | `llm.base_url`（設定または環境変数） |
| **Zed** | `settings.json` — `language_models.openai_compatible.api_url` |
| **Void** | カスタム OpenAI 互換エンドポイント設定 |
| **Cursor**（単一モデルチャネル） | Settings → Models → OpenAI API key → **Override Base URL** |
| **Warp** | カスタムモデル base URL 設定 |
| **Command Code**（`cmd`、commandcode.ai） | `~/.commandcode/providers.json` — プロバイダーごと（およびモデルごと）の `baseURL`（キーは `auth.json` にあり、このファイルには決してない） |

注記：

- **Crush** は今やランチャーレーン — `bili crush` を優先（設定は無変更、HTTPS ドメインが自動 MITM）。
- **Zed** もランチャーレーン — `bili zed` を優先（Linux；設定無変更、モデルドメイン自動 MITM、ループバックプロバイダーは直接のまま）。上記の settings.json `api_url` パスはクロスプラットフォームの代替として残る。
- **Command Code**：上記の行はその BYOK モデル（標準ワイヤ、今日圧縮）をカバーする。そのカタログ/ゲートウェイモデルはカスタムワイヤ（`POST /alpha/generate`）に乗ってバイト単位で中継される — [下記](#認識されないエンドポイントは直接に通り何も圧縮されない-1290) を参照；宣言可能ワイヤの修正は #1295 で追跡。
- **ログインする**クライアント（OAuth/サブスクリプション）は通常エンドポイントをハードコードしている — プレフィックス技は適用できない；代わりに[下の MITM セクション](#クライアントが-httpproxy-connect-を使うが何も圧縮されない) を参照。
- プレーンな **Web アプリ**（ブラウザのみ製品）はインターセプトすべきローカルトラフィックがない。
- VS Code エクステンションは base-URL フィールドをプレーンテキスト設定に保つがシークレットは OS キーチェーンに — ここでは base URL だけが編集される。

## クライアントが `http.proxy` (CONNECT) を使うが何も圧縮されない

一部のクライアント（VS Code ベース IDE：CodeBuddy、Cursor、Windsurf など）は HTTP **プロキシ**設定（`http.proxy`、`codingcopilot.httpProxyURL` など）しか提供せず — 書き換えられるモデル base URL がない。そうしたクライアントはプレーンな `/bili/…` 要求の代わりに、プロキシを通じて `CONNECT <model-host>:443` を送る。そのパスはモデルホストが bili の **MITM ホワイトリスト**にあるときのみ復号される；そうでない場合、bili は TLS バイトをブラインドトンネルする（不透明中継）ことで、モデル要求を見ることも圧縮することも決してできない (#897)。

この失敗モードは今や黙ったものではなく明白：

- ログにターゲットホストごとの一回限りの `BLIND TUNNEL WARNING`、修正手順付き；
- `curl -s http://localhost:8787/__bili/health` と `/__bili/stats`（ループバックのみ）の `blindTunnels`（カウント + 正確なターゲットホスト）；
- そうしたトンネルが存在する間、`acp_status` 出力の `UNDECRYPTED TRAFFIC (instance-level)` セクション。

そうしたクライアントを実際に圧縮するには：そのモデルドメインを `billion-context.json` の `"mitm".domains` に追加する（例：`"mitm": { "domains": ["copilot.tencent.com"] }`）または `BILI_MITM_DOMAINS` 経由、bili を再起動し、クライアントに bili のルート CA を信頼させる（Node ベースクライアントは `NODE_EXTRA_CA_CERTS=~/.local/share/billion-context/ca/root-ca.pem`、またはクライアント自身の CA パス設定）。`/bili/` プレフィックス技はここでは適用されない — 変更すべき URL がない。詳細：[configuration.md → MITM](configuration.md#mitm-transparent-proxy-login-clients)。

## 認識されないエンドポイントは直接に通り、何も圧縮されない (#1290)

bili は既知ワイヤプロトコル（`/chat/completions`、`/llm_raw_chat`、`/v1/messages`、`/responses` など）にパスがマッチする要求のみ圧縮する。他の任意のパスへの要求 — 例：サードパーティプラグインの**カスタムワイヤ**、Command Code の Go プランが `POST /alpha/generate` ようなもの — はバイト単位で中継され**決して圧縮されない**。

その結果は今や黙ったものではなく明白 (#1290)：

- クライアント側 fetch フックは各異なる未ルーティング **POST** エンドポイントをプロセスごとに一度ログに出す（`…is not a recognized model endpoint, so bili did not route it through the proxy…`）；非 POST トラフィック — npm レジストリ、カタログ JSON、git refs — は設計上黙っている (#1657：GET はプロンプトを載せられない)；
- `curl -s http://localhost:8787/__bili/stats`（ループバックのみ）の `unrecognizedPaths`（パスごとのカウント）；
- そうした要求が存在する間、`acp_status` 出力の `UNRECOGNIZED PATHS (instance-level)` セクション。

二つのシームが今や「カスタムパス、標準ワイヤ」ケースをカバーする — パスが非標準だが要求/応答形状が既知四プロトコルのいずれかであるエンドポイント：

1. **クライアント側、クライアントごと** — クライアントのモデル base URL を `/bili/` トンネルのプロトコルセグメント形式にする：

   ```text
   http://127.0.0.1:8787/bili/<protocol>/<upstream-base-url>
   # e.g. http://127.0.0.1:8787/bili/openai/https://relay.example.com/api/custom/complete
   ```

   `<protocol>` は `anthropic`、`openai`、`responses`、`google` のいずれか。パスに関わらずワイヤプロトコルを強制する — すべてのサーバー側シグナルに**優先**する。クライアントの base URL を制御できるがエンドポイントパスが非標準なときに使う。

2. **サーバー側、レーンごと (#1909)** — すでにホスト/パスをルーティングしているプロバイダークーキーに `"protocol"` を宣言する（[configuration.md → `protocol`](configuration.md#protocol) を参照）。クライアントの base URL を変更できないとき（ハードコードされたエンドポイント、MITM インターセプトされたホスト）に使う。

どちらの方法でも、宣言はワイヤを*識別*するだけ — そのプロトコルとしてパースできないボディは依然そのまま中継される (#1284)。真のカスタムワイヤ（独自の要求/応答形状、例：Command Code の `/alpha/generate`）は依然自分自身のサポートが必要；それの修正はプロバイダーの標準プロトコルエンドポイントを使うこと（Command Code の Provider プランは `POST /provider/v1/chat/completions` に投稿し、これは bili が圧縮する）。

## OpenCode

バンドルされたプラグイン 1 つが OpenCode の**両世代**に効く：エージェントファイルは V1 の `server()` エクスポートを V2 の `setup()` と併せて保持するため、ホスト ≥ 1.18.29 は V1 形状を読み、2.x ホストは V2 の `setup()` を読む。独立した [`opencode-acp`](https://github.com/ranxianglei/opencode-acp) エクステンションは V1 のみで、2.x では読み込まれ**ない** — OpenCode 2.x には billion-context が推奨コンテキストマネージャである。以下すべては `@opencode/cli` 2.1.0（V1 レーン：1.14.46 と 1.18.31）でエンドツーエンド検証済み。

| パス | コマンド | いつ |
|---|---|---|
| ランチャー（最易） | `bili opencode` | 1 コマンドでプロキシ+クライアント起動；実設定は無変更 |
| ネイティブ（ランチャーなし） | `bili plugin install opencode` | 実設定への自己起動プラグイン；`opencode` を通常通り起動 |
| 純粋プロキシ（フォールバック） | baseURL `/bili/` プレフィックス | プラグインなし — ワイヤレベルツール注入 |

これらのパスは**互いに排他** — 各々が同じ要求のルーティングを所有するので、ホストインスタンスごとにちょうど 1 つのみが有効。手書きの `/bili/` プロバイダー baseURL は純粋プロキシパスのマーカ；ネイティブプラグインがインストールされている間にそれを書くと**競合する設定**になる (#1958)：ランタイムはセッションごとに一度警告する（オリジンごとに重複除去）+ 修正ガイド付き — プレフィックスを外すかプラグインを外す — そして要求はそのパスがエンコードするプレーンプロキシパスにとどまる（プラグインセッションマーカなし）。サポートされる例外は**同じ**オリジンの明示ピン — URL がすでに載っているプロキシに向く `BILLION_CONTEXT_PROXY` — これは黙ったまま。

### ランチャー — `bili opencode`

HTTPS は cert-MITM、HTTP は `/bili/` を付けた一時 `opencode.json` クローン（JSONC コメント可；opencode 自身がマージする方法でマージ；相対ローカルプラグンスペックはクローン内で絶対パスへ再アンカー — opencode は宣言設定ファイルのディレクトリに対して解決、#826）。ホスト世代は `--version` プロブで検出（プロブ失敗は 1.x に既定）：**2.x** ホストには組み込み V2 プラグイン（`dist/agent/opencode.js`）が一時ラッパーディレクトリとして注入され、その `index.js` がプラグインファイルを再エクスポートする（2.x は設定の `plugin` 配列での裸ファイルパスを拒否）；**1.x** ホストは裸ファイルパスを受け取る。

プラグインが行うこと（両世代）：bili ツールをホスト内でネイティブ登録 — compress / decompress / search_context / acp_status (+ absorb) — すべての送信プロバイダ要求にプロキシヘッダを盖章し、ホスト自身のモデルカタログから読むコンテキストウィンドウ/最大出力を含む（`ctx.catalog.model.list()`、60s ごと更新）をランタイム情報としてプロキシに報告 (#955) — 圧縮はプラグインモードで走り、ワイヤレベルツール注入は**一切ない**。ネイティブオートコンパクトは自動的に無効化される（`compaction.auto: false`）。すべての登録は防御的（オプショナルチェーン）：シームが欠けているか決して発火しないどんな 2.x ビルドでも、プラグインは不活性のまま透明にプレーンプロキシモードでセッションが走る（壊れる代わりに）— API サーフェスが互いに異なる隣接 `dev` ビルド間で観察済み (#754 review probes)。

1.x 固有（検証済み 1.14.46 + 1.18.31）：V1 `.server()` フックはすべてのプロバイダー `options.baseURL` をプロセス内で `<proxy>/bili/…` に書き換え、`compaction.auto: false` をセット；`chat.headers` は要求ごとにプラグインヘッダを盖章；`tool` は bili ツールを実の zod 形状で登録（zod はランタイム依存 — 解決できない場合プラグインは書き換えのみに退化）。明示的な `baseURL` なし**のプロバイダー（SDK 既定、例：裸 `@ai-sdk/openai` → api.openai.com）はグローバル `fetch` パッチで捕捉される（ログ：`v1: fetch patch installed`）— イデムポテント、`/bili/` 包み URL は無変更で通過；OpenAI Responses エンドポイントを含めて検証済み。

### ネイティブ（ランチャーなし） — `bili plugin install opencode`

実 opencode 設定に自己起動プラグインを登録し、`compaction.auto: false` をセット；以降プレーンな `opencode` がそのまま動く。既定では MCP フェースは追加されない（ネイティブプラグインがすでにセッション紐付きの bili ツールを提供）— `--with-mcp` を渡すと 1 つ追加 — そのエントリはオリジンピンを持たないので、プラグインのエフェメラルポートプロキシ再起動を生き残る (#926)。エントリ形式はホスト世代と**この** bili のインストール方法の両方に依存する。**OpenCode 1.x npm インストール**は裸パッケージ名を書く（`"plugin": ["billion-context"]`）— パッケージは `exports["./server"]` → `dist/agent/opencode-native.js` を公開するので、opencode は自身の Npm.add メカニズムで読み、絶対パスゼロ、ポータブル。（その正確な裸名エントリは bili なしの手動インストールとしても機能する — README Quickstart Option 1 参照。）**OpenCode 2.x ホスト**では — およびどんな **git チェックアウト / dev ビルド**でも — インストーラは代わりにローカルシムディレクトリを書く（`<configDir>/plugins/billion-context/index.js` → このインストールの `dist/agent/opencode-native.js`）：2.x は裸パッケージ名をパッケージの `main` フィールド（`dist/index.js`、CLI — プラグイン定義なし）経由で解決するので、裸名はそこで決して読まれない (#3976)；install の再実行（または新パスへの再インストール）でシムが現在のルートに向くよう再生成され、2.x 設定内のレガシー裸名エントリは自動的にシムへ移行される。

ロード時にプラグインは自身のプロキシをブートストラップする（二重化せず健全なインスタンスにアタッチ；opencode が終了すると parent-pid ウォッチドッグが殺す）、モデル API トラフィックを `<proxy>/bili/<upstream-url>` にルーティングし、ランチャーモードと同じネイティブ bili ツールを公開 — 固定ポートなし、環境変数なし、ランチャーなし。オプトアウト：`BILI_NATIVE_OPENCODE=0`。健全なプロキシを作れない場合、要求は直接（非圧縮）に通り一度限りの警告付き、自動回復。`bili opencode` 起動下ではこのエントリは完全にスキップされる（プロキシはランチャーが所有）。

### OpenAI Responses WebSockets (V2)

V2 プラグインは OpenAI の `experimental.ws.handshake` 要求もインターセプトする。両レグが WebSocket を使う：OpenCode → bili → Responses アップストリーム。これは API キー OpenAI と ChatGPT Pro/Plus ブラウザ/ヘッドレス OAuth の両方を含む；ログイン方法はトランスポートを選ばない。OpenCode 設定書き換えも新しい bili 設定も不要。ソケットはローカル起源で協調プラグイン identity を載せなければならない；汎用または未主張のアップグレードは 426 を維持。

ACP 処理、ネイティブツール、usage 計上は有効のまま。クライアント delta は圧縮前に展開される。アップストリーム delta は処理済み履歴が前回の応答を正確に拡張する場合のみ使用される；フォールドは同じソケット上で完全な圧縮入力と共に新しいチェーンを開始する。ref タギングや他の履歴編集も完全入力を必要とすることがあるので、接続再利用はターンごとに増分であることは示さない。実験フックのない古いホストは OpenCode 既存の `providers.openai.settings.transport: "http"` 設定を使わなければならない。リアルタイム、多重化同時応答、リモート WS クライアントはこの統合のスコープ外。検証：ライブ OpenAI/ChatGPT 認証情報ではなく、ローカル Responses WS アップストリームを持つ実 OpenCode V2.0.20。

### 純粋プロキシ（プラグインなし）

他のクライアントと同様に、プロバイダー baseURL をプロキシに向ける：

```json
{
  "provider": {
    "myprovider": {
      "npm": "@ai-sdk/openai-compatible",
      "options": {
        "baseURL": "http://localhost:8787/bili/http://upstream.example/v1",
        "apiKey": "sk-any"
      }
    }
  }
}
```

注：2.0 AI-SDK プロバイダーはローカルエンドポイント（チェックしないもの）でも `apiKey` フィールドを要求する — いかなる非空値でもセット。

このパスは**プラグインなし**を意味する：ネイティブプラグインもインストールされている場合、ランタイムはセッションごとに一度警告する — プロバイダーごとに 1 つのパスを選ぶ (#1958)。

### Status: `/acp` と `acp_status`

`/acp` パネルは全モードでセッション紐付きで、`acp_status` ツールはそのホスト内同等物がどこでも。2.0.x stable では（コマンドエディタがエントリ追加をサポートし（`editor.add`））、V2 プラグインは `/acp` スラッシュコマンドを追加登録する — 合成の非モデルメッセージとしてレンダリングされ、`acp_status` ツールと同じくパネル優先；古い形状では登録は不活性のまま。`opencode run` モードはスラッシュコマンドを一切ディスパッチしないことに注意（モデルに通過）— TUI を使うこと。

同じシームが `/acp-cache` (#1146) を載せる — プロンプトキャッシュ調整レポートへの人間エントリポイント（`acp_cache` ツールと同一出力）：pi/omp はネイティブ登録（全行一覧は `/acp-cache [full]`）；opencode V1 はそれがモデルコンテキストに届く前にプロキシがワイヤから剥奪する無視メッセージとしてレンダリング；opencode V2 は合成メッセージとして（レポートは ~8 KB まで可視）；dsh（両レーン）は既定サマリー台帳を表示 — dsh のコマンド API は引数を渡さないので `full` はない。レガシー opencode-acp セッション (#920) は代わりに明示的な利用不可通知を受ける（そのトラフィックはこのプロキシの圧縮状態をバイパス）。Claude Code はインプロセスコマンド API を持たない：`bili plugin install claude` はモデル仲介の `commands/acp-cache.md` マークダウンコマンドを書き、そのプロンプトが `acp_cache` MCP ツールを駆動してレポートを逐語貼り戻す。codex/kimi/hermes はユーザー入力可能なコマンドシームを公開しない — モデルに直接 `acp_cache` ツールを呼び出させること。フォールドごとの損益判定はオプションの `compress.priceProfile`（入力トークン単位の正規化倍率）で価格付けされる；どのレベルもそれをセットしない場合、要求モデルの models.dev 価格行が絶対 $/Mtok で適用される（解不能モデルにのみカーネル比率既定）— よって breakeven/PAID BACK は箱出しのままアップストリームの実経済を反映する；カスタムマークアップのレレーにはプロバイダーごとに上書き（configuration.md, #1279）。

同じシームが `/acp-rule` (#1251/#1399) を載せる — 永続ルール機能への人間エントリポイント（`acp_rule` ツールと同一出力）：pi/omp はツールの完全操作セットでネイティブ登録 — 裸 `/acp-rule` は記録済みルールのすべてを一覧、`/acp-rule <text>` は 1 つを直接記録（モデルが呼び出したかのように）、`/acp-rule remove <id>` は 1 つを削除、裸 `/acp-rule clear` は記録済みルールのすべてを抹消（`clear <text>` は抹消ではなく記録 — タイポがすべてのルールを破壊してはならない）で。包まれたトランスクリプトメッセージはキャッシュレポートと同様に内容署名でモデルコンテキストから剥奪される — 記録済みルールはシステムプロンプト注入経由でターンごとにモデルに届く。

### Legacy opencode-acp セッション (#920)

1.x ホストでは、移行前の [`opencode-acp`](https://github.com/ranxianglei/opencode-acp) セッションは両レーン下で動き続ける：ランチャーはその一時設定クローンから `opencode-acp` エントリを剥離する（ホストは武装状態で決して読まない）、各レーンはインストール済みパッケージを吸収する（`node_modules` から直接インポート — `.opencode/node_modules`、プロジェクト `node_modules`、グローバル npm ルート、または opencode の設定スコープモジュール、最初のヒットが勝つ）。セッションがレガシーであるとは、opencode-acp の永続化状態ファイルが存在すること（`<XDG_DATA_HOME>/opencode/storage/plugin/acp/<sessionID>.json`、または `acp.jsonc` の `storagePath` のディレクトリ）：

- **レガシーセッション** — 圧縮は吸収された opencode-acp を通って走る（自身の ref とブロックストアは動き続ける：`compress` / `decompress` / `search_context` / `acp_status` / `acp_context_recap` がすべてそこで実行）。そのモデル要求は `x-bili-plugin-bypass: 1` を載せ、プロキシはそれらを逐語転送 — ワイヤ注入なし、nudge なし、セッションバインドなし。
- **新セッション** — bili が所有：ツール呼び出しはプロキシのプラグインエンドポイントへ転送（プラグインモード）。実行者はセッションレーンでルーティングするので、新セッションの `compress` はプロキシに届き、レガシーセッションのそれは opencode-acp に届く。`acp_context_recap` にプロキシ側の対応物はない — 新セッションではプロキシは未知ツールメッセージで応答する。

`/acp` と `/dcp` も同じようにルーティングされる。新セッションの opencode-acp レジストリへの取り込みは、そのトランスフォーム（system / messages / text.complete）をレガシー述語でゲーティングすることで防止される。退化：パッケージが欠けているかインポート失敗（または v1 でない）場合、bili は単独で走り、レガシーセッションは読み取り専用アーカイブとして振る舞う（古いタグはレンダリング、`decompress` は `[Block … not found]` を返し、新しい ref は m00001 から再開）。

### Caveats

- 2.x 系は npm パッケージ `@opencode/cli` として公開され、そのプラグイン API サーフェスはビルド間でまだ移動している（隣接 `dev` チャネルビルドは異なる `ctx` 形状を公開）— 上記のフック/ツール詳細はバージョン固有の観察であり、安定契約ではない。
- 設計注：V2 プラグインは薄いプロトコルクライアントである（内部に acp-kernel なし）。これはプロキシが圧縮権威の単一にとどまるため — エージェントとプロキシ間のカーネルバージョンドリフトを排除する；プラグイン API がコンテキストを変更できないという能力に依存しない（その能力は 2.x ビルドにより異なる）。
