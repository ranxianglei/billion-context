# 会话身份判定（同一客户端会话 ID，不同对话）

设计记录：当请求的**会话 ID**（客户端铸造的会话标识）已经认出之后，
billion-context 如何判定它属于**哪一个对话**。姊妹页：仓库根目录
`SESSION-IDENTITY.zh-CN.md`（**匿名车道**：请求什么 ID 都没有时怎么办）、
`MESSAGE-IDENTITY.zh-CN.md`（消息级身份教义）、`docs/identity-channels.zh-CN.md`
（各客户端把 ID 带进 bili 的接线地图）。规范条文：AGENTS.md KDD #11（身份层级）
与 KDD #18（信道接线的单一缝法则）。

## 两类标识符及其分工

- **会话 ID**（代码里的 `rawId`）。客户端每轮都带的稳定字符串（如
  `x-claude-code-session-id`、`agent-session-id`、`x-conversation-id`）。
  认名层（`src/session-id.ts`）从一个有序的候选头名表里取值——客户端专属的
  高信任名排在裸通用名之前——取出的字符串就是基础键。它负责把请求**归堆**；
  堆里是哪个对话，它管不了。
- **消息 ID**（宿主给每条消息铸造的 UUID，如 dsh 的稳定盖章）。存在时，它是
  "同一会话 ID 下多个对话"之间的裁决者。合法形状规则在 `src/msgid-pin.ts`
  （长度 ≤512、拒收保留前缀 `acp_summary_`、拒收控制字符）；多份手写同步副本
  的一致性由 `tests/msgid-rule-parity.test.ts` 机械钉死。

两者都只是客户端↔bili 之间的记账信息：所有内部字段/头（`biliMsgIds`、
`x-bili-msg-ids`）在出站前一律剥除（`UPSTREAM_HOP_HEADERS`），永不进入模型端点。

## 判定梯（`src/session-resolve.ts`，`resolveSessionOrder`）

每个会话 ID 下维护一份**骨架**：消息类型序列、头部哈希碎片、system/persona
文本的 sha256（空串 = 非锚定）、声明的模型——防抖落盘持久化，重启不会重跑
冷启动认领竞态（#3397）。每个请求按顺序走：

1. **派发车道令牌**（#5095）：claude 子代理等每轮唯一的派发令牌直接认领自己
   的确定性键，无需任何佐证。
2. **该 ID 下的首次到达**。主对话形状的完整历史认领原始键；无 persona 标签的
   浅历史（单条用户 blob、没有 assistant 行）**从不**认领——进
   `<ID>|sub:aux`。#1916"审查偷占原始键"竞态在这一档被杀死，且不需要读正文。
3. **逐字续接**。前缀对齐 + 尾部片段核验。覆盖几乎每一轮的快路径。
4. **persona 文本变了（同一 ID、不同 system prompt）**。每一档逃生都要
   *逐字级*内容证据——区分"换了提示词的同一次对话"与"挂在共享 ID 下的陌生
   对话"：
   - 已存记录的头部消息被逐字重放（锚点迁移，#2241/#2250）；
   - 声明的模型切换有请求头佐证（#2601/#2817）；
   - 重启后持久化前缀链延续（#2156/#2815）；
   - ≥8 组同位置吻合 run，证明是宿主体内改写同一段历史（#4778，
     `CONTINUATION_MIN_RUN`）；
   - 更短的重放但尾部片段核验通过（压缩换头、尾巴原样，#5686）。
   任一档成立 → **重新锚定回原始键**。全部失败 → **派生 persona 车道**
   `${会话ID}|sub:<fp16(persona文本)>`：后缀确定性计算，同一 persona 后续每轮
   恒定落在同一条车道上，车道数不随流量增长。
5. **同一 persona、顺序分叉**。尾部对齐则重锚（骨架跟随活着的端）；形状完全
   对不上 → 派生任务车道 `${会话ID}|sub:task:<skel8(类型序列)>`。
6. **末档：消息 ID 救援**（#5719，`tryMsgIdRescue`）。只在那些"字节级证据
   **恰好在那一轮全部被销毁**"的出口才咨询（典型事故形状：客户端本地压缩删了
   行、同一轮又改写了易变的 system prompt 字段——#5719 本尊）。收到的宿主
   消息 ID 与该键下已存行重叠 ≥1 → 同一对话，重锚；零重叠 → 反证分叉；请求
   没带 ID → 照 #5719 之前的行为分叉。

下游一切状态（存储行、折叠块、水位种子、账本序号）都挂在判定梯返回的那个键
上——原始键或带后缀的键——所以同一会话 ID 下的两个对话各自存储、各自折叠、
各自压缩，互不干扰。

### 为什么消息 ID 档在最后一位而不是第一位

规则本身是无条件的：**会话 ID 对上 + 消息 ID 重叠 ≥1 ⇒ 同一对话**，不附加
任何其他条件（owner 教义；实现就在 `src/session-resolve.ts` 的
`tryMsgIdRescue`）。刻意的是它在梯子上的**位置**。理由成文（owner 讨论
2026-11-07，裁定：维持现状）：

1. **语义不对称**。*零*重叠是安全的反证；*正*重叠推不出"同一对话"——存在一类
   合法流程复用同一个会话 ID、内容里带着更早的历史、但属于不同角色（标题生成、
   审查、派生任务——事故记录 #150 新任务、#1916 自动审查、#4438 审查请求整条
   主管道横穿原始键并打爆状态）。若把重叠裁决设为全局第一步，这类请求会在任何
   结构性检查出手之前就被判成主对话的一部分；而在盖章车道里（主流程每轮都把
   全部历史连同 ID 原样重发，重叠**恒成立**），多角色分流会被永久短路、后面
   所有档位变死代码。那时正确性系在"上游恰好不发 ID"上，不是判定自身的保证。
   放在末位后，同一条规则只在结构性证据已说"像新对话"、且字节链因已知良性
   原因断掉的位置启用——在那里，"有重叠"排除了所有其他解释，结论才是铁的。
2. **数据位置**。续接检查跑在内存骨架上（上一轮请求刚写入）；已存消息 ID 集
   合在数据库里。把比对虽便宜但要读库的一步放到纯内存步骤前面，等于给热路径
   每轮加一次存储读取。
3. **可得性**。多数车道的请求根本不携带消息 ID（未盖章、未接采集），这一档对
   它们不存在。

## 开关分层（合并后哪些生效、哪些保持关闭）

| 层 | 机制 | 合并后默认 |
|---|---|---|
| 会话 ID 认名（含新增 `x-conversation-id`、`agent-session-id`） | 不灰度；值是客户端发来的，只作本地键用，绝不转发 | 对全部安装生效 |
| 消息 ID 采集（代理读客户端本地转录/sqlite：claude-code、codebuddy、mcode、goose、qwen-code） | `env BILI_IDENTITY_HARVEST` **或**灰度键 `rollout.features.identityChannelHarvest`（任其一即可使能）× 仅回环来源 | 全量**关**，直到显式开启 |
| 行钉住（盖章/采集来的 ID 写入存储行身份，两条 wire 均覆盖） | 既有灰度键 `pluginLaneServerHistory` | 0%（未动） |
| 内部 ID 字段/头的出站剥除 | 无条件 | 中性（这些字段本就不该出代理） |

各车道的完整状态表（已接 / 闭合备忘 / 暂缓，附审计理由）见
`docs/identity-channels.zh-CN.md`。

## 信任边界与退化契约

- **整轮退化，绝不做部分错绑**。任何一步失败（行数不对、文件写到一半、表结构
  漂移、校验拒收、角色抽查不符）都丢弃该轮**整份**候选列表，请求整体回退到
  接线前的路径。不存在"映射一部分、猜其余"的模式。
- **仅回环采集**。即使开关打开，注册表也拒绝非回环来源；适配器默认信任本机
  客户端。
- **布局知识是源码审计级**。适配器对表、列、排序、"哪些行该数"的预期来自阅读
  上游源码而非真机测量——这正是采集功能出厂即双开关默认关的原因。
- **分叉安全性**。唯一会认错的前提是两个不同对话在同一会话 ID 下逐字共享长段
  内容；碎片是哈希级的，实际不成立。已知角落：浅辅助调用可能先到场抢占空 ID；
  真正的主对话随后到场靠持久化前缀链诸档回到正确归属或干净分离——已有回归
  测试钉住（首次到达认领规则 #316；#1916 aux 分支）。
- **#5719 档的可达性保留意见**。审查/辅助派发是否会携带与父记录重叠的盖章 ID
  取决于宿主行为，生产日志尚无实证——按 PR #5826 review P1 跟踪为"加一行日志
  观察"的后续项，明确不以猜测关闭。
