# 技術ノート

README に記載されている 3 つの使用オプションの背後にあるメカニズムレベルの詳細です。
README では各オプションを簡潔に記述しており、「実際の動作原理」に関する内容はオプション間の説明ではなく、ここに記載されています。

## 拒否リクエストのトークン測定

コンテキストオーバーフローからの回復処理では、アップストリームのコンテキストウィンドウと、拒否されたリクエストの合計トークン数、入力メッセージ数、および補完（completion）予約量を区別します。パーサーは、OpenAI/DeepSeek 形式の括弧付き分割（`requested N tokens (M in the messages, C in the completion)`）と、SGLang/LiteLLM 形式のコロン区切り分割（`requested a total of N tokens: M tokens from the input messages and C tokens for the completion`）の両方を受理します。明示的な入力カウントは既存のキャリブレーションリングに供給され、補完カウントは既存の出力ヘッドルーム予約を有効化します。ウィンドウ情報のみ、または不完全なエラーメッセージからは、捏造されたトークン測定値は提供されません。このパース処理はプラグインモードとプロキシモードで共有されており、宣言されたモデルウィンドウを変更することはありません。

## 短いソースビュー後のフォーク回復

フォーク採用では、ソースの最後の `active` フラグではなく、子プロセスのリプレイに対して保持された圧縮ブロックを判定します。短いソースリクエストにより、フォールドが一時的に無効化される場合がありますが、その完全な元のスパンは子プロセス内で返ってくる可能性があります。完全に存在する保持スパンはアクティブブロックとしてコピーされますが、明示的に展開されたブロック、消費済みティアの子、およびフォーク境界をまたぐスパンは独立してアクティブ化されません。ティアの子は、採用された祖先とともに無効レコードとして付随します。プランニングと採用処理は、ソースセッションを変更しません。

## ネイティブプラグインライフサイクル（オプション 1）

読み込み時に、プラグインは**独自のプロキシを生成**します（または、正常に実行中の既存プロキシにアタッチします — 親 PID ウォッチドッグがクライアント終了時にそれを破棄します）。モデルトラフィックを `<proxy>/bili/<upstream-url>` に書き換え、`compress` / `decompress` / `acp_status` をネイティブクライアントツールとして登録し（プラグインモード）、`/acp` パネルを現在のセッションにバインドします。また、クライアントの**独自のモデル設定**をプロキシに報告します（ランタイム情報プロトコル、#955）。これにより、圧縮予算がレジストリの推測値ではなく実際のウィンドウを使用します。オプトアウト用の環境変数: `BILI_NATIVE_PI=0`, `BILI_NATIVE_OMP=0`, `BILI_NATIVE_OPENCODE=0`, `BILI_NATIVE_DSH=0`, `BILI_NATIVE_KIMI=0`, `BILI_NATIVE_HERMES=0`, `BILI_NATIVE_ZCODE=0`。

## プロキシ再利用とアタッチゲート (#1225, #1335, #1232, #1660)

ネイティブフックは、独自のものを生成する代わりに、すでに実行中のプロキシにアタッチできます — ただし、以下のライフサイクルゲートを通過した場合に限ります。再利用はアイデンティティベースです（#1225）：既存のプロキシは、**同じコード**（エントリスクリプトの sha256、インスタンスファイルに記録）を実行しており、**レーンが互換性がある**場合 — 各ランチャーはクライアントのレーンを宣言し、2 つの*異なる宣言された*レーンは決して共有せず、宣言されたレーンを持たないインスタンスは手動で起動されたユーザーゾーンデーモンであり、その軸ではワイルドカード互換 — **かつライフサイクルゲートを通過している**場合（§以下）にのみアタッチされます。ライフサイクルゲートとは、アームされた親 PID ウォッチドッグ（`watchdog.armed == true`）であり、つまり親 PID を持つランチャーによって生成され、最後にアタッチされたセッションが死んだときに死ぬことを意味します。**または**、ユーザーゾーンインスタンス（レーンなし、ローンチトークンなし）であり、定義上免除されます（#1660）。#1225 以前に書き込まれたインスタンスはコードフィンガープリントを持たないため、決してアタッチされません：再構築または更新されたインストールは、次の起動時に常に新しいプロキシを開始するため、修正が即座に反映され、古いコードを黙って提供することはありません。

| リスナー | アタッチ? | 理由 |
|---|---|---|
| このセッションによって生成されたプロキシ | ✅ | 生成時にアーム済み |
| 他のセッションのアーム済み共有プロキシ（ウォッチャー設定済み、#1186） | ✅ | 共有は設計通り |
| 手動で起動された `bili start` デーモン（ユーザーゾーン、#1660） | 🔶 条件付き | **ユーザーゾーン**インスタンス（レーンなし、ローンチトークンなし）：**アーム済み**のもの（管理された共有プロキシ、#1225）は、互換性のある任意のクライアントレーンによって利用されます；**アーム未設定**の手動ものは、デフォルト（`attachPolicy: own-lane`、#2877）では、レーン付きフックによって利用されません — 代わりに独自のものを生成します。`attachPolicy: global-fallback`（#2877 以前）または `attachExternal=1` の下では利用されます。いずれの場合も、そのライフタイムとバージョンはあなた自身が管理します |
| アーム未設定の**レーン付き**プロキシ（クラッシュしたセッションの孤児；#1330 以前は検証不能） | ❌ 明確に拒否 | ライフサイクルドリフトの兆候（#1335）：これを利用すると、ライブセッションが所有していないプロキシを黙って再利用することになります |

フックはアタッチ前に各候補の `/__bili/health` をプローブします：アーム済み → アタッチしてウォッチャーを登録（変更なし）；**アーム済みユーザーゾーン**候補は、レーンアフィニティポリシーに関係なくアタッチされます（管理された共有プロキシ、#1225）；**アーム未設定ユーザーゾーン**（手動）候補は、`attachPolicy: global-fallback`（#2877 以前）または `attachExternal=1` の下でのみアタッチされます — デフォルト（`own-lane`）では、レーン付きフックは独自のものを生成します（#2877）；アーム未設定の**レーン付き**候補（クラッシュしたセッションの孤児、または `watchdog` フィールドを全く報告しない #1330 以前のビルド — 検証不能、アーム未設定として扱われる）は**明確に**拒否され、セッションはセルフマネージドポートゾーン（ベース `18787`、またはレーンのスティッキードリフトレコード；生成時にアーム済み、最後のセッションとともに死ぬ、#1186 ウォッチャーセマンティクス）で独自のプロキシを生成します。バージョンズレは固定されます：コードフィンガープリントチェックが最初に実行されるため、再構築または更新されたインストールは、ユーザーゾーン免除であっても古いデーモンを利用しません。コスト：アタッチ可能なものが存在しない場合、セッションごとに 1 つの短命プロキシプロセスが追加されます（セッション状態はディスク上で共有されるため、圧縮の継続性は影響を受けません）；マルチインスタンス警告（#394）は対応してより頻繁に表示されます。**エスケープハッチ：** 設定ファイル内の `native.attachExternal: true` または `BILI_NATIVE_ATTACH_EXTERNAL=1` は、ウォッチドッグ状態に関係なく（#1330 以前のビルドを含む）*レーン付き*リスナーへのアタッチを拡張します — その場合、これらのデーモンのライフタイムとバージョンはあなた自身が管理します；`attachExternal` は**レーン付き**デーモンの*ライフサイクルゲート*のみを管理します（ユーザーゾーンアタッチを開閉するものではありません — その軸は `attachPolicy` です）；`attachUrl`（環境変数 `BILI_MCP_PROXY` / `--origin`）は明示的なターゲットオリジンを固定します。明示的なユーザー指示によるアタッチ（kimi/dsh 用の `BILLION_CONTEXT_ATTACH` / プリセット `BILLION_CONTEXT_PROXY`）は、発見プロセスを完全にバイパスし、構造上免除されます。

アタッチ発見は、**すべての**ライブインスタンスに対してレーン認識です（#1232）：ランチャーはインスタンスレジストリの単一のインスタンスファイル（後書き込み優先 — 並行マルチクライアント使用下では、他のクライアントのプロキシを指す可能性があります）だけでなく、すべてのライブエントリをプローブし、すべての候補に上記のゲートを適用します。互換性のある候補の中で、ランチャー自身の宣言されたレーンを持つ最新のインスタンスが勝者となります；レーンを持たないインスタンス（ユーザーゾーンデーモン）は、レーン軸ではワイルドカード互換であり、デフォルトでゲート免除です（#1660）— ただし、レーン付きフックが実際にそれにフォールバックするかどうかは `attachPolicy` によって管理されます：`own-lane`（デフォルト）は*アーム未設定*の手動デーモンを利用しません（#2877）、一方 `global-fallback` は #2877 以前のワイルドカード利用を復元します。`another bili instance is running` 警告（#394）もレーン認識です：同じレーンまたはレーンなしの共存に対して発火しますが、2 つの*異なる*宣言されたレーンの間では沈黙します（それらのセッションファイルは互いに排他です）。

**再利用されたプロキシは、独自のプロセスローカルのリゾルバ状態を保持します（#5222）。** アタッチ/再利用はセッションを*長命*プロセスに引き渡します；OS レベルのネットワーク変更（WSL/VPN スイッチ、MagicDNS 引き継ぎ）の後、そのプロセスの libuv スレッドプール — `dns.lookup` と undici のデフォルトコネクタがアウトバウンド接続で共有するもの — が固着し、他のプロセスが正常に解決しているにもかかわらず、その内部でのすべてのルックアップがタイムアウトする可能性があります。*ホスト*（例：DSH Web）を再起動しても、それは更新されません：インスタンスレジストリは同じ PID を黙って再採用します。対策：PROXY プロセスを再起動する（`~/.local/state/billion-context/instances/` に記録された PID を kill する）、またはアウトバウンドをアップストリームプロキシ経由でルーティングする（`-F` / `BILI_UPSTREAM_PROXY`、これはローカル DNS 承認を完全にスキップします）。#5222 以降、トンネル承認も自己防御します：メインプールのルックアップがリトライを使い切った場合、`unresolvable` 判定の前に、新しいワーカースレッドプールで 1 回のプローブが実行されるため、固着したプロキシは健全な宛先を誤って拒否することを止めます（ワーカーの結果によって承認され、完全な回復のためにプロキシを再起動するようオペレーターに警告する大きな警告ログとともに — その時までアウトバウンド接続は固着したプールを共有し続けます）。フェーズ 2（オーナー決定 2026-10-31：検出 + 表面化、自己再起動はしない）は、承認 MAIN プールの結果のみを供給源とする永続固着検出器を追加します（ワーカープローブは承認を緩和しますが、プールを修復しません）：THROW するルックアップのみが失敗としてカウントされます（権威的な空の応答はリゾルバが到達可能であることを証明します）、そしてゲート — このプロセスが以前に正常に解決した少なくとも 2 つの異なるホストが、それぞれ現在 ≥5 分間連続して失敗している（`src/resolver-wedge.ts` の `WEDGE_MIN_HOSTS` / `WEDGE_SUSTAIN_MS`；トラッカーは FIFO で 256 個のユーザー指定ホストに上限）— が Web パネルのバナー、`/__bili/status` + `/__bili/overview` 上の追加フィールド `resolverWedge`（健全な間は null）、`acp_status` アラーム行、およびエピソードが持続する間 10 分ごとに再記録される警告ログ行を駆動します；プロセスの動作は変更されません。

## 共有状態ディレクトリとマルチインスタンスセキュリティ境界 (#394, #1724)

ホスト上のすべての bili インスタンスは、**同じ**ホスト毎のストレージを読み書きします：XDG データディレクトリ（`~/.local/share/billion-context/` — セッションレコード、CCR コンテンツストア、プレフィックスアフィニティ）および状態ディレクトリ（`~/.local/state/billion-context/` — ログ、インスタンスレジストリ）。コントロールプレーンはレーン認識です（#1232：アタッチ発見と #394 共存警告の両方が宣言されたレーンを尊重します）、しかし**データプレーンは分割されていません** — ディスク上にセッション毎のオーナーやレーン毎の分離はありません。これにより 2 つの結果が生じます：

- **インスタンス間セッション可視性。** 各インスタンスの Web UI（`__bili/sessions` リスト / 詳細 / ログ）は共有ストア全体を再スキャンするため、ループバック経由で到達可能な任意のインスタンスは、そのホスト上の他の任意のインスタンス/レーンによって作成された*任意*のセッション — 生のメッセージ、コンテンツストアペイロード、圧縮ブロック — を列挙し、読み取ることができます。
- **再起動ドレイン競合。** 再起動時、新しいプロセスは古いプロセスがフラッシュを完了する前にストアをハイドレートするため、後書き込み優先により古いプロセスの最終的な書き込みが失われる可能性があります：末尾更新の喪失とプロバイダープレフィックスキャッシュの破棄（アウトバウンドボディがプロバイダーがキャッシュしたものから乖離する）。#1724 の緩和策：#405 スナップショットカウンターガード（古いセッション書き込みを拒否）、プレフィックスアフィニティ書き込み時 Union ガード（#1737：1 つのインスタンスのフラッシュが兄弟チェーンを上書きすることはない）、および自己再起動順序修正（#1742：代替プロセスが生成される前に永続状態がディスクにフラッシュされる）。ホスト主導の再起動（dsh など、#991）は、その kill/spawn 順序が bili によって制御されないため、これらのデータレイヤーガードに依然として依存しています。

**セキュリティ姿勢：** 共有状態サーフェスは、管理エンドポイントのループバックゲート（非ループバックソースアドレスは拒否）およびユーザーのホームツリーのファイルシステム権限（両方のディレクトリは $HOME 配下にあります）によって*のみ*保護されています — セッション毎の認可はありません。**シングルユーザホスト**では、それで十分です。**マルチユーザホスト**では不十分です：プロキシのループバックポートに到達できるローカルアカウントは、すべてのユーザーのすべてのセッションを読み取ることができます。そのようなホストは、ホスト毎のストレージを分割する必要があります（ユーザー毎/レーン毎のサブディレクトリ）— #1724 で名付けられた根本修正（方向 #1）であり、まだアーキテクチャ決定としてオープンです；Web UI スコーピング（#1724 方向 #4）はインスタンス間ブラウジングを軽減しますが、この境界を変更しません。
## Runtime-info プロトコル (#955)

ネイティブプラグインはクライアントプロセス内で動作するため、クライアント自身が使用するモデル設定を読み取ることができます。この真実（truth）をプロキシに2つのチャネルでプッシュし、コンテキストウィンドウの解決チェーンにおいて、プロキシは models.dev レジストリや組み込みテーブルよりもこれを優先します：

| チャネル | タイミング | フィールド |
|---|---|---|
| リクエストごとのヘッダー（`x-bili-plugin` でゲート制御） | すべてのモデルリクエスト | `x-bili-plugin-context-window`, `x-bili-plugin-max-output`, `x-bili-plugin-model` |
| `POST /__bili/plugin/runtime-info` (loopback) | プラグインブートストラップ + 報告された設定の変更時 | `{agent, model, contextWindow?, maxOutput?, baseURL?, conversationId?, source}` |

ウィンドウの解決順序は以下の通りです：`anthropic-beta` のネゴシエーション > リクエストごとのプラグインヘッダー > runtime-info > ランチャー環境変数 > ルート設定 > models.dev レジストリ > 組み込みテーブル。runtime-info ステップでは、リクエストが `x-bili-plugin` ヘッダーを保持している場合、**エージェント単位のエントリ**を読み取ります（agent と model が一致する必要があります）。ヘッダーを持たないリクエストは、`conversationId` で記録された**会話スコープのエントリ**を解決します。このキーは、セッションがバインドするのと同じ会話シグナル（クライアントの会話ヘッダー、カスタムセッションヘッダー、またはボディ内の `prompt_cache_key`）に基づいています。いずれの場合も model は一致する必要があります（#1531: omp は `prompt_cache_key` をスタンプしますがプラグインヘッダーは付与せず、メイン/サブエージェントセッションは異なるモデルを動作させながら同じエージェント名を共有するため）。報告された `maxOutput` は、リクエストボディが独自の出力予算を保持していない場合のみ有効になります。実装：`src/agent/pi.ts`（pi と omp をカバー）、`src/agent/opencode-native.ts` (v1)、`src/agent/opencode-v2.ts`、`src/agent/dsh-native.ts`、`src/kimi/native-mcp.ts`（ブートストラップ時の報告のみ — kimi のプロバイダー `custom_headers` は静的であるため、モデル切り替え時にリクエストごとのヘッダーが古くなるため）、`hermes-plugin/__init__.py`（Python プラグイン：`llm_request` ミドルウェアによるリクエストごとのヘッダー、最大出力およびホストのモデル別コンテキストウィンドウ — hermes 自身の `HERMES_HOME/context_length_cache.yaml` から読み取り、ミス時は fail-open（#3261）— `pre_api_request` フックで捕捉）— 他のクライアント統合も同じプロトコルに従うべきです。

**DSH の `maxOutput` 報告は宣言にゲート制御されています — 宣言されていないカスタムモデルは、全体の上限チェーンを空にします（#2904）。** `src/agent/dsh-native.ts` は、ホストの `resolveModelInfo(provider, model)` が正の `defaultMaxTokens` を返す場合**のみ** `maxOutput` を転送し、DSH はモデルアイテムが明示的に `maxTokens` を宣言した場合**のみ**それを設定します — プロバイダーレベルの出力デフォルトは決して報告されません。宣言された `maxTokens` を持たないユーザー追加のカスタムモデルの場合、`defaultMaxTokens` は `undefined` となるため、両方の runtime-info チャネルが空になります。models.dev エントリがなく、bili 設定の `output` もない場合、4ソースの上限チェーン（#1840）は何も解決せず、`restoreOutputBudget` はクライアントで枯渇した予算をセッションのハイウォーターマークまで引き上げます — これは長いセッションでは、小さな正の値を経て汚染された低い値まで減衰しています。その結果、すべてのターンが推論のみで実行され、`length`/`max-tokens` で停止します。既知の上限を持つモデルに切り替えると、これが隠蔽されます（ハイウォーターは上限までフロアアップされるため）、したがって切り替えはトリガーであり、原因ではありません。真の修正箇所は **DSH 側**です：`undefined` ではなく、設定されたプロバイダー/モデルの出力デフォルトを報告すること（即座のユーザー回避策は、モデルアイテムに `maxTokens` を設定することです）。bili は意図的にクォータのフロアを推測しません（#1842）。代わりに #2904 は、`/acp` パネル、Web UI のセッションページ（データソース `/__bili/sessions/<id>/detail`）、および `/__bili/plugin/status?conversationId=`（`outputBudgetDegraded`）に、劣化状態を永続的に表示します — 健全な値または上限が到着すると自動的にクリアされます — さらに `degenerateTurnWarning` を `length`/最大出力終了に拡張し、ログ内で切り詰めがその原因と相関付けられるようにします。

**omp: OMP の Cowork トランスポートが出口を所有している場合、`prompt_cache_key` のスタンプは保留されます（#2583/#3556）。** ネイティブ omp モードでは、スタンプされた `prompt_cache_key` がリクエストごとのセッションシグナルの唯一であり、その唯一の消費者は bili 自身のフェッチレイヤーインターセプターです（モデル URL を `<proxy>/bili/<url>` に書き換え、転送前にフィールドを削除します）。最近の OMP ビルドには "Cowork transport" が同梱されています（2026-07-30 に導入、can1357/oh-my-pi `642892ae`；プロキシ処理 `e22a5ff2`）。これはデフォルトの `anthropic`/`anthropic-messages` リクエストを node:https を介して直接送信します — 明示的なプロキシ環境変数（`PI_PROXY` / `PI_PROXY_ANTHROPIC`）がそれらを Bun の fetch に戻さない限り、`globalThis.fetch` に触れることはありません。#3556 以降、`bili omp` ランチャーはこのギャップを自ら閉じます：ユーザーが `PI_PROXY` / `PI_PROXY_ANTHROPIC` を設定していない限り、`PI_PROXY_ANTHROPIC=<proxy origin>` をエクスポートするため、デフォルトのランチャーレーンでは Cowork が直接ダイヤルするのではなく、圧縮可能なレーン（スタンプされたキーがプロキシによって消費され削除される）に乗ります。この保留はまた、証明書 MITM レーンにもゲート制御します — #3556 はそれを宛先ルーティングチェックの上に持ち上げましたが、ネストされた配置ではそれが完全にスキップされていました。そこでスタンプすると、フィールドがそのまま Anthropic の厳格なスキーマに乗ることになります（HTTP 400 `prompt_cache_key: Extra inputs are not permitted`）。スタンプゲート（`src/agent/pi.ts` の `stampPromptCacheKey` → `ompCoworkTransportBypassesFetch`）は、OMP 自身のモデル別出口選択を反映しています：プロブンドirectなトラフィックはスタンプされず、プロセスごとにモデルごとに1回の大きな警告が出ます。結果として、これらの直接リクエストはプロキシに対して非圧縮かつ匿名で送信されます（ID/パネル/課金の劣化 — #1403 と同じトレードオフ）；他のすべてのレーン（ランチャー `/bili/` 書き換え、MITM ホワイトリスト、他のプロバイダー/API、プロキシ設定ホスト）は変更ありません。既知の残存問題：モデルホストに一致する `NO_PROXY`/`no_proxy` ルールは、`PI_PROXY` / `PI_PROXY_ANTHROPIC` が設定されていても OMP のプロキシ処理を無効にします — その場合、リクエストはスタンプされたまま直接ダイヤルします（同じ 400 クラス）；代わりにそのようなホストを `NO_PROXY` から削除してください。逆の非対称性は fail-safe です：OMP の形状ベースのフェッチフォールバック（Request オブジェクト入力、非レコードヘッダー、非サポートボディ）は、プロキシ環境変数がなくても `globalThis.fetch` にルーティングされ、そこで保留されたスタンプは ID を劣化させるだけで、ハードフェールすることは決してありません。完全なカバレッジにはホスト側の変更（Cowork の出口を `globalThis.fetch` 経由にルーティングする）が必要です — #2583 の境界注記を参照。

ランチャー環境変数ティアは、純粋なプロキシクライアント（インプロセスプラグインなし）をカバーします：
`bili <client>` は起動時にクライアント自身のモデル設定を読み取り（codex の場合は `model_context_window` / `model_max_output_tokens`、pi / omp の場合は `contextWindow` / `maxTokens`、opencode の場合は `limit.context` / `limit.output`、codebuddy の場合は `maxInputTokens` / `maxOutputTokens`）、`BILI_LAUNCHER_MODEL_WINDOWS` / `BILI_LAUNCHER_MODEL_MAX_OUTPUTS` を介してプロキシに引き渡します（#971）。プラグイン報告が存在する場合、常にこれよりも優先されます。

最初のモデルリクエストの前にセッションはまだ存在しないため、`/acp` パネルは `GET /__bili/plugin/status?conversationId=<agent>&fallback=latest` をプローブし、404 ではなくランタイムテーブル（`phase: "pre-first-request"`）から応答します — 報告された設定はすぐに可視化され、トラフィックが着地すると実際のセッションが引き継ぎます。

## Claude ネイティブ姿勢 (#964)

Claude Code にはインプロセスの拡張ポイントがないため、`bili plugin install claude` は `~/.claude/settings.json` に管理ブロックを書き込みます（環境変数 `ANTHROPIC_BASE_URL=http://127.0.0.1:<port>/bili/<upstream>`、`DISABLE_AUTO_COMPACT=1`、および `SessionStart` フック）、さらに以前と同じユーザースコープの MCP シェルを追加します。フック（claude の最初のモデルリクエストの前に発火）は、すべてのレーンと同様にポートを解決します（#1660）：明示的なピン（`BILI_CLAUDE_NATIVE_PORT` > 設定 `claude.nativePort`）は、その正確なポートで**strict-port** を起動します（占有者は明確に拒否され、#964 が保持されます）；それ以外の場合は、自己管理ゾーンに乗ります — レーンのスティッキーレコード、なければベース `18787` — 非 strict で、子プロセスの EADDRINUSE +1 ラダーが競合を解決し、決定したポートがスティッキーとして記録されます。ラダーに対する1つの例外（#1723）：レーンのポートの保持者が、**異なるビルド**を実行している同じレーンのインスタンスである場合（アップグレード再起動の重複 — 旧バージョンがまだドレイン中）、子プロセスはそれが解放されるのを待ち（最大5秒）、ドリフトする代わりに*同じ*ポートを再バインドします；決して離れない保持者は待機を使い切り、以前と同様に通常のラダーを取得します。プロキシが起動した後、フックは各セッションで管理対象の `ANTHROPIC_BASE_URL` をライブオリジンに再ピンします（`repinClaudeManagedBaseUrl`）、そのためポートがホップしても次の起動時に自己修復され、焼き込まれた URL が実行中のプロキシからデシンクしたままになることはありません。アップストリームオーバーライド：`BILI_CLAUDE_UPSTREAM`（または既存の `claude.anthropicBaseUrl` 設定）。インストールはもはや `claude.nativePort` を永続化しません。`BILI_NATIVE_CLAUDE=0` でオプトアウトできます — その場合、フックは同じ解決ポートで**passthrough** プロキシを起動します（そのまま転送、圧縮オフ）ため、claude は引き続き動作します。ブロックは純粋な JSON マージ/ストリップです：外部キーは決して触れられず、`bili plugin remove claude` は正確に復元します。ネイティブブロックがインストールされたマシンでも `bili claude` は引き続き動作します — それは静的な URL を自身のプロキシでオーバーライドし、フックは休眠状態のままです。
## 注入優先順位 — 避ける限りファイルは使用しない (#535)

bili はユーザーデータを所有しません。起動されたクライアントはすべて**実際のホームディレクトリ**で実行されるため、ランタイムの書き込みはユーザーが期待する場所に保存されます。クライアントをプロキシに向ける際、ランチャーは優先順位に基づいて選択します。**まず環境変数**（hermes/dsh/codex 用のプロキシ/CA 環境変数、pi/omp 用の `BILI_PROVIDER_REWRITES` URL マニフェスト。これはロード時にそれらの拡張機能の `registerProvider` によって消費されます）、次に**CLI フラグまたは拡張機能 API**（codex の `-c key=value`、opencode プラグイン）、そして**最後に生成ファイル**です。現在、生成ファイルとして使用されているのは opencode の一時 `opencode.json`（終了時に削除される）と dsh のループバック例外のみです。dsh のフェッチスタックはループバックターゲットに対してプロキシ環境変数を無条件にバイパスするため、ローカルアップストリームは、dsh が設定パスの環境変数やアップストリームループバックのオプトアウト機能を獲得するまで、永続的な `~/.dsh-bili` オーバーレイ書き換えを維持します。旧バージョンによって作成されたオーバーレイディレクトリはそのまま放置され、実際のホームディレクトリにマージされることはありません。

## 2つの圧縮モード — `compress` を実行するのは誰か

プロキシは2つのモードのいずれかで動作し、**モードが `compress` の実行者を決定し、それが要約がモデルにどのように伝達されるか（「キャリア」）を決定します**。この区別は #377 の根本原因です。

| | **ランチャー / プラグインモード** (`bili pi`, `bili codex`, …) | **プロキシモード** (プレーンクライアント → `/bili/`) |
|---|---|---|
| クライアント | bili 拡張機能を備えた ACP ネイティブエージェント (pi/omp) | 拡張機能なしの任意の OpenAI/Anthropic クライアント |
| `compress` の実行者 | **エージェント** (pi はローカルで実行) | **プロキシ** (サーバーサイドの圧縮ループ) |
| 再送信履歴内の `compress` ツールコール? | はい — エージェント自身の会話の一部 | いいえ — 一時的なプロキシループのトラフィック |
| プリフライトブロック (ツールコールなし)? | 最終手段のバックストップ — エージェントは通常、自身の `compress` コールで圧縮しますが、入力単体でウィンドウを超える場合 (#470) には両モードで `src/preflight.ts` が発火します | はい — `src/preflight.ts` がクライアントの背後で圧縮を実行 |
| **ワイヤー上の要約キャリア** | **`compress` ツールコール** | **`acp_summary` ユーザーメッセージ** |
| ワイヤー上のシステムメッセージ | 常にちょうど1つ (クライアント + プロンプト) | 常にちょうど1つ (クライアント + プロンプト) — 要約はユーザーメッセージに乗る |
| SGLang "単一システム" 400 (#377) | 発生しない | 発生しない (要約はユーザーメッセージであり、システムではない) |
| プロキシが注入する `compress` ツール | なし — エージェントは4つの ACP ツールをネイティブに登録 | 4つのコンテキストツール (有効化されている場合) |
| プロキシが注入するナッジ | **はい** — エージェントには独自のナッジチャネルがないため、プロキシ側のナッジが能動的な圧縮トリガーになります (プリフライト単体ではハードリミットでのみ発火; #451) | はい (有効化されている場合) |

**キャリアが異なる理由。** プラグインモードでは、エージェントが圧縮を所有します。`compress` コールとその結果はエージェント自身の履歴に存在し、ターンごとに再送信されるため、要約はツールコールに乗ります。これにより、エージェントのビューはカーネルの `acp_summary` フォールバックをレンダリングしません (`billion-context-pi` の `src/messages.ts` は `acp_summary_*` をスキップします)。プロキシモードでは、クライアントは ACP ネイティブではないため、プロキシがサーバーサイドで `compress` を実行します。ツールコールはクライアントの履歴に入らず、プリフライトブロックにはツールコール自体が存在しないため、カーネルの `acp_summary` メッセージが唯一のキャリアとなります。カーネルはこれをロール `system` としてレンダリングしますが、厳格な OpenAI 互換バックエンド (SGLang) はインデックス 0 にちょうど1つのシステムメッセージを要求するため、`systemToUser` (`src/util.ts`) がこれを `user` メッセージとして再表現し、アンカー位置に留めます。これにより、ヘッドのシステムメッセージ (プレフィックスキャッシュのアンカー) が圧縮ターン間でバイト単位で安定し、新しいブロックが会話全体のプレフィックスを無効化することがなくなります。

**なぜ `user` であり、`system` や偽造ツールコールではないのか。** ストリーム中の `system` メッセージは SGLang が拒否するものです (#377)。偽造された `compress` ツールコールは「純粋な」キャリアですが、プロキシモードでは ID によってアシスタントの `tool_calls` と `user` の `tool_result` のペアを捏造し、リクエスト内でツールを宣言し、本物のコールを持たないプリフライトブロックを処理する必要があり、単独のノートを再表現するよりもはるかに侵入的です。`user` メッセージは会話のどこにでも許可されるため、SGLang の単一システムルールとプレフィックスキャッシュの安定性を両立させるための最小限の変更です。受け入れられたトレードオフ: 要約は折り畳まれた履歴の代わりであり、それをユーザーターンとして再表現することは意味論的な不一致ですが、モデルはこれを許容します (明確に `[Compressed conversation section]` とマークされています)。

**2つのモードは共存できるか？**

- **同じプロキシインスタンス: はい、設計上可能です。** 1つのプロキシがプラグインクライアントとプレーンクライアントを同時に処理します。`pluginMode` はリクエストごとに決定され (`x-bili-plugin` ヘッダー)、セッションごとにバインドされます (`session.metadata.pluginAgent`)。ランチャーは実行中のプロキシを再利用します。
- **同じセッション: モードはスティッキーです。** プラグインモードで作成されたセッションはプラグインモードのままです (メタデータ継承)。プレーンセッションは、一致する会話 ID を持つプラグインリクエストが届いた場合のみ、プラグインモードに*アップグレード*できます (ヘッダーが優先されます) — ダウングレードされることはありません。実際には、プレーン→プラグインのアップグレードには、プラグインクライアントの会話 ID が既存のプレーンセッション ID と一致する必要がありますが、これは発生しません (各クライアントは独自の ID を生成するため)。
- **モード間ブロックの危険性: 理論上のみです。** 同じ会話 ID がモード切り替えにまたがる必要があります。プラグイン→プロキシは安全です (ツールコールは共有履歴にあります)。プロキシ→プラグインでは、プロキシが作成したブロック要約が孤立する可能性があります (そのツールコールはエージェントの履歴に存在せず、エージェントのビューは `acp_summary` をスキップするため) — しかし、上記の ID 一致が必要であり、それは発生しません。

**圧縮が実際に実行されたことの検証。** `compress` を実行した後、プロキシは確認マーカー (`📦 [ACP] Compressed …`) をプレーインのアシスタントテキストとして出力します — しかし、持続的なコンテキスト圧力下では、モデルがツールを一度も呼び出さずに*そのマーカー形式を自分で書き込む*ことが観察されました (#717): 実際の使用率が 89% に上昇する間、約2時間で17回の偽の「圧縮」がありました。したがって、トランスクリプトに表示されるマーカー行は永続性の証明ではありません — 信頼する前に `acp_status` (ブロック数の増加、圧縮可能範囲の開始位置の前進) で検証してください。バックストップとして、プロキシはモデルが独自に出力するマーカー形状の行を除去し、`[marker-echo]` 警告をログに記録します。また、ナッジと注入されたプロンプトの両方が、マーカーはプロキシのみが出力するものであることを明示的に述べています。
### モード切替は Responses 投影を変更する — 帰属はホストを責めてはならない (#2867)

Responses レーンでは、2 つのモードは履歴中間の `system`/`developer` アイテムを異なる方法で投影する: プラグインモードはそれらをその場で保持する (`__bili_inplace_sysdev`, #1638 のプレフィックスキャッシュ変動修正) — #3227 以降、ネイティブプロキシモードの Codex クライアントも同様である (`isCodexClient` による UA 検出); その他のプロキシクライアントは、先頭の developer ブロックへのホイスティングを維持する (#1085 のホイスティングとアンカリング)。したがって、セルフヒールによるプロキシへのデグレード (#2155) は、**同一**の受信履歴を異なる転送バイトに再投影する — ホストが何も変更していないにもかかわらず、転送システムフィンガープリント (#2350) が反転し、素朴な台帳はそれを「ホストがシステムプロンプトを書き換えた」として計上してしまう。
修正: 台帳は現在、投影フィンガープリント (`systemFp`) を、生受信 system/developer ストリームのモード非依存の**正規化**フィンガープリント (`canonicalSysFp`, ロール + コンテンツ + 順序、投影前のキャプチャ) とペアリングする。決済時: 投影が反転し正規化が安定 → 原因は `projection` (独自の次元: `pf` フラグ、`projSwitches` カウンター、コールドウィンドウ、レポートセクション — プロキシ自身の所为); 正規化も変更 → 原因は `prompt` (ホスト側の真の書き換え、#2350 の意図どおり); 正規化のみ変更 (例: プラグインモード中の履歴中間編集、これは先頭ブロックには触れない) は、請求バケットなしで観測的に記録される (`cf`)。不明な正規化側は分類されない (レガシー読み取り)。各サンプルはさらにそのモード (`pm`) を保持し、prepare-responses は理由 (セルフヒールデグレード / リストア / ヘッダー欠如) を伴う 1 行の遷移ログを出力する。記録されるのはハッシュ、長さ、モード、理由のみであり、プロンプト本体は決して記録されない。ワイヤ上の挙動は変更されていない: 両方の投影は以前と全く同じままである; 切替は誤帰属されるのではなく、*記録*されるようになった。

## `/bili/` チャネルは直接アドレス可能 — ホストフックがミスした場合のフォールバック (#5907)

ネイティブレーンの引き継ぎは、ホストプロセス内の `globalThis.fetch` をパッチし、モデル URL を `{proxy}/bili/{original-URL}` に書き換えることで機能する。そのパッチがカバーするのは正確に 1 つのこと: 現在のグローバル fetch を通じた呼び出しである。プラグインインストール前に fetch リファレンスをキャプチャしたモデルクライアント、非 fetch トランスポート (undici ディスパッチャー、生 http、WebSocket) を使用するクライアント、または別の JS レalm またはプロセスでターンを実行するクライアントは、パッチを完全にバイパスする — そしてバイパスは**構造上**不可視である: リクエストはプロキシに到達しないため、そのターンについて bili.log に何も表示されない (セッションなし、転送なし、ゲート拒否なし)。サードパーティによる代入ベースの置換は異なり、**無音ではない**: #1158 以降、ガード付きアクセサはすべての外部インストールをログに記録し、それを下流として再チェーンする (16 回を超えるインストールはログ上限; ルーティング権限は決してガードを離れない)。ホストプロパティが非設定可能である場合、または `BILI_RECLAIM_FETCH_PATCH=0` の場合、代わりにクラシックな直接インストールが適用される — その姿勢は現在、リスクと `/bili/` の救済策を名指しする 1 回限りの警告をログに記録する (#5907)。

`/bili/{absolute-upstream-URL}` は単なる URL プレフィックスであるため、ベース URL を制御できる**任意**のクライアントが直接それを使用できる — フックは不要である。プロバイダの `baseURL` を `http://<proxy-host>:<port>/bili/<upstream-base>` に設定することは、リモートエージェントのサポートされる形状 (configuration.md, `host`) であり、レーンのフックが明らかにターンをミスした場合の推奨フォールバックである: 圧縮、請求、ゲート拒否、ログ記録はすべて同一に適用される。なぜなら、それはフックが書き換えるのと同じチャネルだからである。注意: 直接クライアントはプラグイン帰属ヘッダーを持たないため、そのセッションは匿名 (`pfa-*`) チェーンに配置され、帰属のないトラフィックと同様にウィンドウ解決ラダーによってサイズ決定される (#5907)。

## Responses ネイティブチェーンリングはサポートされていない — 履歴は再生されなければならない (#1954)

Responses ワイヤアダプタ (`src/server.ts` の `prepareResponses`、`src/loop/adapter-responses.ts` の `buildRequest`) は**ステートレスな再生圧縮器**である: それは `parsed.input` を*完全な*会話として扱い、それを圧縮し、その後 `ACP_KEEP_RESPONSE_ID=1` がない限り `previous_response_id` を破棄する。レスポンス系譜ストアを保持しないため、ネイティブチェーンリング継続が参照する履歴を**マテリアライズできない**。

OpenAI のネイティブチェーンリング (`store:true` + `previous_response_id`、サーバー保持履歴) と bili のクライアント再生モデルは、相互に排他的なパラダイムである。したがって、デルタのみの継続 (新しいターン + `previous_response_id` のみ、完全な再生なし) は、**参照も参照されたターンも**上流に到達する — 以前のコンテキストは上流で静かに失われるが、リクエストは依然として 200 を返す。それが #1954 の背後にあるメカニズムである。

**ここで出荷されるもの (アプローチ A — 可視性のみ)。** 空でない `previous_response_id` が除去された場合、両方のパスは現在、その id を名指しし、結果を述べる `warn` を出力する。トリガーは明示的な `store:true` ではなく、id **単独**に基づいている。なぜなら Responses はデフォルトでレスポンスを保存するため、`store` が省略されていても参照されたレスポンスは上流で解決可能であり、`store` で判断すると一般的なケースを見逃すからである。アプローチ A は転送バイトを変更せず、何も閉じない: デルタリクエストは依然として履歴を失い、依然として 200 を返す。それは単に、損失が無音であるのを止めるだけである。

**観察であり、証明ではない。** 現在のビルド/テストでは、codex は `store:false` を送信し、`previous_response_id` を決して設定しないため、これは codex にとって*今日*は何もしない (no-op) である。それは既存の E2E + トラフィックからの観察であり、クライアントが決してチェーンリングしないことの証明ではない — E2E はデルタチェーンリングの形状をカバーしていない。codex はネイティブでチェーンリングをサポートする Responses API に対する OpenAI 自身の CLI であるため、トークンを節約するためにネイティブ継続に切り替える将来のバージョンは合理的な進化である; それまでこれは潜在的な高重大度ギャップのまま留まる。

**今日のチェーンリングクライアントのための安全なオプション:** 完全な入力/出力履歴を再送信する (bili は通常通り圧縮/転送する)、または id を保持するために `ACP_KEEP_RESPONSE_ID=1` を設定する — しかし KEEP の下では、参照された履歴はサーバー側に存在し、bili の圧縮/プレフィックスキャッシュ会計はそれを見ることができない。真の修正 (圧縮前に系譜をマテリアライズする) は機能 #1973 として追跡されている。公式移行ガイド: https://developers.openai.com/api/docs/guides/migrate-to-responses
## シングルライター: どのコピーを誰が所有するか (#991)

マシン上の各 bili の存在には、ちょうど **1 つのライター**（書き手）しか存在しません。インストールしたものが更新も行うものであり、他の何ものもそのコピーをインプレースで上書きすることはありません:

| レーン | コピーの保存場所 | 更新元 |
|------|---------------|------------|
| グローバル `bili` | npm グローバル (`npm i -g billion-context`) | `bili update` / バックグラウンド自動更新 |
| **pi** | pi のパッケージマネージャー (npm 形式) | **`pi update`** — bili は決して上書きしません |
| **opencode** | opencode のプラグインディレクトリ | **opencode のプラグインマネージャー** — bili は決して上書きしません |
| **dsh** | 各プロファイルの pnpm ストア | 定期チェックにより、プロファイルごとに dsh のプラグインチャネルが再実行されます — グローバルの bili 自己更新によって駆動される **または**、グローバルが実行されていない場合はプロファイルコピー自身のプロキシによって駆動されます (dsh-market インストール, #1196); 手動: `dsh plugin add billion-context@latest`. pnpm のハードリンクストアは決してインプレースでコピー上書きされてはなりません |
| omp / claude / codex / kimi / zcode | コピーなし — エントリはグローバルの bili インストールを指す | グローバルコピーとともに更新される |
| **hermes** | `~/.hermes/plugins/billion-context/` (コピーされたファイル + グローバル dist を指す `bili.json` サイドカー) | **`bili plugin update hermes`** がファイルを再コピーする; サイドカーはグローバルインストールを追跡する |

これは単なる慣習ではなく、コードで強制されています: 自己更新プログラム (`src/update.ts` → `hostManagedInstall`) は、pnpm 仮想ストア (`.pnpm`) またはホストエージェントツリー (pi / opencode / dsh / kimi / omp のホーム) 配下のインストールディレクトリを検出し、それらを **スキップ** します; `installViaTarball` は構造的にそれらを拒否するため、直接の呼び出し元がストアを破損させることもできません。*コマンド* の混在は問題ありません (`dsh plugin add` ≡ `bili plugin install dsh` — 同じチャネル、同じレコード); ガードが禁止しているのは *ライター* の混在です。`bili plugin update [client]` は、各レーンをその所有者を通じて駆動し、レーンごとの更新パスを表示する唯一のコマンドです (`bili plugin list` は同じレーンごとのチャネルを表示します)。

## ストックセッションの自己修復 — 検出定数と対策 (#2155)

3 つの障害形態は、`src/session-self-heal.ts` 内の 1 つの検出器ファミリーを共有し、リクエストごとに 1 回評価されます (`prepare` の後、ナッジを運ぶレーンのみ; バイパスおよびサイドレーンは決してクレジットを得ません):

- **D2 ゾンビプラグインレーン** — プラグインがアンインストールされた (またはその MCP 子プロセスが死んだ) にもかかわらず、すでに開かれているクライアントウィンドウがセッションをプラグインバインド状態に保っている場合 (スティッキーな `metadata.pluginAgent`, `src/server.ts`)。シグナル: 5 連続のラウンド (`SELF_HEAL_WINDOW`) がナッジされ、`x-bili-plugin` ヘッダーを **持たず**、ワイヤー上で bili ツールを **宣言せず**、圧縮削減を **生み出さなかった** こと。対策: **プロキシモードへデグレード** — 単一の `pluginMode` フリップ (`pluginAgent !== undefined && !pluginLaneDegraded(session)`) が ACP ツールのワイヤー側注入を再実行し、コンプレッションリライター、CCR スタンピングおよび吸収を再アームし、**ナッジを保持** します (ツールが戻ってくるため)。ワイヤー注入が利用できない場合 (`compress.injectTool=false` → `degradeAvailable` が false)、対策は **ナッジ抑制** にフォールバックします。回復: ライブなプラグインヘッダー (`pluginLaneRestore`, `pluginMode` フリップの前にホイスティングされるため、最初のヘッダー付きリクエストはすでにプラグインモードである — スティッキーな `pluginAgent` を回復シグナルとして使用してはならず、そうするとデグレードがアームされた 1 ラウンド後にクリアされてしまう)。バインドは保持され、決して消去されません。
- **D1 ナッジアイドル** (非プラグインの一般化) — 5 連続のナッジされたラウンドで、削減がゼロかつ bili ツール使用がゼロであること。「ナッジされた」とは、テキストが実際に注入されたことを意味します — #3004 以降、デシードゲートの判定が配信の事実です (`prepared.nudgeOutcome === "injected"`); 否決されたアームはアイドルストリークにクレジットを与えません (ゲート前の式は、モデルが受信しなかったチャネルで抑制をアームしていました)。対策: 4 つすべての `willInjectNudge` ゲートでナッジを抑制します (`&& !nudgeSuppressed(session)`、緊急パスもカバー)。2 つの境界が、抑制が永久にラッチされるのを防ぎます (#3004): デシードラダーのフォールバックエスケープは、抑制中でも 1 つのレガシーアドバイスを突き抜けて実行します (障害回復パスは抑制より優先順位が高く、`consumeFallback` がカウンターをリセットする)、そしてラッチはアームから `SELF_HEAL_SUPPRESS_CAP_MS` (10 分) のウォールクロック後に期限切れになります — その後再アームするには、新しい完全な `SELF_HEAL_WINDOW` のアイドルラウンドのコストがかかります。回復: いかなる圧縮削減または bili ツール使用でも、抑制を早期に解除します。
- **D3 ゲートウェイ殺害されたサマリー** — HTTP 524/504 (Cloudflare クラス) で死んだ **非ストリーミング** のプリフライトサマリーは、インプレースで再試行されません (古い一時的な再試行パスは、死んだゲートウェイに対して試行ごとに約 100 秒を消費していました); 代わりに、セッションは **最初の** ヒット時に `metadata.preflightStreamSummary = true` を学習し、サマリーは SSE として再要求されます — 手動の `compress.streamSummary` ノブ (#2133) と同じ学習ストアで、自動アームされます。カスケードは両方向で尊重されます: どこでも明示的な `streamSummary: false` (グローバル → プロバイダー → モデル) はオペレーターのオプトアウトであり、どちらの学習パスもアームせず、古い学習フラグは無視されます (`PreflightDeps` 内の `streamSummaryOff`)。

観測可能性: `session.metadata.selfHeal = { detected, action, since }` は `/__bili/sessions` で公開され、Web UI でバッジ表示され ("heal")、すべての遷移で 1 行の `[self-heal]` ログ (検出 + 回復) が出力されます。`bili plugin remove <client>` はベストエフォートでライブプロキシをクエリします (インスタンスファイル → `GET /__bili/sessions`、2.5 秒タイムアウト、失敗時はサイレント) であり、そのクライアントのセッションが直近 **10 分間** でアクティブだった場合に注記を表示します。
## 劣化ダイレクトフォールバック — 拒否、自己修復、アナウンス (#4516, #3304, #2924, #4079)

ネイティブレーンのプロキシが利用できない場合、モデルトラフィックはダイレクト送信 (`directSendOrRefuse`, `src/agent/native-intercept.ts`) にフォールバックします。このパスは劣化モードであり、すべてのレーンで共有される3つの契約があります（ゲートレスレーン pi/omp/opencode-V1 は #4516 以前これらを持っていませんでした — 1.06M トークンの生履歴がそのままプロバイダーに送信されていました）:

- **サイズアーム** — いかなる劣化送信の前にも、ボディは dsh のゲートと同じ doom 計算 (`bodyProvablyOverWindow`) で価格付けされます。ステージ1は生バイトフロアとウィンドウの比較、ステージ2は構造的メディアバイトの除去です（#4111 の方向性: コアテキストが収まるメディア中心のボディは拒否されない）。基準は `MIN_ASSUMED_WINDOW_TOKENS` (1M, #4079 — 宣言されたウィンドウが誤って小さくなることがある) 未満のウィンドウを仮定しません。その帯域のボディはプリフライトに委ねられます。データ欠如（`x-bili-plugin-context-window` ヘッダーなし、ボディ読取不能）はダイレクト送信に対して OPEN に失敗します — ローカルガードは自身の無知によって誤ってブロックしてはなりません。判定: 422 `x-bili-gate: oversize-refusal-fallback`、リトライ可能、アップストリーム方言に従ったワイヤー形状、メッセージはフロア/コア/ウィンドウと利用不能理由 (`bootstrap-failed` vs `dead` — 後者はレーンがオリジンを持っていたが失った場合のみ) を示します。
- **自己修復** — ブートストラップ失敗はもはやプロセス生存期間中のダイレクト送信を意味しません。ライブオリジンが見つからない各リクエストは、15秒のクールダウンの下でオーナーの `respawn` を発火します（singleFlight — 並行リクエストは1回の試行を共有）。その後、`state.spawnWaitMs ?? readyTimeoutMs ?? 15_000` 以下のインフライト試行を待ちます: pi スパウンレーンは `SPAWN_BUDGET_MS + 10 s` を設定するため、遅いコールドスタート (#4515) は一般的な上限で拒否されるのではなく、待たれます。回復にはホスト再起動は不要です。
- **アナウンス** — 劣化状態への/からのすべての遷移は、リクエストごとに1行ではなく、bili.log に1行（プロキシ回復 / ダイレクト化 / 拒否）をログ出力します。`state.lastUnavailableReason` は拒否文言に WHY を保持するため、ユーザーは「まだ起動中」と「死んだ」を区別できます。

opencode V2 リゾルバーレーン (`createLiveOriginResolver`) は独自のプローブ駆動リトライを維持します。この契約は、それらがカバーしないプレーンインターセプトパスを対象とします。パネルへの帰属レポートは引き続き dsh のみです（#4516 参照）。

## 統一 ACP タグエコー是正 — 4つの不変条件 (#2023/#2066/#2190/#2248)

1つの PR が3つの是正脚（refs-run 残留 #2023、退化クローズ除去 + 出口監査ネット #2190、出力ドロップ + 署名付き思考の逐語 #2066）を、すべてのテキスト書き換えサーフェス（ループアダプター、プラグインパススルー、JSON 除去関数、終了監査）を支配する単一のハードルールセットの下に統合します:

1. **思考チャネルはバイト逐語です。** Anthropic `thinking`、Google `thought`、OpenAI `reasoning_content`/`reasoning`、および Responses 推論サマリーはそのまま乗ります — エコー形状の推論も含みます。根拠: 推論リプレイ（DeepSeek スタイル）と署名検証はこれらのバイトを検証します。書き換えはそれらをデシンクさせ、セッションを壊します (#1960/KDD#10)。アダプターはこれらのフィールドを `createIdentityStreamFilter` 経由でルーティングし、除去関数 (`stripOpenaiChatText`, `stripResponsesText`) はそれらを無変更のままにします（ディフェンシブインディプス）。注: これは #1881 以前の推論エコー除去を逆転します — 思考チャネルはもはやクリーニングされません。
2. **モデル散文は管理可能です。** レンダリングタグエコー、マーカー行、bili 内部テキスト、退化オープン/クローズ残留、および（吸収指示がある場合）ツールコール出力全体は、可視テキストチャネルからのみ除去されます。
3. **ファイル宛のモデル出力はバイト同一です (#1039)。** ツールコール引数は、どのようなバイトを持っていようとも、いかなるフィルターにも入らない。
4. **ユーザー送信バイトは決して書き換えられない。** ユーザー自身のフラグメントの逐語エコーは、除去が武装していても生存します (#463 免除、形状ではなくリクエストテキストにキーされる)。

出口監査ネット (#2248) はログのみのままです: 生出口（未認識フレーム、解析失敗）はそのまま転送され、`[tag-echo] raw exit` をログ出力することで、ワイヤーを変更せずに新しいリーク形状が可視化されます。`tests/unified-acp-invariants.test.ts` (8つのテスト、両レーン) で固定されています。

## キャッシュ台帳の累積はカバレッジ条件付き (#2202)

台帳は各リクエストを経過した各フォールドに対して記録します（サンプルごとに `requestsAfter += 1`）、パネルはそのカウンターを `netSaved = Σ (S − σ) × requestsAfter` に変換します。記録は*このリクエストがフォールドから利益を得たという主張*であり — これはフォールドのカバレッジバイトが実際に再送信ワイヤーに乗っている間のみ真です。ホストが bili の知識の外でそれらを削除した場合（dsh ネイティブコンパクト、#2193）、古いカウンターは破壊された基盤の上で上昇し続けました: #2193 インシデントでは、1510 のカバレッジ ID が永久に消えたにもかかわらず netSaved が 355M を示していました。

修正はライター側、主張サイトにあります: `reconcileFoldCoverage` はすでにこの証拠のためにすべての受信パスを検査するため、今後はブロックごとの存在を `session.metadata["foldCoverageByBlock"]` に記録します — ブロック ID ごとに `{p, r, t, e}`（逐語存在 / リアンカー経由で回収 / カバレッジ総量 / かつて存在したラッチ）。台帳は各フォールドをブロックにスパースな `LedgerFold.bid` でリンクします（`recordCacheFoldsFromBlocks` で一度だけ設定、イージープロキシパスとレイジープラグインモードパスの両方の唯一のチョークポイント）、そして測定された割合 `(p + r) / t` で増分をスケーリングします:

- **1** — 完全カバレッジ、または使用可能な記録なし → #2202 以前のカウンターとバイト同一（健全なセッションとすべてのレガシーエントリ）;
- **f** — 部分カバレッジ → 比例累積;
- **0** — カバレッジ喪失が検証済み → カバレッジが戻るまで累積凍結。

2つのクラスは `e` ラッチによって自己校正されます: カバレッジ ID が*かつて*存在として見られたフォールドは検証可能であり、完全な不在は喪失を意味します; 作成後に ID が*決して*出現しなかったフォールドは構造的に検証不可能です（生オリジナルではなくフォールドビューを再送信するビューフォールディングホスト）であり、静かにゼロにされるのではなく、現状維持の記録を維持します。カバレッジ喪失はライブ計算されます (`e === 1 && p + r === 0`)、そのためスティッキー状態なしで回復が累積を再開します; 1つの warn/info ログがフリップごとに発火します (`foldCoverageLostLogged` 重複排除キー)。

証拠衛生は #1195 ガードを反映します: サイドリクエスト形状のパス（受信メッセージ < 10 — タイトル生成、WebSearch 洗練）は証拠を一切取得しません（記録なし、バックボーンロールなし、ドリフトストリーク移動なし、リセットなし）。短いパスは次のパスの整列を歪め、幻の完全喪失を生み出すためです。

パネル表示は喪失したフォールドをヘッドライン数字から除外します: ウェブセッションビューでは、それらを個別のラベル付きセグメントとして表示します（行ツールチップ、概要サブ行、詳細統計） — 喪失前の凍結済み節約は可視のまま、喪失後の成長は停止します。
## OpenAI チャットワイヤの prompt_cache_key: デフォルトで全箇所にスタンプし、厳格なアップストリームを A/B プローブで保護する (#2218/#2645/#3556)

dsh プラグインレーンにおいて、ボディキーベースのリレーが読み取れる唯一のアイデンティティシグナルは、チャットボディ内の `prompt_cache_key` です（勝利する会話ヘッダー `x-bili-plugin-conversation` は bili 内部専用であり、その名前で外部に送信されることはなく、ヘッダー読み取り型リレーには `x-session-id` が渡されます）。そこで対立する2つの集団が出会います。**厳格な直接 API** は未知のボディパラメータを 400 で拒否します — 厳格さは同一オリジン内でモデル単位で異なります（#2645: 1つの NVIDIA ゲートウェイモデルはキーを受け入れ、その兄弟モデルは拒否する）— 一方、**アカウントプール**（リモートリレープールを含む）は、そのキーをプレフィックスキャッシュルーティングのシグナルとして読み取ります。そのため、どこかでキーを落としても、それらのセッションのキャッシュアフィニティが静かに劣化します（#1403 の逆パターン）。デスティネーション形状のテストでは裁定できません：ループバック専用のゲート（#2649 の試み）は厳格な API を修正しますが、最大の2つのプール集団（docker-bridge/LAN/VPS/ドメイン名プール）からキーを剥奪してしまいます。

決定された設計 = **デフォルトスタンプ + 実証的自己修復（プローブして記憶する）**：

- スタンプ（`src/session-id.ts` → `resolveRelayAffinityPck`）：内部会話ヘッダーが存在する場合 ⇒ すべてのデスティネーションに `<conversation id>` をスタンプ；クライアントが供給したキーは、そのペアがアブレーションされるまでそのまま通過し、その後保持されます（これにより、後のターンで 400 の往復コストを再支払わないようにします）。解析不能なオリジンは失敗オープン（スタンプ維持）になります。設定表面ゼロ — 新しいフィールド、環境変数、CLI フラグはありません。
- プローブ（`src/server/relay.ts`、#552 互換性ラダーと同じバッファードボディシーム）：キーを含むエグレスボディに対する**最初の** 400 で、`prompt_cache_key` を除いた同一ペイロードを一度だけ再送信します。リトライが受理された ⇒ 因果関係が証明された ⇒ プロセスメモリ（`src/pck-probe.ts`）に `origin(+model)` ペアを記憶 — メモリ内のみ、永続化なし、再起動で再プローブ。リトライも失敗した ⇒ このフィールドのせいではない ⇒ リトライを破棄し、元の 400 を無加工で転送し、何も学習しない（400 には多くの原因がある；A/B の裁定のみがアブレーションを許可する）。リクエストごとにプローブは1回のみ。
- 粒度：origin+model、#2645 で測定された厳格さを反映 — 共有プールオリジン上の1つの厳格モデルは、兄弟モデルのスタンプを維持します。
- 可視性（オーナー要件）：初回アブレーション時に、origin/model、影響を受けるセッション、およびアカウントプールの注意を明示的に示す WARN ログを出力（「このデスティネーションがあなたのリレー/アカウントプールである場合、そのプレフィックスキャッシュアフィニティは劣化する可能性があります」）；`acp_status` は現在の抑制リストをセクションとして保持；Web パネルにはセッション付きのバナー（zh/en）を表示；スクリプトは `GET /__bili/status` から `pckSuppressions` を読み取ります。すべてプロセスローカル；再起動でクリアされ、再プローブされます。
- モード：プラグインレーン（登録エージェント / dsh プラグイン、内部会話ヘッダー存在）のみがスタンプします；プレーンプロキシモードは双方向とも純粋なパススルーであり、バイト単位で不変です。

テスト：`tests/issue2645-pck-probe.test.ts`（厳格アップストリームのターン1自己修復、ターン2記憶、寛容プールのプローブなし、汚染アップストリームの 400 転送と学習なし、クライアント所有キーのアブレーション後ドロップ、モデル粒度ペア）+ `tests/issue2218-relay-affinity-signal.test.ts` の書き換え済みマトリクス。

### #5079: ポリシー反転 — 自己スタンプはデフォルトで OFF、1つのノブがすべてのワイヤを制御

オーナー裁定（#2649 のデフォルトスタンプ裁定を差し替え）：このフィールドを含むリクエストを即座に拒否するサービスが**多数**存在し、その集団を事前に列挙することはできない — したがって、要求されない限り bili は独自の `prompt_cache_key` を書き込みません。ゲートは既存の `promptCache.routing` ノブ（`ACP_PROMPT_CACHE_ROUTING`、または Web UI のクイック設定スイッチ）であり、今や両方のワイヤにおける bili 自身の出力を同時に制御します — 新しい設定表面はありません：

- `"disabled"`（**新しいデフォルト**；認識されないものはすべてここで解析）：bili はどこにも独自のキーを書き込みません。このゲートはクライアント供給キーには影響しません — すべてのモードでそのまま転送されます（上記の A/B プローブ&リメンバーは、origin+model ペアが拒否することが証明されたクライアントキーを依然として保持します）。
- `"auto"`：#5079 以前の動作と完全に一致 — チャットワイヤはプラグインレーンのすべてのリクエストにスタンプし、Responses ワイヤは `api.openai.com` のみで注入します。
- `"enabled"`：サポートするすべてのレーンでスタンプ/注入（Responses ワイヤ：任意のホスト）。

チャットワイヤにおける Bili 所有 vs クライアント所有：プラグインレーンにおいて、バインドされた会話 ID と等しいボディキーは、bili 自身の機構のエコーである可能性があります（クライアントキーが勝利するためのアイデンティティ昇格には、内部会話ヘッダーの不在が必要であるため）、したがって `"disabled"` 下では bili 自身の出力としてカウントされ、剥奪されます；その他の値はクライアント所有として残され、転送されます。Responses ワイヤのミラー：昇格していないアイデンティティ下でセッション ID と等しい明示的なボディキーは bili 所有です（omp/dsh 拡張がスタンプする）；昇格アイデンティティはクライアントが供給したことを意味します。

アップグレード通知（オーナー要件）：`"disabled"` で実行中のインスタンスには、1回限りの通知が表示されます — Web パネルのバナー（閉じ可能、状態ディレクトリの `upgrade-notices.json` にインスタンスごとに永続化）、`acp_status` の行、起動ログ行 — 戻すべき集団（`"auto"`/`"enabled"`）を特定します：workbuddy パネル/ハブなどのリレーや、キーなしでトラフィックがランダムにルーティングされるとプレフィックスキャッシュアフィニティが劣化するアカウントプール。公式 API の直接ユーザーは無視できます。閉じる操作はルーティング値を変更しません。

テスト：`tests/issue5079-pck-default-off.test.ts`（解析フォールバック、両ワイヤマトリクス（bili 所有エコー行を含む）、通知モジュール、デフォルトオフ/auto ペアの実プロキシエグレスアサーション）+ `tests/issue2218-relay-affinity-signal.test.ts` の更新済みマトリクス。

## 未カバー履歴監査 — 正直な最小判定 (#4331)

「圧縮可能な範囲が残っていない — コンテキストはすでに最小です」という停止シグナルは、構造的に検証不可能でした：PRE-FOLD OFFER が枯渇したときに発火しましたが（`postCompressTail`、#2404 ピニング）、アクティブブロック範囲の和集合とセッションの参照セットを比較するものは何もありませんでした。ライブ ZCode セッションで、この失敗が大規模に示されました — アクティブブロックにない 138 個の中間履歴参照（約 65K トークン、コンテキストの約 16%）、最大の連続区間は `m00312`–`m00411`（100 メッセージ）、一方レシートは3回連続でグローバル最小を宣言していました。カーネルは、そのようなスパンが提供された場合に見つけることができます（master での再現により検証済み）；欠けていたのは、グローバルカバレッジ監査と、最小である場合のみ「最小」と主張する判定でした。

設計（`src/uncovered.ts`、ホストサイドのみ、カーネル変更なし）：

- `uncoveredHistoryRuns()`：メッセージ配列を走査し、すべてのアクティブブロックのカバレッジ外（`collectVisible` 述語）のエントリを見つけ、連続区間をグループ化し、各区間を分類します：現在のオファーが一部をカバーしている場合はスキップ（モデルは今すぐアクション可能）；そうでない場合は、`structuredClone(state)` に対して `core.processTurn` を2パス実行して差分を比較します — 通常設定 vs 緩和 `{preserveRecentMessages: 0, preserveRecentTokens: 0}` — 緩和パスでのみ提供された参照をゾーン非表示（保護された最近ウィンドウ内）とみなします。実証ゾーン差分は、カーネル自身の保護ゾーンルールを意図的に再利用し、コピーしないため、ルールが進化するにつれて自己維持されます（過大近似は過少報告に傾く）。`VIABLE_RANGE_MIN_TOKENS`（200）未満の区間は沈黙します。通常オファーパスをすでに実行した呼び出し元は、`normalRanges` を渡すことができます（配列 = 信頼して再利用、空でも可；undefined = 呼び出し元データなし、監査が自身のパスを実行）し、acp_status は `processTurn` を1回だけ追加で支払います。関数全体は助言的：任意の throw は「区間が見つからない」にデグレードし、レシートやステータスを壊しません。
- **acp_status** に追加的な `UNCOVERED HISTORY` セクション（トークン順トップ5区間、残りはカウント）を追加し、すべてのアクティブブロックの外側にあり、かつ上記のライブ Compressible-ranges リストにも存在しない質量を列挙します — カバーされたブロック間の孤立サブゲート区間（マージでは決して折りたたまれない、#4331 / #847 の恒久ホールクラス）を含む。可視性のために命名され、明示的に折りたたみ提案ではありません；行は `scope:"uncompressed"` で不変のままドリルダウンできます。
- **Tier-2 カバレッジ不変条件（レビュー済み、P4 でピニング）**：監査のカバレッジセットは `coveredMessageIds` = アクティブブロックの `effectiveMessageIds` の和集合（子再帰なし）（kernel/src/state.ts:57-64）。これは安全です。なぜなら、すべてのブロック作成パスは消費された子の `effectiveMessageIds` を新しい親に和集合し（kernel/src/unit-projection.ts:178-183）、子を非アクティブ化するためです（kernel/src/compress.ts:1578-1581）— T2/T3 の親は状態モデルに完全な蒸留スパンを持ち、ハイドレーションがそれを保持します（状態 JSON 全体）。DB サイドの `blocks.payload_json` 走査にはその性質がなく、`directBlockIds` 再帰が必要です（以前の独立試みがそれを保持した理由）；状態モデルには不要です。
- **postCompressTail**：クリーンな全オファー枯渇で階層蒸留がない場合、判定の前に監査を実行します。区間が見つかり、かつ合計が `UNCOVERED_RECEIPT_FLOOR_TOKENS`（10K、レシート専用）以上 → 正直なテキストでそれらを特定（「最小ではない」、acp_status へのポインタ）。フロア未満 — または区間なし — 場合、#1387 契約文字列がバイト安定で発火し、master と完全に一致します：小さな拒否残骸は、すべての折りたたみで再注意を促してはなりません（pi #521 ルール）、一方、実質的な漏れはそれを上書きします。フロアは acp_status セクションには意図的に適用されません：明示的な検査表面は注意を促す表面ではなく、#4331 のオプション1はそこにサイズゲートを指定していません。10K 合計は、オーナー承認待ちのプロダクト値です（レビュアーの独立した選択と一致）。

動作変更（開示済み）：旧 = オファー枯渇時の無条件「すでに最小です」；新 = グローバル監査が検証し、かつ未カバー質量が 10K レシートフロアをクリアした場合のみその主張 — フロア未満ではレシートは master とバイト同一（したがって `tests/compress-success-tail.test.ts` は master バイトのまま、差分ゼロ）、その #2404/#1387 フロア未満残骸フィクスチャはフロアのピニングとして機能します。サブゲート残骸は acp_status で可視化されました（以前はすべての表面で不可視）。設定/環境表面は追加されません；ナッジプロンプトテキストは不変（カーネル所有）。既知の制限は別の観察として残します：レシートの残り計算は、提出されたスパンが一部でも重複する場合、提供されたバッチ全体を削除するため、部分的に折りたたまれたマージバッチは過大報告ではなく過少報告する可能性があります。

テスト：`tests/issue4331-uncovered-history.test.ts`（ホールセッション → 正直な判定 + 特定スパン；排出済みセッション → 契約文字列；フロア未満沈黙；階層優先度；**Tier-2 蒸留カバレッジピニング** — 実際のホストパス経由で1つの T2 親に蒸留された3つの T1 は、子スパンを監査に漏らしてはならない；acp_status の両方向；フォーマッター上限）+ `tests/compress-success-tail.test.ts` は master から不変（その < 10K 残骸フィクスチャがフロアをピニング）、`tests/issue2029-status-baseline-provenance.test.ts`（すべてのステータスリーダーカーネル呼び出しがプロベナンスベースラインに供給）、`tests/issue847-compress-failure-guards.test.ts`（サブゲート残骸が診断で可視、依然として提供されない）。

## イベントループウェッジ自己終了と EADDRINUSE ホルダー診断 (#4762)

長時間実行のスタンドアロンプロキシ（v0.1.208 フィールドレポート：dsh-harness レーン、最後のログ行は 48 MiB セッションの折りたたみ調整再アンカー）は、リスニングソケットを**依然として保持しながら**メインイベントループを15分以上ブロックしました — HTTP は死に、ソケットは開いたまま。外部ハーネスの子プロセス（`BILI_LAUNCH_TOKEN` なし）は、設計上 EADDRINUSE で即座に失敗します（`src/listen-policy.ts`）、そのため約70秒ごとの再起動は、誰かがゾンビを手動で kill するまで `listen failed: EADDRINUSE … exiting before persist` で死に続けました。2つのギャップ：ウェッジしたプロキシにポートを譲らせるものは何もなかったこと、そして死のメッセージが「別のプロセス」を非難しながら、その他のリスナーが実際に**サービング**しているかをチェックしなかったこと — さらに悪いことに、間歇的に accept キューを排出するウェッジゾンビは、起動時のツインヘルスプローブを通過するため、そのインスタンスは何もサービングしていないのに、子プロセスは「サービング中のインスタンスがサービングを続ける」というヒントで終了しました。

設計：

- **ウォッチドッグ**（`src/event-loop-watchdog.ts`）：別々のワーカースレッドが時計を**所有**します — メインスレッドが永久にブロックされていても、ワーカー自身のイベントループは刻み続けます。これがすべてです。メインは `WATCHDOG_HEARTBEAT_MS`（5秒）ごとにハートビートを投稿します；ワーカーは5秒ごとにチェックします：ギャップ ≥ `WATCHDOG_SOFT_WARN_MS`（30秒） → 1回の法医学 WARN 行（uptime/RSS）；ギャップ ≥ `WATCHDOG_HARD_TIMEOUT_MS`（300秒） → bili.log + stderr に FATAL 行、その後 `process.exit(1)`（終了モード）。しきい値は設計上ハードコードされています（設定表面はオーナーゲート付き）：正当な大きな圧縮は数秒から数分で完了し、チャンク間でループを譲渡するため、**連続した**5分の沈黙はデッドロックのみです。`startServer` の**入口**でアームされます（ツインプローブ、エンジン/ストレージ初期化、ハイドレーションはすべてその下で実行 — ウェッジは起動中に到着し得る、#4762 自身の再現クラスは同期 I/O ホットスポット）— スタンドアロンプロセスのみ；プラグイン注入モードではアームされません（HOST プロセスを kill してしまうため）。法医学行は、ファイルレグが設定されている場合常に bili.log にルーティングされます；ワーカーの STDERR レグは、stderr が TTY であるか、ファイルレグが全くない場合にのみ出荷されます — 満杯で排出されていないパイプへのブロッキング書き込みはエラーイベントを発火しません（#5012 クラス）、したがってワーカーがその死んだパイプに FATAL 行を書き込むと、終了を発火させる代わりに**自分自身**がウェッジします；ゲートは構造的であり、防御的ではありません。ワーカーは unref されているため、セーフティネットがクリーンな自然なプロセス終了を人質に取ることができません。ワーカーはインライン `eval` コードとして実行されます。なぜなら `dist/index.js` は参照できる兄弟ファイルのない単一バンドルだからです；その唯一の import はガード付き `require("worker_threads")` です — `parentPort` グローバルは eval ワーカーには存在しません（ReferenceError、Node 22 で検証済み）。ワーカー生成失敗は、1つの warn で監視なしにデグレードし、起動を壊しません（可用性がガードレールより優先）。
- **ホルダー診断**（`src/port-owner.ts` + `src/server.ts` の両方の EADDRINUSE 死パス）：死の瞬間に、既存リスナーの `/__bili/health` を一度再プローブします（2秒予算；ワイルドカードバインドはループバックオリジン経由でプローブ — `holderProbeOrigin`）。応答あり → ヒントはピアがサービング中であり、スポナーがそれに取り付くべきと述べる；応答なし → ヒントはホルダーがウェッジまたは死んでいるように見え、具体的な解放を特定します：pid が既知の場合（レスポンダー pid が古いレジストリエントリに優先；同じレーンのレジストリ pid にフォールバック）、`taskkill /PID N`（Windows）/ `kill N`（POSIX）、それ以外の場合は `netstat/lsof`。`[eaddrinuse-diag]` としてログ出力され、`BILI_LAUNCH_TOKEN` が設定されている場合、スポーンポートログに書き込まれます（この子プロセスの stderr は bili.log にミュートされます、#2864）。両方のパスをカバーします：エンジン前の早期ツイン衝突終了と、バインド後の `server.on("error")` 終端ブランチ。
- **なぜ起動時の裁定を信頼するのではなく再プローブするのか：** 早期ツインチェック（`findVerifiedSameLaneTwin`）はバインドの数秒前に実行され、遅いパスの `classifySameLanePeer` はレジストリのみです（pid 生存、ヘルスチェックなし）。その間に発生するウェッジ — まさに #4762 の形状 — は両方の真実を反転させます。そして1つの浅いプローブでは、遅いが生存と、ウェッジだが排出中（ゾンビは一部のプローブに応答した）を区別できないため、文言は「ウェッジのように見える」と述べ、kill の決定をオペレーター/スポナーに委ね、それに基づいて行動しません。
- **スコープ外（文書化済み）：** 繰り返し EADDRINUSE 後の親側強制 kill は、このリポジトリではなく**スポナー**（DeepSeek Harness）に属します — 診断行は今や正確に何をすべきかを伝えます。

動作変更（開示済み）：旧 = ウェッジしたスタンドアロンプロキシはポートを保持したまま永遠に生き、すべての再起動は不透明な EADDRINUSE で死んだ；新 = メインループの連続沈黙 ≥ 5分 ⇒ 30秒で1つの warn、1つの FATAL ログ行、その後 `process.exit(1)` によりスポナーの通常の再起動がポートを回復し、すべての終端 EADDRINUSE メッセージにサービング/ウェッジ裁定 + kill ガイドが追加されます。新しい設定/環境/CLI 表面はありません — しきい値はモジュール定数です。プラグインモードの動作は不変（ウォッチドッグはそこにアームされません）。

テスト：`tests/event-loop-watchdog.test.ts`（裁定境界テーブル（warn-once 意味論を含む）；デフォルトピニング；**実ワーカー**ウェッジ統合 — 同期スピンがメインループをハードしきい値を超えてブロックし、トリップが発火し、両方の法医学行が `[v=…]` タグ付きでログファイルに到達；健全なストリームはトリップしない；生成失敗シームがクリーンにデグレード）+ `tests/port-owner.test.ts` 追加（ワイルドカードオリジン書き換え；サービング/ウェッジ/匿名ヒント文言；ライブレスポンダー pid が古いレジストリ pid に優先；死んだホルダーは非サービングとして読まれる；登録前「starting」は非サービングとして読まれる）。

## 依存関係監査 — zod アドバイザリ GHSA-mrhx-c7xc-m3w5 と jimp のネスト zod 誤検出 (#4820)

新規インストールの `npm audit` は、高重大度のアドバイザリ GHSA-mrhx-c7xc-m3w5（CVE-2023-54404、CVSS 7.5 High、**可用性/DoS のみ** — 機密性または完全性の影響なし）を、異なる処理が必要とされる2つの異なるチェーンに対して報告します：

- **直接 `zod`**（`package.json` `dependencies.zod`、KDD #1 による正確なピン）。真に影響を受けています：脆弱なコードは `v4/core/schemas.js` の `$ZodArray.handleArrayResult` にあり、制約なしの配列スキーマに対して過大配列を検証する際、要素ごとの検証問題を上限や早期終了なしに蓄積します。`4.1.8 → 4.6.7` に更新（パッチ済み行は 4.6.6 から始まり、`abortEarly` ゲートの早期 break と、4.1.8 にない `capSize` 登録を追加）。ピンは**正確**（範囲ではない）のままです。これにより npm は opencode ホストと1つの共有インスタンスにデデュプでき、KDD #1 の相互運用保証を維持し、`tests/opencode-native-v1.test.ts` でカバーされます。私たちのツリーでは、このコピーは `src/agent/opencode-native.ts`（OpenCode V1 プラグインツール、遅延不透明 import）のみによって消費されます；Pi/プロキシレーンでは読み込まれません。
- **Jimp のネスト `zod@3.x`**（`optionalDependencies.jimp`；各 `@jimp/*` は `zod ^3.23.8` を宣言するため、npm はすべての `node_modules/@jimp/*/node_modules/zod` 下に 3.x コピーをネストします）。これは**私たちの jimp 使用法に対する誤検出**であり、semver 範囲から仮定するのではなく、ソースレベルで確立されました：脆弱な関数は zod の v4 実装（`v4/core/schemas.js`）にのみ存在し、v3 には決してありません；3.25.x インストールでの `import "zod"` は v3 コアに解決されます；そして `@jimp/*` はプレーンな `"zod"` を import します（決して `zod/v4` を import しません）。したがって、jimp を通じてバグは到達不可能です。したがって、jimp の zod 3→4 を強制オーバーライドしません（パッチ済み 3.x に収束するものがないクロスメジャーオーバーライドで、jimp 自身の検証セマンティクスをリスクにさらす）；代わりにアップストリームを追跡します。到達可能性の制限は明示的に保たれます：jimp は任意であり、遅延読み込み（`src/image-rescale.ts`）、不在時はパススルーにデグレードし、画像処理中にのみ到達可能です。境界：3.25.x ターボール**内部**のバンドル v4 プレビュー自体が修正前です — 将来の `@jimp` が `zod/v4` を import する場合、この結論を再評価してください。

ハード CI/ランタイム監査ゲートは意図的に延期されています：jimp チェーンのために赤のままになるため、例外を追加しない限り、そして例外は狭くスコープされ、説明され、再訪問可能でなければなりません — 全面的な抑制ではありません。直接 zod の更新が着地し、アップストリーム jimp が追跡された時点で再検討してください。

## フルリサンダムウォーターマークファストパス (#5403 / #5418)

プラグインレーンホスト（dsh スレッドモデルと、すべてのリクエストで**完全な**履歴と新しいテールを再送信するクライアント）は、ターンごとに、完全なボディの `JSON.parse`、完全な `openaiToCore` 変換、および結果 AST の `session.lastMessages`（`snapshotMessages`）へのターン間ピンを支払いしていました。#5403 の規模（20k メッセージ、ターンあたり約 81 MiB 受信）では、そのペアが2時間で6回 JavaScript ヒープを上限を超えさせました。

レーンは今やウォーターマークを保持します。すべての成功したプラグインレーンチャットコンプリートレスポンスは、そのリクエストの `messages` 配列のサーバー測定要素数 T を `x-bili-pf-seq` にスタンプします。T は `src/server/fastpath-scan.ts` によって測定されます。これは単一パス構造スキャナ（文字列状態機械を持つ文字列ウォーク）です：信頼できるほど十分な JSON を検証しながら、スパンオフセットのみを割り当てます — AST なし、完全な解析なし。クライアントサイドは1つの状態機械（`src/agent/pf-channel.ts`）で、1つのチョークポイントで給水されます：`src/agent/native-intercept.ts` の `globalThis.fetch` インターセプトは、すべてのプラグインレーンモデルリクエストに `x-bili-pf-count`（および以下の v2 テール ID）をスタンプします — `/bili/` ルーティングブランチ、生プロバイダー URL 書き換えブランチ（attach モード、V1 fetch パッチ）、**そして**プロキシ直結セルフブランチ（プロバイダー URL がプロキシルートに直接ダイヤルするホスト、例：dsh プロファイルバンドル；これはコンテナ化ゲート実行がそのレーンが静かにチャネルをシードしないことを発見した後に追加されました）— そしてすべての成功レスポンスからスタンプを学習するため、どのレーンもハンドシェイクを再実装しません。

増分レーン（#3248/#4491）との関係 — **一緒に実行安全**、二度処理しません：両方のメカニズムは同じ痛点（プラグインホストの完全履歴再送信）に攻撃しますが、ターンごとにリクエスト形状で分割します。dsh シムの divert は ANTHROPIC-WIRE ボディ（`wireMessagesLookAnthropic`；OpenAI ツール形状 `role:"tool"`/`tool_calls` は常にフルリサンダムに乗る、#3433）でのみ作動します — そして #5403 の形状はまさに逆のワイヤ（chat-completions / openai プロファイル）であり、そこでは増分レーンは決して divert しません。したがって、2つのレーンは競合ではなく補完です：anthropic-wire プラグインセッションは増分レーンによってサーブされ、OpenAI chat-completions プラグインセッションはウォーターマークファストパスによってサーブされます。1つのリクエストは**正確に1つの**パスを歩きます（シムがターンごとに選択）；サーバーサイドでは、`x-bili-plugin-turn` マーカーを持つ任意のリクエストはウォーターマーク評価を完全にスキップします（混合スタンプなし — ゲートマトリクスの `incrementalTurn` 行）、そして divert されたレスポンスは `x-bili-pf-seq` を決して持ちません（代わりに `x-bili-applied-seq` を持ちます）。レーンが構築する合成再エントリリクエストは、pf-* 名のない明示的なヘッダー許可リスト（`PASSTHROUGH_HEADERS`）を持ち、したがってハンドシェイクヘッダーはそのパス経由でも漏れません。残りの無害ケース：混合セッションでは、古い `x-bili-pf-count` が1つの非 divert ターンに伴う可能性があります — それは最大で1回の検証ラウンドのコストしかなく、その後レスポンスが真を再スタンプします。

アイデンティティチャネル v2/v3（オーナーラダー msgid > order > hash、#11）：裸のカウントは境界を**位置**のみで固定します — 要素を書き換えつつカウントを一定に保つクライアントは不可視のままです。私たちのシムがループ内にある場合、リクエストはさらに `x-bili-pf-tail-ids` を持ちます：要素 K−1（前のターンのアンカー）のホストサイドメッセージ ID と、すべての**新しい**要素 — 「几个，不是几十个」（数個、数十個ではない）。ホストは chat-completions ボディに ID を入れませんが、注入された拡張はそれらをホストコンテキストから読み取ります（要素ごとのルールは増分エンベロープと共有、#4491）— したがってホストリリースは不要です。ワイヤ形式はセグメントごとのパーセントエンコーディング（`ids.map(encodeURIComponent).join(",")`）です：区切りカンマはリテラルのまま、ID 内部のカンマは %2C として移動するため、サーバーの分割後デコードは任意の ID アルファベットに対して曖昧さを持ちません。**整合性証明なし（オーナー裁定 2026-11-02）：** ホストは履歴を圧縮し**書き換え**るため、証明ゲーティングは現実と戦い、チャネルを殺しました — msgid は永遠に一意であり、ORDER は検証済みデルタ内でそれらをバインドし、バイトレベルのヘッドチェックは境界の真です。したがってキャプチャは**スロットごと**です：使用可能なホスト ID を持たない要素（ネイティブコンパクト化サマリー `acp_summary_*`、ペルソナサイドカー、外国形状、重複 ID）は、隣人を汚染する代わりに、未知スロットプレースホルダー `?`（ワイヤ上 `%3F`）に乗ります；完全に解決できないリストのみがストレージをクリアします。サーバー裁定：長さ不良 / 重複実 ID / デコード不能セグメント ⇒ このターンの UNcredited 静かデグレード — ブレーカーに向かうことは決してない（シム↔プロキシドリフトはレガシーパス + 再スタンプで自己修復）；prevId ≠ 保存アンカー ⇒ UNcredited、**両方**が既知 ID の場合のみチェック — どちらかの `?` はアイデンティティ主張なし（ペナルティなし）。ヘッダー不在 ⇒ 純粋なカウントモード；v2 以前のすべての動作はバイト単位で不変です。レーンカバレッジ：チャネルはプロトコル統一です — レーンは、**この**リクエストのホスト ID を解決する薄いキャプチャアダプターのみで異なります（オーナールール：クライアント間では「ID がどこから読み取られるか」は異なり得るが、それ以外は異なる）：dsh はスロットごとにホストのディスパッチコンテキストからそれを読み取ります（`pfSlotIdsOf` — 上記の `?` プレースホルダー）、pi は送信ボディに対してセッションブランチエントリをファミリーごとにウォークします（anthropic `laneMsgIdsForWire`、openai-chat `laneMsgIdsForOpenAiWire`）、opencode は増分エンベロープのためにすでに整列した検証済みリストを再利用します（#4491）、omp は `before_provider_request` でホストが stash するブランチエントリのフェッチ層整列を、**実際に**送信されたボディに対してウォークします（`ompTurnMsgIds` — エンベロープが乗る同じコピー）— **anthropic-wire ターンのみ**：その厳格なカウント+ロール証明は、設定組み立ての先頭システムランをブリッジできず、そこでの失敗クリアは同じ会話 ID の共有フックのリストを**消去**します（フックが最初に実行され、このプランナーが最後に実行される）— openai-wire ターンは共有 `laneMsgIdsForOpenAiWire` リゾルバーのみによってカバーされます（#2583 モデルごとのエグレス）。pi/opencode/omp ウォーカーはオールオアナッシングであり、失敗した解決は保存リストを**クリア**します（それらにとって失敗は**位置**知識自体が欠如していることを意味するため、クリアが正直な動きです）— 解決不能なリクエストは古いアンカーに乗るのではなくカウントモードにデグレードします；dsh のスロットごとキャプチャは免除されます（上記）。1つのプロトコル注記：chat-completions ボディは、ブランチエントリを持たない設定/状態から組み立てられた system|developer 要素で始まります；openai リゾルバーはその先頭ランを位置固定合成トークン（`bili-ps-<i>` — スロットごとに安定、文字セット安全、8-hex uuid エントリ ID ターンが HIT であるのは：ウィンドウ原点 K が確定し、プロセス内シード（前のターンの正規コア、モジュールレベル `WeakMap<Session, …>`、パネル分解がセッション真実について正直であるように Session オブジェクトの外に意図的に配置）が同じモデルの下で正確にそのカウントでスタンプされた場合です。**v4 カウント緩和（オーナー裁定 2026-11-02）：** 形状有効な `x-bili-pf-tail-ids` リストがサーバー自身の簿記（`len = T − K + 1`、サーバー側で再検証）と幅が一致する場合、K は台帳（`seed.stampT`）から来て、エコーされた `x-bili-pf-count` は診断に降格します — 欠落または古い/同期外れたエコーはもはやミスを生み出しません（決定文字列は `hit(no-count)` / `hit(count-off=N)` として痕跡を残し、決してブレーカー燃料にはなりません）；そのようなリストなしでは、v4 以前のラダーがバイト単位で不変のまま実行されます（エコーは `stampT` に等しく、T より厳密に小さい必要があります）。最初の `HEAD_CHECK_ELEMENTS`（8）要素はバイト同一のシステムランに変換され、ウィンドウヘッドは system/developer 要素ではありません（引き上げられたシステムは `reconcileSystemAnchor` を同期外れさせるため）。HIT 時、パイプラインは完全な解析の代わりに `[seed cores] + [新鮮に解析されたウィンドウコア [K..T)]` を受け取り、`snapshotMessages` はテールウィンドウのみをピンします。ウィンドウコアはプレフィックスに対して再キー付けされます。なぜなら `openaiToCore` は呼び出し内出現順序でクラスター ID を発行し（`_N` サフィックス付きの `h_<sha256-16>` ベース）、与えられた配列位置から `wireIndex` をスタンプするためです — 繰り返しコンテンツベースは stash されたプレフィックスからその序数を継続しなければ、台帳のアイデンティティ契約が壊れます；K=1 で再キー付けされないウィンドウは、2つの異なるワイヤメッセージをマージさえします（prune は等しい wireIndex で最初のユーザーピンランを拡張します）。

失敗ソフト規律（逸脱防止ロック）：レガシーパイプラインコードは**不変**です — この機能は呼び出し元が供給する入力を交換するのみであり、**任意の**疑念（スタンプなし/不良/古い — v4 上記の台帳有効テール ID リストがリクエストを運ぶ場合を除く；カウント退行 `ahead`、ゼロ成長 `T === K`（台帳有効な1要素リストでも `no-progress` を維持、空ウィンドウは空の `lastMessages` ベースラインをピンする）、モデル切り替え、ヘッドドリフト、ホイスティング危険、壊れたスキャン、アームされたブレーカー）は、そのターンについて不変の完全解析パスにフォールバックし、それは新鮮に測定された T を再スタンプするため、古いクライアントは1ラウンドトリップで収束します。5連続の CREDITED ミスは、レーンを1時間 HIT なしに保持するブレーカーをアームします — 保持されたターンはスキャンと再スタンプを続けます（スタンプなし保持はクライアントのウォーターマークを永遠に孤立させる；そのデッドロックは出荷前にユニットテストで発見され、ピニングされました）。CREDITED は、ミスが明らかに私たちのせいではないことを証明する場合（クライアントが嘘をついたり書き換えたりした）を意味します；未シード/進捗なしミスは無料です。

宣言された信頼境界（§7.4 — 人間レビュー必須、自動マージなし）：要素カウントを一定に保ちつつプレフィックスバイトを編集するクライアントは検出されません — アンカーを除き、そこでは v2 が運ばれた prevId を保存されたものと比較し、再発行された ID は1つの UNcredited ミスと自己修復のコストです。そのトレードオフは、バイトレベル再検証をスキップする価格のすべてです；それは §7.4 人間レビューをクリアし、したがって**実験的**グレーロールアウトとして出荷されます — 約5%のインストールでデフォルト ON（オーナー裁定 2026-11-02：GA 前の小規模コホート、閉じるまですべてのインストールに見える1回限りの Web 紹介通知、3状態クイックスイッチ付き）— A/B ゴールデンが送信バイト同一性をピニングし、インストールごとのオプトイン/オプトアウト（`rollout.features.pluginFullResendWatermark: true|false` / `BILI_ROLLOUT_PLUGIN_FULL_RESEND_WATERMARK=1|0`）。破壊的書き換え（告知コンパクト化、切り詰め、並べ替え）はカウントを変更し、古いコアがカーネルに供給される前に捕捉されます — v4 下では、捕捉はクライアントエコーから幅算術自体に移動します：縮小されたプレフィックスは ID リストが満たせない非正幅を要求するため、CREDITED `ahead` / `seed-stale` 裁定は v4 以前と正確に発火します。

正直な制限：(1) マルチモーダルテール（`image_url` を含むコンテンツ配列）が stash に着地すると、その履歴の残りの部分についてレーンは完全レガシーターンにデグレードします — カーネルはメッセージが最後の要素である場合と履歴中間の場合で、ユーザーコンテンツ配列画像を異なる方法でレンダリングするため、凍結 stash は位置非依存でレガシーバイトを再現できません；テキストワークロード（#5403 レポーターの形状）は影響を受けません。(2) ヘッドフラグメントは、システムランチェックのために各 HIT で再解析されます（8要素）。(3) 両方の `x-bili-pf-*` ヘッダーはアップストリームで剥奪されます（`UPSTREAM_HOP_HEADERS`）— プロトコルヘッダーはモデルトラフィックに決して漏れません。
