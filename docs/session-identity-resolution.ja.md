# セッションアイデンティティ解決（同じクライアント ID、異なる会話）

セッション ID（クライアント発行の会話識別子）が判明した時点で、billion-context がそのリクエストが**どの会話に属するか**をどう決めるかの設計記録。姉妹ページ：`session-identity.md`（姉妹——*匿名*レーン：リクエストが ID を全く持たない場合の対応）、`message-identity.md`（メッセージ単位のアイデンティティ教義）、`docs/identity-channels.md`（そもそも ID を誰が bili に運ぶか）。規範的記述：AGENTS.md KDD #11（アイデンティティ階層）と KDD #18（チャネル配線法）。

## 二つの識別子とその役割

- **セッション ID**（コードでは `rawId`）。クライアントが毎リクエスト送る安定文字列（例：`x-claude-code-session-id`、`agent-session-id`、`x-conversation-id`）。認識（`src/session-id.ts`）は順序付き候補名リストから値を選ぶ——クライアント固有の高信頼名を裸の汎用名より先——その文字列がベースキーになる。リクエストを一山にまとめるだけ；山の中のどの会話かは決して言わない。
- **メッセージ ID**（ホスト発行のメッセージ毎 UUID、例：dsh の正規スタンプ）。存在する場合、同じセッション ID を共有する会話同士の仲裁者になる。正規形ルールは `src/msgid-pin.ts`（長さ ≤512、予約 `acp_summary_` プレフィックス拒否、制御文字拒否）；対称ピン `tests/msgid-rule-parity.test.ts` が手動同期コピーを固定する。

両者はクライアントと bili 間の簿記にすぎない：すべての内部フィールド/ヘッダー（`biliMsgIds`、`x-bili-msg-ids`）はプロキシを出る前に剥離される（`UPSTREAM_HOP_HEADERS`）。どちらもモデルエンドポイントに到達することはない。

## 解決ラダー（`src/session-resolve.ts`、`resolveSessionOrder`）

各セッション ID の下、リゾルバは**スケルトン**を保つ：メッセージ種順列、先頭フラグメントハッシュ、system/persona テキストの sha256（"" = アンカー非）、宣言モデル——デバウンス永続化され、再起動でコールドスタートクレーム競争が再実行できない（#3397）。到着する各リクエストは以下を順に踏む：

1. **ディスパッチレーントークン**（#5095）：ディスパッチ毎トークン（claude サブエージェント）は自分の決定論キーを即座にクレーム——裏付け不要。
2. **ID 下での初認**。メイン形状の履歴が生のキーをクレーム。タグなし浅い履歴（単一 user blob、assistant ターンなし）は決してクレームしない——`<id>|sub:aux` を得る；散文を一切読まずに #1916 の review-steals-raw 競争が死ぬ場所。
3. **バイトレベル継続**。プレフィックス整列 + 末尾フラグメント検証。ほぼ全ターンをカバーする高速パス。
4. **persona テキスト変更（同じ ID、異なる system プロンプト）**。脱出階段、各々が*逐語*の内容証拠を要求——「新しいプロンプトで履歴を継続」vs「共有 ID 下の見知らぬ者」：
   - 先頭フラグメントが逐語再生（アンカー移行、#2241/#2250）；
   - ヘッダーで裏付けられた宣言モデル変更（#2601/#2817）；
   - 再起動後の永続プレフィックスチェーン連続性（#2156/#2815）；
   - 同じ履歴のホスト側編集を証明する ≥8 の同インデックス一致ラン（#4778、`CONTINUATION_MIN_RUN`）；
   - フラグメント検証済み末尾を保持する短い再生（#5686）。
   いずれかの階段を通る → **生のキーへ再アンカー**。すべて失敗 → **派生 persona レーン** `${sessionID}|sub:<fp16(personaText)>` —— 決定論サフィックスなので、同じ persona の連続呼び出しは常に同じレーンに着地し、レーン数はトラフィックで増えない。
5. **同じ persona、分岐した順序**。末尾整列再アンカー（スケルトンは生きた端に従う）；本当に整列しない形状 → 派生タスクレーン `${sessionID}|sub:task:<skel8(kinds)>`。
6. **最後の手段メッセージ ID 階段**（#5719、`tryMsgIdRescue`）。バイト証拠が*そのターン内で破壊された*ために全バイトレベル階段が失敗した出口でのみ参照される（クライアント圧縮が system プロンプトフィールド書き換え中に行を削除——#5719 事故）。≥1 個の到着ホスト ID が統一ストア内のセッション ID キー下に記録された行と一致 → 同じ会話、再アンカー。ゼロ重複 → フォークを確認。リクエストに ID なし → フォークは #5719 前と全く同じように進む。

下流すべて（ストレージ行、フォールドブロック、ウォーターマークシード、台帳 seq）はラダーが返したキー——生かサフィックス付き——でキー付けされるため、1 つのセッション ID 下の 2 つの会話は独立して保存、フォールド、圧縮される。

### なぜメッセージ ID 階段が最後で最初にないか

ルール自体は無条件：**セッション ID 一致 + ≥1 個重複メッセージ ID ⇒ 同じ会話**、追加条件なし（オーナー教義、`src/session-resolve.ts` `tryMsgIdRescue` で正確に実装されている）。意図的なのはラダー中の位置である。記録された根拠（オーナー議論 2026-11-07；裁定：現状維持）：

1. **意味的非対称性。** *ゼロ*重複は安全な陰性証拠；*陽性*重複は「同じ会話」を証明しない——正当に 1 つのセッション ID を共有しながら別の役割に属するフロー（以前の履歴を埋め込む review/title/派生トラフィック——事故 #150 fresh task、#1916 auto-review、#4438 review rides the raw key through the full pipeline）。重複判定をグローバル第一段階として走らせると、構造チェックが分離する前にそれらのリクエストをメイン会話として分類し、スタンプレーンでは——メインフローが毎ターン ID を付した全過去メッセージを再送するので、重複は*構造的に*成立——多役割分割が恒久的にショートカットされ、以降の全階段がデッドコードになる。正しさは判定自体ではなく、上流クライアントが偶然 ID を省略することに依存することになる。最後に置くことで、同じルールは構造証拠が既に「新しい会話」と言い、かつ既知の良性理由でバイトチェーンが切れた場所で初めて発火する——そこで「ある程度の重複」は他のあらゆる説明を除外する。
2. **データ局所性。** 継続チェックはメモリ内スケルトン（前のリクエストで満たされる）上で走る；保存されたメッセージ ID セットはデータベースにある。比較は安いもののディスク backed のチェックをメモリ resident のものより前に置くと、ホットパスにターン毎ストア読み取りを加える。
3. **可用性。** ほとんどのレーンはメッセージ ID を全く持たない（未スタンプ、未配線）；そのリクエストには階段自体が存在しない。

## 切り替えレイヤー（何が統合され、何がオフのままか）

| レイヤー | 機構 | 統合後の既定 |
|---|---|---|
| セッション ID 認識（新規名 `x-conversation-id`、`agent-session-id` 含む） | ゲートなし；値はクライアント供給、ローカルキーとしてのみ使用、転送されない | すべてのインストールで有効 |
| メッセージ ID ハーベスト（プロキシがクライアントローカル transcript/sqlite を読む：claude-code、codebuddy、mcode、goose、qwen-code） | `env BILI_IDENTITY_HARVEST` **または** コホート `rollout.features.identityChannelHarvest`（どちらだけでも有効）× ループバックソースのみ | オプトインまで**どこでも off** |
| 行ピンニング（スタンプ/ハーベスト ID を保存行アイデンティティに書き込む、両ワイヤ） | 既存コホート `pluginLaneServerHistory` | 0%（不変） |
| 内部 ID フィールド/ヘッダーの上流転送前剥離 | 無条件 | 中立（フィールドは出ることすら想定されていなかった） |

レーン毎の完全ステータステーブル（配線済み / クローズメモ / 保留、監査理由付き）：`docs/identity-channels.md`。

## 信頼境界と劣化契約

- **ターン全体劣化、部分的誤ペアリングは絶対にしない。** いかなるステップの失敗（行数不一致、破損ファイル、スキーマドリフト、検証拒否、ロールスポットチェック不一致）も、そのターンの候補リスト全体を破棄し、リクエストは配線前パスと全く同じにフォールバックする。一部のメッセージをマップして残りを見当つけるモードはない。
- **ループバック限定ハーベスト。** レジストリは有効化されていても非ループバックソースを拒否する；アダプタは信頼されたローカルクライアントを前提とする。
- **レイアウト知識はソース監査グレード。** アダプタの期待（テーブル、列、順序、どの行がカウント対象か）は上流ソースを読むことから来て、測定インストールからは来ない——ハーベストをオプトインスイッチの後ろに出す理由。
- **フォーク安全性。** 唯一の誤割り当て前提は、1 つのセッション ID 下で長い*逐語*内容を共有する 2 つの異なる会話；フラグメントはハッシュグレードなので実際には起こらない。文書化されたコーナー：浅い aux 呼び出しが先に到着して空 ID を巡って競争しうる；メイン会話はその後、永続プレフィックスチェーン階段で回復または分離——回帰ピン済み（初認クレーム規則、#316；#1916 aux 分岐）。
- **#5719 階段の到達可能性注記。** review/aux ディスパッチが親の行と重複するスタンプ ID に乗るか否かはホスト挙動に条件付き——1 行トレースログフォローアップとして追跡（PR #5826 レビュー所見 P1）、推測で故意にクローズしていない。約束されたトレース行は現在存在する：各発火が `[session-resolve][msgid-rescue] <rawId> hits=N/M exit=<tag-changed|diverged-order|shorter-divergent>` を warn で記録（`src/session-resolve.ts`、#5865 レビュー P2）——≥2 vs ≥1 の閾値決定はそのフィールド証拠から行うべきで、推測によるものではない。

- 新規ハーベストレーン：新規 `src/identity-<client>.ts`（自己完結、独自ストレージリーダー、認識済みセッション ID のみで結合）+ `src/identity-sources.ts` の登録行 1 つ + 両チャネルドキュメントの行 1 つ。利用箇所からクライアントストレージを読むことは絶対になし（KDD #18）。

- いかなる新規内部 ID キャリアも `UPSTREAM_HOP_HEADERS` と対称ピンのバリデータ表面（`tests/msgid-rule-parity.test.ts`）に加えなければならない。
