# メッセージ ID レーンインフラストラクチャ：sessionid+msgid の生産/消費マップ

> ステータス：#5826 リリースレビューが命じたギャップ修正の姉妹ドキュメント（オーナー裁定 2026-11-07）。アイデンティティラダー教義は message-identity.md（kernel）と session-identity.md（セッション側）にある；このファイルは*1 つだけ*の仕事——クロスレーン公共基盤である sessionid+msgid がどこで生産され、どう運ばれ、誰が検証するか（6 コピー）、どこにピンされ、その 5 つの消費者と宣言された信頼境界を説明すること。これらに触れる前にこれを読むこと。

## 1. 何ものか

4 つのプラグインレーン（dsh / omp / opencode / pi）はホストが全メッセージに安定 UUID（**msgid**）をスタンプし、各リクエストとともに上流に乗る；bili はメッセージアイデンティティをそこにピンする（書き換え/並べ替え/圧縮を生存）。サーバー側 **sessionid** = ホスト会話 ID（persona 分割ルール後 `|sub:<fp>` サフィックスを持つことがある、KDD #9）。両者合わせで台帳トリプル `(session_id, msg_id, content_hash)` の最初の 2 次元：msgid がアイデンティティを固定し、コンテンツハッシュが誤ペアリングを守る（KDD #11/#13 がラダーとスナップショットレンダリング教義を持つ；ここでは繰り返さない）。

## 2. 生産（誰が ID を作るか）

| レイヤー | 内容 | 場所 |
|---|---|---|
| ホスト発行 | ホストが会話スコープ内でメッセージ毎安定 UUID を割り当てる（圧縮後再利用なし）；`acp_summary_*` ネームスペースは kernel 合成アンカーに属する——ホスト ID はこれをクレームしてはならない | dsh: `options.messages[].id`；pi/opencode/omp は各自のホストフィールド経由 |
| dsh 薄集約器 | `hostMsgIdsOf`（全有無）+ `pfSlotIdsOf`（スロット毎変種、悪いスロットは `?` で乗る） | src/agent/dsh-native.ts (~:1186/:1202) |
| pi パーサー | `laneMsgIdsForWire` / `laneMsgIdsForOpenAiWire`；**正規バリデータを直接呼ぶ**（ミラーではなく）；設定組み立て先頭 system スロットは枝エントリなし → 合成 `bili-ps-N` 位置トークン | src/agent/pi.ts |
| opencode / omp | 同じ既に検証済みリストを再利用（transform フック / `ompTurnMsgIds` fetch レイヤー整列、anthropic ワイヤターンのみ） | src/agent/opencode-native.ts / omp レーン |

規律：集約器は「取得と前選別」のみ；アイデンティティ裁定権を持たない——裁定は §4 バリデータと §5 ストレージにある。

## 3. トランスポート形状（ID がどう上流に乗るか）

4 つのキャリア、**すべてモデルアップストリーム転送前に剥離される**——モデルワイヤはまだメッセージレベル ID を持たない（#2821 教義）：

1. **エンベロープフィールド** `biliMsgIds`：フルリセットモデルボディ上の並列配列、messages に長さロック、同じライフサイクル（ingress で剥離、src/server/prepare-anthropic.ts など）。
2. **増分ターンペイロード** `msgIds`：`POST /__bili/plugin/turn` のエンベロープ（src/agent/incremental-client.ts）；サーバーが `biliMsgIds` を再スタンプ（src/incremental-lane.ts）。
3. **ウォーターマークヘッダー** `x-bili-pf-tail-ids`（v2-v4、#5403/#5418）：ウィンドウ区間のみ = 最後のアンカー要素 + K 以降追加された全要素、セグメント毎パーセントエンコード、カンマ区切り（ID 内のカンマは `%2C` で乗る、セパレーターは文字のまま）；兄弟 `x-bili-pf-count` カウントスタンプ。pf-* ヘッダーは**プロトコルヘッダーでありホップヘッダーではない**：`UPSTREAM_HOP_HEADERS` 経由で上流前に剥離。
4. **台帳 seq 兄弟** `biliLedgerSeqs` / `ledgerSeq` スタンプ（#4316 L3 PR2/3）：1 始まり正整数並列配列、`validateMsgSeqs` で検証、同じ厳密検証後劣化ライフサイクル。

## 4. 検証コピー（なぜ 6 つか、どう同期を保つか）

構造制約：**注入されたホストバンドルは外部ランタイム内で動いてサーバーモジュールを import してはならない**（src/agent/dsh-native.ts ~:1177、src/agent/incremental-client.ts ~:227 の制約コメント）。ミラーリングはしたがって怠慢ではなく構造的必然。6 コピーとその選別面：

| コピー | 場所 | 役割 | 厳密性プロファイル | 劣化方向 |
|---|---|---|---|---|
| **正規** `validateMsgIds` | src/msgid-pin.ts | ingress ゲート（フルリセット + 増分ターンゲート） | 厳密全有無 + 正確な長さ；拒否：非文字列/空/長すぎる(>512)/予約プレフィックス/\s/\p{C}/重複 | フィールド破棄 → ターンがコンテンツハッシュ/ID にフォールバック |
| 寛容受信変種 `incomingMsgIdsOf` | src/msgid-pin.ts | #5719 最後の手段階段入力 | 幅契約なし、**重複排除ゲートなし**；制御クラス = `\s`+C0/Del のみ（U+200B は通過） | undefined → #5719 前パス |
| dsh ホストミラー | hostMsgIdsOf / pfSlotIdsOf (src/agent/dsh-native.ts) | ホスト側収集 | 全有無 / スロット毎 `?`；完全 \p{C} クラス | ターンが非増分にフォールバック / スロットが ? で乗る |
| incremental-client ミラー `screenMsgIds` | src/agent/incremental-client.ts | エンベロープに乗る前の前選別 | 全有無ブール | 「no field」フォールバック（400 で全リクエストを殺すのを回避） |
| pf チャネルインライン選別 | src/agent/pf-channel.ts (capture ~:99) | ウォーターマーク ID 捕捉状態機械 | スロット毎 `?` + `MAX_IDS=2048` 上限 + 解決失敗が保存リストをクリア | カウントのみモード |
| ワイヤデコード `parseTailIds` | src/server/fastpath.ts | tail-ids ヘッダーのサーバー側デコード | 全セグメント無効化；#5826 レビュー時点で完全な正規拒否集合を強制（予約プレフィックスゲートクローズ） | このターンカウントのみ、ブレーカークレジットなし |
| 証拠のみ寛容 `collectRequestIds` | src/request-membership.ts | #4805 決済メンバーシッププローブ入力 | 悪いエントリをスキップ（無効化しない）、制御文字スクリーニングなし、再送 toolCallIds にフォールバック | 空証拠 → このサイクルメンバーシップ未解決 |

**機械的ロック：`tests/msgid-rule-parity.test.ts`。** すべての拒否クラスが全コピーに通され、現在の判定がコピー毎アサートされる。意図的分岐は*分岐として*ピンされる（例：U+200B が `incomingMsgIdsOf`/`collectRequestIds` を通過——両者は純粋証拠役割；そのような ID は厳密ピンされた保存 ID と決して重複しないので誤アンカーできない）。いかなるコピーのルール変更も、理由付きマトリクスを意図的に再ピンするまで CI が赤になる。「同期を保つ」コメントは今や CI backed。

レビューからの一回きりのクローズ：`parseTailIds` だけがデコード側に予約プレフィックスゲートを欠いていた；ここでクローズ。すべての本番エミッターは既に前選別済みなので、これは単一サーバーチョークポイントでの防御の多層化で、より保守的（リスト全体無効 → 劣化）、ゼロの動作表面。

## 5. 永続化の唯一の真実源

統一ストアの `messages.msg_id` 列が唯一の ID 真実：ingestion が検証済み ID を行にピンする（T5 裁定：並列台帳なし；スケルトン行は ID を持たない）。台帳主キー `(session_id, msg_id, content_hash)`；正規行は**コンテンツハッシュではなく MSGID** でキー付け（#4491）；フォーク複製が番号を保持（#4316 L3 PR3/3 `cloneSessionRows`）。

## 6. 消費者（5 つ；それぞれが ID に何を尋ねるか）

| 消費者 | 場所 | 答えられる質問 | ID 使用境界 |
|---|---|---|---|
| ① ストレージ列アイデンティティ | 統一ストア `messages.msg_id` | 全決済/reconcile パスの結合キー | 単一のアイデンティティ空間入口点；他の 4 つの ID 証拠は最終的にここに折り込まれる |
| ② session-resolve 最後の手段階段 #5719 | tryMsgIdRescue (src/session-resolve.ts ~:324；フォーク出口呼び出し箇所 ~:432/:481/:501) | バイト/tag 証拠が破壊された後（圧縮がセル削除、system 書き換えがフラグメント削除）、このリクエストは*同じ*セッションか？ | 同じ raw キー下で*任意*の ID 重複 ⇒ 同じセッション；注：レーン帰属なし（§7 境界 B） |
| ③ 決済メンバーシッププローブ #4805 | probeRequestMembership (src/request-membership.ts；呼び出し箇所 src/server/prepare-openai.ts:597, prepare-anthropic.ts:640；消費 cache-ledger.ts:1866) | この ID はこのセッションの台帳に許可されたか？ needle = 最新許可 ID | **純粋証拠——アイデンティティ空間に入らない**、再キー付け/フォークしない；最悪 1 サイクル未決済、自己修復 |

## 7. 信頼境界（バグではなく契約の一部として宣言）

- **A. §7.4 ウォーターマークブラインドスポット：** 要素数を不変にするプレフィックスタイプ編集は検出不能。人間レビューゲート、決して自動マージ；マルチモーダル末尾がキャッシュに入ると、その履歴は永久に legacy ターンへ劣化する。
- **B. #5719 最後の手段階段にレーン帰属がない：**「任意 ID 重複 ⇒ 同じセッション」はメイン vs 補助レーンを区別しない。ホストが persona/review サイドディスパッチに重複 ID をスタンプする場合（共有 ID 空間、または親ターン ID を埋め込む review）、フローはメインセッションにアンカーし `record()` がスケルトンの tag/model をフォーク自身のものに上書きする。ホストが本当にそうするかは repo から証明不可能——条件付きリスク、処置はオーナー裁定待ち（トレースログ提案は #5826 コメント内）。素朴な tag 等値前提は拒否：dsh はターン毎 system プロンプトをローテーションするので、*同じ*レーンの隣接ターンは異なり、その前提は救助自体を殺す。
- **C. membership needle が aux 埋め込みで貫通可能：** 親ターン ID を埋め込むサイドリクエストはプローブ needle を古い行に着地させうる → そのサイクル決済未解決（次のメイン規模リセットで自己修復）。証拠のみ役割下で最大 1 ロストサイクル；許容。
- **D. ホスト発行前提：** ID は会話スコープ内で安定かつ一意、圧縮後再利用なし。封じ込め：誤ペアリングは自分の raw キー下の記録を汚染するだけで、それ以外は汚染しない。

## 8. 変更規則（これらに触れる前のチェックリスト）

1. いかなる拒否クラスの追加/変更/削除も → 厳密ファミリーの全コピー（`validateMsgIds`、`incomingMsgIdsOf`*、dsh ミラー両方、`screenMsgIds`、pf-channel インライン、`parseTailIds`）と tests/msgid-rule-parity.test.ts のマトリクス行を、1 つの変更で更新。（*`incomingMsgIdsOf`/`collectRequestIds` の寛容性は意図的；変更にはオーナーレベルの正当化が必要。）
2. 新規消費者はコードを書く前に §6 に 1 行登録する。
3. ホストバンドルはサーバーモジュールを import してはならない（§4 構造制約）；新規ミラーは対称テストに自分の行を得る。
4. ID は上流可視ボディ/ヘッダーに到達しない（strip 規律、§3）；pf-* ヘッダーはプロトコルヘッダー地位を維持。
5.「ID 不一致 / destroyed 誤診 / キャッシュ壊れ」系バグを議論する前に、message-identity.md ラダーとここ §6 を確認し、そのセッションがどの消費者パスを通るか確立する。
